## 一 门槛修正：30 Hz 从来不是要求

> 🔴 **本节及全文所有 Hz 数字都带 15.625 ms 量化误差（2026-10-24 晚已确认并修正）**
> `hmd.jsonl` 的 gap_p50 在 **15 场录制里全部等于 62.000 ms**（= 4 × 15.625 ms 系统 tick），
> 一秒不差 ⇒ 真实位姿间隔落在 **47–78 ms** 之间都会报成 62 ms。
> **本文 §五 的归因（「位姿路径本身吃掉 ~60 ms」）是错的**：实际是 Windows 定时器的
> `Event.wait` 量化 + `time.monotonic` 的 16 ms 读数台阶。改用 `backend/pacing.py` 的
> Pacer/Gate 后真机是 **pose 20.00 Hz / stereo 10.00 Hz**（见文末「订正」）。
> ✅ 仍然成立的是：①门槛是 10 Hz 不是 30 Hz；②`stereo_ticks` 这类计数；③一切空间量。

部署代码 `nav_online.py` 的三个频率各管各的：

| 量 | 配置 | 实测（本文真机） |
|---|---|---|
| 位姿 | `pose_hz = 20` | **16.59 Hz**（gap p50 62 ms） |
| 双目 | `stereo_period_s = 0.1` ⇒ 10 Hz | **8.33 Hz**（`stereo_ticks = 2.02`） |
| 关键帧 | 非周期（位移/转角/时长三选一） | **0.33 Hz**（静止时） |

⇒ **立体深度喂的是建图（关键帧平均 1.86 Hz），不是逐帧控制。** 用 33.3 ms 淘汰模型的口径从根上就不对，之前几轮「学习型立体全部超标」的判定需要按 10 Hz 重读。

## 二 部署块实测（不是模型单独）

之前的计时都是「模型单独、输入已在显存」。把 `stereo_points` 后处理算进去才是感知线程真正付的钱（每组 200 次）：

| 分辨率 | 方案 | p50 | p90 | p99 | 占 10 Hz 预算 |
|---|---|---|---|---|---|
| 720×405 | SGBM CPU nd=64 | **21.2** | 24.4 | 28.8 | 21% |
| 720×405 | LAS2-M 编译 half+合批 | **51.0** | 60.8 | 84.4 | 51% |
| 1080×608 | SGBM CPU nd=96 | 64.6 | 73.2 | 87.3 | 65% |
| 1080×608 | LAS2-M 编译 half+合批 | **58.7** | 69.7 | 98.4 | 59% |

🔴 **1080 档出现交叉：SGBM 反而比 LAS2 慢。** SGBM 随像素线性增长，LAS2 是 launch-bound 几乎不涨（720→1080 像素 ×2.25，部署块延迟 51.0→58.7 ms 只 ×1.15；SGBM 21.2→64.6 ms 是 ×3.05，视差范围随 fx 一起涨）。

⚠️ **测量漂移**：720 档 LAS2 这里 51.0 ms，而模型单独测是 58.5 ms（加后处理反而更快，逻辑上不可能）⇒ 跨会话漂移约 **±10%**。**方向可靠，绝对值别用来卡边界。** 1080 档的 58.7 ms 是另一次实测。

## 三 解耦线程的实现

⚠️ **采集不能挪**：D3D11 立即上下文不是线程安全的，`OpenVRSensors` 的方法只能在感知线程里调。所以拆的是**重活**，不是采集。

| 部分 | 位置 | 理由 |
|---|---|---|
| `read_stereo` / `read_rgb` | 感知线程 | D3D11 上下文不可跨线程 |
| 视差 + 点云 + 近距判定 | **`_stereo_worker_loop`** | 这是 51 ms 的主体 |
| `KeyframePolicy.decide` | 感知线程 | 按 tick 算位移/转角/时长，必须在位姿时钟上 |
| ORB 特征 | `_stereo_worker_loop` | 只触发在关键帧上 |

交接是**纯快照 + 丢弃最新**：`queue.Queue(maxsize=1)` + `put_nowait` + `queue.Full: pass` ⇒ **位姿线程永远不会因为双目排队而阻塞**。`_commit_keyframe` 抽出成共享方法，内联与解耦两条路径行为逐位一致（不是复制粘贴两份）。

配置：`decoupled: bool = True`、`stereo_min_period_s: float = 0.02`。

## 五 为什么位姿只有 16.59 Hz（瓶颈不在双目）

内联时 tick 62 ms，把 51.7 ms 的双目块拿走后仍是 ~60 ms ⇒ **双目块大部分与 I/O 等待重叠，从来没真正阻塞过位姿**。

🔴 这条推翻了一个直觉上很合理、但没被验证过的假设。**下一步要 profile 的是位姿路径本身**（SteamVR `getDeviceToAbsoluteTrackingPose`、`DeadReckoner.update`、OSC 历史遍历），不是双目。

⚠️ **但注意 `stereo_ticks` 的因果链方向**：位姿慢 ⇒ 量化台阶 ⇒ 立体被压到 8.33 Hz。所以**修位姿是提升立体频率的唯一路径**，调 `stereo_period_s` 无用（这条与 `nav_online.py` 的 `RateMeter` 文档串一致）。

## 六 GIL 争用下的 LAS2（原标题「不可用于线程化管线」，已被订正 B 推翻）

> 🔴 **本节的数字是真的，结论和根因是错的（2026-10-24 深夜订正）**。
> 81.5× 的竞争者是「主线程不停跑纯 Python 循环」，真实管线里没有这种线程；
> 机制也不是 Dynamo guard 遍历调用栈，而是 **Windows 下 GIL 等待被 15.625 ms 定时器量化**。
> 见文末「订正 B」。

三组对照，同一台机器、同一时段：

| 竞争负载 | LAS2 块（编译版） | 相对空闲 |
|---|---|---|
| 空闲 | 49.3 ms | 1.00× |
| numpy 竞争 53 ms（**释放 GIL**） | 72.2 ms | 1.46× |
| python 竞争 53 ms（**持有 GIL**） | **4017.8 ms** | **81.50×** |
| python 竞争 26 ms（持有 GIL） | 3686.7 ms | 74.79× |

同一个负载下，**SGBM 只慢 1.60×**（19.1 → 30.5 ms）。

根因：`torch.compile` 的 Dynamo guard 每帧要走一次 **Python 调用栈遍历**；纯 Python 循环把它拖垮。**eager 版只慢约 2.3×**（同条件下 p50 111.8 ms），差别全在 wrapper。⇒ 这是 `torch.compile` 的固有开销，与模型本身无关。

🔴 **推论：LAS2 越快（GPU 上耗时越短），Python guard 的固定开销占比越高，而且负载越轻相对惩罚越大（26 ms 时 74.8×）。在真实管线里无法通过「少给这个线程活」来回避。**

## 订正 A（2026-10-24 深夜）：§4/§5 被 Windows 定时器推翻

本文写作时（下午）测的 18 Hz 不可复现。**同日晚上的调查发现根因是测量工具**：`Event.wait` + `time.monotonic` 在 Windows 上分辨率不够。

### A.1 被推翻的陈述

| 原文 | 实况 |
|---|---|
| 「解耦收益 +5%（内联 18.01 → 解耦 18.93 Hz）」 | **不可复现。** `Event.wait` + `time.monotonic` 的组合下，无论 body 耗时取 0.3–47 ms，实测 gap 恒为 **62 ms（≈16.1 Hz）**；18–19 Hz 只能在外部进程调过 `timeBeginPeriod(1)` 时出现，是环境噪声不是代码行为 |
| 「内联把位姿压到约 11 Hz」 | 同样是量化伪影，实测推翻 |

### 真正的根因

两个独立的 Windows 机制叠加：

1. **`threading.Event.wait` 向上取整到 15.625 ms 系统 tick** —— 请求 49.7 ms 实测 **62.26 ms**；
2. **`time.monotonic` 本身是 `GetTickCount64()`** —— 读数台阶 **16.000 ms**，**纯忙等也对不准 50 ms**（自旋误差 p50 6.0 ms）。

⇒ 只换等待原语**没用**，必须同时换时钟。这条是本文最该记住的教训：**先确认测量工具的分辨率，再相信它给出的差异。**

### 修完之后的实测

`backend/pacing.py`（Pacer：perf_counter + sleep + 1.5 ms 自旋；Gate：绝对累加）接进感知/控制循环后，真机 SteamVR 30 s：

```
pose_hz      20.00   (目标 20.0)   gap p50 0.050 s
stereo_hz     9.96   (目标 10.0)   gap p50 0.100 s
errors       []
```

回归护栏：`tests/test_pacing_regression.py`（读真实 gap；已验证故意把频率减半会红）。
完整根因与双时钟契约见 `FACTS.md` 的「感知循环 16.1 Hz 的根因」与「双时钟契约」两行。

### 仍然成立的

§三（解耦的实现，采集不能挪）、§八（LAS2 家族与跨系列裁定）、§九（精度）**不受影响**：那些测的是 `perf_counter` 域下的耗时和真值误差，与本次时钟问题无关。

## 订正 B（2026-10-24 深夜）：§六 的 GIL 问题根因推翻 + 双 venv 割裂已解决

§六 测出的 81.5× 是真实数字，但**成因和结论都被推翻**。

### B.1 被推翻的陈述

| 原文（§六） | 实况 |
|---|---|
| 「有别的 Python 线程持 GIL 时慢 81.5×」 | **条件写得太宽。** 81.5× 的竞争者是主线程**不间断**跑纯 Python（`.tmp/block_contention.py`：`work_python(53)` 后 `sleep(0)`，占空比约 100%）。真实管线里没有这种线程：位姿/控制是 Pacer，大部分时间在 `sleep` |
| 「根因是 Dynamo guard 每帧走 Python 调用栈」 | **推翻。** 同一个半占空负载下（`.tmp/gil_test.log`：竞争者忙 53 ms、睡 50 ms），编译版 101.7 ms、eager 版 209.9 ms，相对各自空闲（约 50 / 105 ms）**都是约 2×** ⇒ 编译 wrapper 没有额外惩罚。「eager 只慢 2.3×、差别全在 wrapper」是拿两种负载比出来的 |
| 「负载越轻相对惩罚越大（26 ms 时 74.8×）」 | **推翻。** 26 ms 与 53 ms 两档竞争者都是不间断循环，占空比相同，所以倍数相近 |
| **「不能进这条管线」** | **推翻。** 真实架构（双目独立线程 + 位姿 Pacer 20 Hz + 控制 Pacer 10 Hz）下 LAS2 只慢 **1.5%**（`.tmp/retest_gil.log`，Py3.11：52.3 → 53.1 ms）；SGBM +1.4%（21.9 → 22.2 ms）。位姿 Pacer 自旋 1.5 / 0.5 / 0 ms 三档结果相同（53.2 / 51.7 / 51.6 ms） |

### B.2 真正的根因：GIL 等待超时被 Windows 定时器取整（与订正 A 同一个机制）

CPython 在 Windows 上等 GIL 是带超时的等待，超时 = `sys.getswitchinterval()`（默认 5 ms）；等满超时才要求持有者让出。超时换算成毫秒时**截断取整**，于是：

1. switchinterval < 1 ms ⇒ 超时截成 **0 ms** ⇒ 立刻要求让出；
2. switchinterval ≥ 1 ms ⇒ 等待被系统定时器**向上取整**，本进程没调 `timeBeginPeriod` 时是 **15.625 ms**。

LAS2 编译版每帧有几百次 GIL 释放/重取（kernel launch、同步、拷贝）。对手**不间断**跑 Python 时，每次重取都要等满一个取整后的超时。`.tmp/convoy_probe3.py`（Py3.14，同一进程连续测，只计竞争期内完整跑完的帧）：

| 条件 | 每次等待 | LAS2 p50 | 相对空闲 | p50 ÷ 每次等待 |
|---|---|---|---|---|
| 空闲 | — | 50.9 ms | 1.00× | — |
| switch 0.2 ms | 0 | 73.3 ms | 1.44× | — |
| switch 0.9 ms | 0 | 73.9 ms | 1.45× | — |
| switch 1.0 ms | 15.625 ms | 11277.0 ms | 221.41× | 722 |
| switch 5.0 ms（默认） | 15.625 ms | 11226.8 ms | 220.42× | 719 |
| `timeBeginPeriod(1)` + switch 5.0 ms | 5 ms | 3681.4 ms | 72.28× | 736 |
| `timeBeginPeriod(1)` + switch 1.0 ms | 1 ms | 754.1 ms | 14.80× | 754 |

⇒ **断崖正好在 1000 µs**。四种等待时长下「帧耗时 ÷ 每次等待」都落在 **719–754**：帧耗时 ≈ 每帧约 730 次 GIL 交接 × 每次等待。这和订正 A 里 `Event.wait` 被取整到 15.625 ms 是**同一个 Windows 机制**，只是受害者换成了 GIL。

- **SGBM 为什么只慢 1.60×**：一帧只有一次 `compute()`，GIL 只交接几次。区别在交接次数，不在 guard。
- ⚠️ 探针启动时全局定时器分辨率已是 1.000 ms（别的进程调过），但本进程不调 `timeBeginPeriod` 时仍按 15.625 ms 等（719 × 15.625 ≈ 11227）⇒ 别的程序调高分辨率**不会**替本进程修。
- **真实管线为什么没事**：Pacer 线程大部分时间在 `sleep` 里**主动**放掉 GIL，主动释放会立即唤醒等待者，不走超时。只有别的线程**连续**跑纯 Python 超过一个超时，LAS2 才付这笔钱。Pacer 自旋 0 / 0.5 / 1.5 ms 结果相同（B.1），所以**自旋长度不是原因**。

🔴 **剩余风险（未测）**：建图/回环线程里若有长段纯 Python（例如回环里的 Python 循环），LAS2 那一帧最坏被拖长约这段的长度。`sys.setswitchinterval(0.0009)` 能把最坏情况压到 1.45×，但它是整个解释器的全局设置；插件若与宿主同进程，会影响宿主，上线前要评估。

### B.5 上 1080 长边：现状与前置清单

**先纠正一个口径**：`capture_width=1080` 拿不到 1080×608。`_mip_for` 取「仍不小于目标」的最深 mip，2880×1620 的 mip 链只有 1440×810 / 720×405 ⇒ **1080 实际走 mip1，输出 1440×810**（2026-10-25 实测 `_mip_for(2880, 1620, (1080, 1)) = 1`）。真正的 1080×608 要在 mip1 之后加一次 CPU `INTER_AREA` 缩放；`MirrorEye.map_rgb(size=...)` 已支持，但 `OpenVRSensors.read_stereo` 没把 `size` 传下去，内参也要按 1080 重算。

**已有的 1080 证据（全是 Middlebury 离线，不是 VRChat 镜像）**：

| | SGBM（nd=96） | LAS2-M 编译 half+合批 |
|---|---|---|
| 部署块 p50 / p99 | 64.6 / 87.3 ms | **58.7** / 98.4 ms |
| 同像素 EPE / bad1 / relZ | 1.783 / 13.9% / 0.587% | **1.194 / 8.6% / 0.484%** |
| 8–16 px 带 bad1 | 18.6% | **3.7%** |
| 64+ px 带 bad1 | **9.2%** | 17.0% |

**已核对、不用改的**：

1. 深度尺度不随分辨率变：fx 与视差同比例（`nav_online.py:117-119` 注释），`stereo_points` 的 `step=2` 也是像素级，点数随面积涨约 2.25×；
2. SGBM 视差范围按 fx 自动缩放：`disparity_range_px` 在 fx 202.5 / 303.75 / 405 下给 64 / 96 / 128；
3. 回环 PnP 用的是每帧存下的 `K`（`nav_loop.py:151`），跨分辨率会话的内参不会混。

**要做的（按顺序）**：

1. **LAS2 后端还没接进 backend**：backend 里没有任何 torch/LAS2 代码，只有 `make_sgbm`。需要一个可选的视差后端（`stereo_disparity` 的 `matcher` 换成 LAS2 包装），首次编译 70–330 s 要放到启动时预热；
2. **决定 1080 的实现**：直接用 mip1 的 1440×810，还是 mip1 + CPU 缩到 1080×608。1440 档 LAS2 模型单独 51.6–66.2 ms（`.tmp/las2_family.log`），但 `max_disp` 对 M 无效（§8.2），1440 档会截断在 192 px；
3. **ORB 与词汇树**：`orb_features = 1000` 不随分辨率变，同样 1000 个点在 2.25 倍面积上更稀；`models/bow_vocab.npz` 用 720 档录制训练。都要用 1080 录制重测召回，必要时重训；
4. **真机验证**：`.venv_las` 下跑真实 SteamVR + 镜像 + LAS2，看 `status.rates` 位姿仍 20 Hz、立体 10 Hz，并开 `record_images` 存一段 1080 原图，留作受控重放；
5. **建图/回环线程同跑时的 LAS2 耗时**（B.2 的剩余风险）。

⚠️ **与旧建议的关系**：`全分辨率验证录制SOP（2026-10-05）.md` §9.6 写「不建议直接把 `capture_width` 改成 1440」，理由是**位姿与双目同线程**时 B 段 `loop 235 ms` 超立体周期 2.35 倍、占 `pose_stale` 47%。双目解耦（§三）后这条成本理由**已不直接适用**，但它的两条翻转条件（自主模式跑一段确认位姿 ~20 Hz；存原始双目对做受控重放）仍是上 1080 前该做的验证，即上面第 4 步。

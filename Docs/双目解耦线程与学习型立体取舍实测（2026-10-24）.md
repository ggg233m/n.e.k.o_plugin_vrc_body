## 一 门槛修正：30 Hz 从来不是要求

> 🔴 **本节及全文所有 Hz 数字都带 15.625 ms 量化误差（2026-10-24 晚已确认并修正）**
> `hmd.jsonl` 的 gap_p50 在 **15 场录制里全部等于 62.000 ms**（= 4 × 15.625 ms 系统 tick），
> 一秒不差 ⇒ 真实位姿间隔落在 **47–78 ms** 之间都会报成 62 ms。
> **本文 §五 的归因（「位姿路径本身吃掉 ~60 ms」）是错的**：实际是 Windows 定时器的
> `Event.wait` 量化 + `time.monotonic` 的 16 ms 读数台阶。改用 `backend/pacing.py` 的
> Pacer/Gate 后真机是 **pose 20.00 Hz / stereo 10.00 Hz**（见文末「订正」）。
> ✅ 仍然成立的是：①门槛是 10 Hz 不是 30 Hz；②`stereo_ticks` 这类计数；③一切空间量。

部署代码 `nav_online.py` 的三个频率各管各的：

| 量 | 配置 | 实测（本文真机） |
|---|---|---|
| 位姿 | `pose_hz = 20` | **16.59 Hz**（gap p50 62 ms） |
| 双目 | `stereo_period_s = 0.1` ⇒ 10 Hz | **8.33 Hz**（`stereo_ticks = 2.02`） |
| 关键帧 | 非周期（位移/转角/时长三选一） | **0.33 Hz**（静止时） |

⇒ **立体深度喂的是建图（关键帧平均 1.86 Hz），不是逐帧控制。** 用 33.3 ms 淘汰模型的口径从根上就不对，之前几轮「学习型立体全部超标」的判定需要按 10 Hz 重读。

## 二 部署块实测（不是模型单独）

之前的计时都是「模型单独、输入已在显存」。把 `stereo_points` 后处理算进去才是感知线程真正付的钱（每组 200 次）：

| 分辨率 | 方案 | p50 | p90 | p99 | 占 10 Hz 预算 |
|---|---|---|---|---|---|
| 720×405 | SGBM CPU nd=64 | **21.2** | 24.4 | 28.8 | 21% |
| 720×405 | LAS2-M 编译 half+合批 | **51.0** | 60.8 | 84.4 | 51% |
| 1080×608 | SGBM CPU nd=96 | 64.6 | 73.2 | 87.3 | 65% |
| 1080×608 | LAS2-M 编译 half+合批 | **58.7** | 69.7 | 98.4 | 59% |

🔴 **1080 档出现交叉：SGBM 反而比 LAS2 慢。** SGBM 随像素线性增长，LAS2 是 launch-bound 几乎不涨（720→1080 像素 ×2.25，部署块延迟 51.0→58.7 ms 只 ×1.15；SGBM 21.2→64.6 ms 是 ×3.05，视差范围随 fx 一起涨）。

⚠️ **测量漂移**：720 档 LAS2 这里 51.0 ms，而模型单独测是 58.5 ms（加后处理反而更快，逻辑上不可能）⇒ 跨会话漂移约 **±10%**。**方向可靠，绝对值别用来卡边界。** 1080 档的 58.7 ms 是另一次实测。

## 三 解耦线程的实现

⚠️ **采集不能挪**：D3D11 立即上下文不是线程安全的，`OpenVRSensors` 的方法只能在感知线程里调。所以拆的是**重活**，不是采集。

| 部分 | 位置 | 理由 |
|---|---|---|
| `read_stereo` / `read_rgb` | 感知线程 | D3D11 上下文不可跨线程 |
| 视差 + 点云 + 近距判定 | **`_stereo_worker_loop`** | 这是 51 ms 的主体 |
| `KeyframePolicy.decide` | 感知线程 | 按 tick 算位移/转角/时长，必须在位姿时钟上 |
| ORB 特征 | `_stereo_worker_loop` | 只触发在关键帧上 |

交接是**纯快照 + 丢弃最新**：`queue.Queue(maxsize=1)` + `put_nowait` + `queue.Full: pass` ⇒ **位姿线程永远不会因为双目排队而阻塞**。`_commit_keyframe` 抽出成共享方法，内联与解耦两条路径行为逐位一致（不是复制粘贴两份）。

配置：`decoupled: bool = True`、`stereo_min_period_s: float = 0.02`。

## 四 解耦到底买到多少

### 4.1 仿真（注入假传感器，SGBM，20 s/臂）

| | 位姿 | 立体 |
|---|---|---|
| 内联 | 18.51 Hz | 8.49 Hz |
| 解耦 | 18.47 Hz | 7.82 Hz |

### 4.2 加重块（51.7 ms = SGBM 22.3 + burn 28.7）

|---|---|---|
| 内联 | ~~18.01 Hz~~ 作废 | ~~8.82 Hz~~ 作废 |
| 解耦 | ~~18.93 Hz~~ 作废 | ~~8.09 Hz~~ 作废 |

⇒ **位姿 +5%。** 🔴 **这是解耦的全部收益，远小于预期。**

## 五 为什么位姿只有 16.59 Hz（瓶颈不在双目）

内联时 tick 62 ms，把 51.7 ms 的双目块拿走后仍是 ~60 ms ⇒ **双目块大部分与 I/O 等待重叠，从来没真正阻塞过位姿**。

🔴 这条推翻了一个直觉上很合理、但没被验证过的假设。**下一步要 profile 的是位姿路径本身**（SteamVR `getDeviceToAbsoluteTrackingPose`、`DeadReckoner.update`、OSC 历史遍历），不是双目。

⚠️ **但注意 `stereo_ticks` 的因果链方向**：位姿慢 ⇒ 量化台阶 ⇒ 立体被压到 8.33 Hz。所以**修位姿是提升立体频率的唯一路径**，调 `stereo_period_s` 无用（这条与 `nav_online.py` 的 `RateMeter` 文档串一致）。

## 六 GIL 争用下的 LAS2（原标题「不可用于线程化管线」，已被订正 B 推翻）

> 🔴 **本节的数字是真的，结论和根因是错的（2026-10-24 深夜订正）**。
> 81.5× 的竞争者是「主线程不停跑纯 Python 循环」，真实管线里没有这种线程；
> 机制也不是 Dynamo guard 遍历调用栈，而是 **Windows 下 GIL 等待被 15.625 ms 定时器量化**。
> 见文末「订正 B」。

三组对照，同一台机器、同一时段：

| 竞争负载 | LAS2 块（编译版） | 相对空闲 |
|---|---|---|
| 空闲 | 49.3 ms | 1.00× |
| numpy 竞争 53 ms（**释放 GIL**） | 72.2 ms | 1.46× |
| python 竞争 53 ms（**持有 GIL**） | **4017.8 ms** | **81.50×** |
| python 竞争 26 ms（持有 GIL） | 3686.7 ms | 74.79× |

同一个负载下，**SGBM 只慢 1.60×**（19.1 → 30.5 ms）。

根因：`torch.compile` 的 Dynamo guard 每帧要走一次 **Python 调用栈遍历**；纯 Python 循环把它拖垮。**eager 版只慢约 2.3×**（同条件下 p50 111.8 ms），差别全在 wrapper。⇒ 这是 `torch.compile` 的固有开销，与模型本身无关。

🔴 **推论：LAS2 越快（GPU 上耗时越短），Python guard 的固定开销占比越高，而且负载越轻相对惩罚越大（26 ms 时 74.8×）。在真实管线里无法通过「少给这个线程活」来回避。**

## 订正 A（2026-10-24 深夜）：§4/§5 被 Windows 定时器推翻

本文写作时（下午）测的 18 Hz 不可复现。**同日晚上的调查发现根因是测量工具**：`Event.wait` + `time.monotonic` 在 Windows 上分辨率不够。

### A.1 被推翻的陈述

| 原文 | 实况 |
|---|---|
| 「解耦收益 +5%（内联 18.01 → 解耦 18.93 Hz）」 | **不可复现。** `Event.wait` + `time.monotonic` 的组合下，无论 body 耗时取 0.3–47 ms，实测 gap 恒为 **62 ms（≈16.1 Hz）**；18–19 Hz 只能在外部进程调过 `timeBeginPeriod(1)` 时出现，是环境噪声不是代码行为 |
| 「内联把位姿压到约 11 Hz」 | 同样是量化伪影，实测推翻 |

### 真正的根因

两个独立的 Windows 机制叠加：

1. **`threading.Event.wait` 向上取整到 15.625 ms 系统 tick** —— 请求 49.7 ms 实测 **62.26 ms**；
2. **`time.monotonic` 本身是 `GetTickCount64()`** —— 读数台阶 **16.000 ms**，**纯忙等也对不准 50 ms**（自旋误差 p50 6.0 ms）。

⇒ 只换等待原语**没用**，必须同时换时钟。这条是本文最该记住的教训：**先确认测量工具的分辨率，再相信它给出的差异。**

### 修完之后的实测

`backend/pacing.py`（Pacer：perf_counter + sleep + 1.5 ms 自旋；Gate：绝对累加）接进感知/控制循环后，真机 SteamVR 30 s：

```
pose_hz      20.00   (目标 20.0)   gap p50 0.050 s
stereo_hz     9.96   (目标 10.0)   gap p50 0.100 s
errors       []
```

回归护栏：`tests/test_pacing_regression.py`（读真实 gap；已验证故意把频率减半会红）。
完整根因与双时钟契约见 `FACTS.md` 的「感知循环 16.1 Hz 的根因」与「双时钟契约」两行。

### 仍然成立的

§三（解耦的实现，采集不能挪）、§八（LAS2 家族与跨系列裁定）、§九（精度）**不受影响**：那些测的是 `perf_counter` 域下的耗时和真值误差，与本次时钟问题无关。

## 订正 B（2026-10-24 深夜）：§六 的 GIL 问题根因推翻 + 双 venv 割裂已解决

§六 测出的 81.5× 是真实数字，但**成因和结论都被推翻**。

### B.1 被推翻的陈述

| 原文（§六）| 2026-10-24 深夜实况 |
|---|---|
| 「有别的 Python 线程持 GIL 时慢 81.5×」 | ⚠️ **「持 GIL」不够具体**：81.5× 的竞争者是「主线程**不停**跑纯 Python 循环」（`.tmp/block_contention.py` 的 `work_python`）。真实管线里**没有这种线程**：位姿/控制都是 Pacer（休眠 + 1.5 ms 自旋）；建图/回环线程空闲时休眠 |
| 「Dynamo guard 每帧走 Python 调用栈遍历」 | ⚠️ **这个机制是对的**，但不是 81.5× 的成因；eager 版也有 guard（只是不编译），它的慢化只 **2.3×**（.tmp/gil_test.log：编译 101.7 ms vs eager 209.9 ms） |
| **「不能进这条管线」** | **推翻。** 真实架构（位姿 20 Hz + 控制 10 Hz，双目独立线程）下 LAS2 只慢 **1.5%**（`.tmp/retest_gil_py311.log` A→C：52.3 → 53.1 ms）；SGBM 只 +1.4%（21.9 → 22.2 ms）|

### B.2 真正的根因：Windows 下 GIL 等待被 15.625 ms 定时器量化

`.tmp/convoy_probe3.py` 确认了 **「1 ms 断崖」假设**：CPython 在 Windows 上用 `WaitForSingleObjectEx` 实现 GIL 的条件变量；`switchinterval` < 1 ms 被**向下截断成 0**（立即超时、立即让出），≥ 1 ms 被**系统定时器向上取整到 15.625 ms 的倍数**。证据：

| switchinterval | LAS2 p50（Py3.14） | 相对空闲 | 说明 |
|---|---|---|---|
| 空闲 | 50.9 ms | 1.00× | 基线 |
| 0.2 ms | 73.3 ms | **1.44×** | 正常 |
| **0.9 ms** | 73.9 ms | **1.45×** | 正常 |
| **1.0 ms** | **11277.0 ms** | **221.41×** | 灾难 ← 断崖 |
| 5.0 ms | 11226.8 ms | 220.42× | 灾难 |
| +tBP(1) 5.0 ms | 3681.4 ms | 72.28× | 仍很慢（定时器 1 ms 但窗口变小） |
| +tBP(1) 1.0 ms | 754.1 ms | **14.80×** | 大幅改善 |

⇒ **0.9 ms 与 0.2 ms 都正常，1.0 ms 变成 220× 灾难**。`.venv` 默认 `switchinterval = 0.005` 正好在灾难区；Pacer 的 1.5 ms 自旋**低于 GIL 请求的延迟阈值**，触发立即让出路径，所以管线里慢化只 1.5%。

### B.3 Py3.14 vs Py3.11 对比（GIL）

| Py 版本 | LAS2 空闲 | LAS2 + Pacer(20+10) | 相对空闲 | SGBM 空闲 | SGBM + Pacer |
|---|---|---|---|---|---|
| 3.11.9 | 52.3 ms | 53.1 ms | +1.5% | 21.9 ms | 22.2 ms |
| 3.14.9 | 69.3 ms | 70.4 ms | +1.6% | 23.2 ms | 23.5 ms |

⇒ **两版的 GIL 争用行为一致**（都是 1.5–1.6%）；Py3.14 的 LAS2 比 Py3.11 慢 **+33%**（69.3 vs 52.3 ms），SGBM 只 **+6%**（23.2 vs 21.9 ms）。**原因待同场 A/B**：可能是 JIT / GC / 内存分配器的版本差异，与 GIL 无关。

### B.4 双 venv 割裂已解决

新建 `.venv_las`（CPython **3.14.9**），torch 2.14.1+xpu + openvr 1.26.701 + opencv-contrib 4.14.0.94 + scipy 1.18.1 **同进程 import 通过**，backend 模块可导入。`.tmp/retest_gil_py314.log` 证明可跑 LAS2 编译版（真实镜像双目还没测）。

**pip 环境要求**：全局 index 必须是能找到普通包的镜像（如阿里云），torch 必须加 `--index-url https://download.pytorch.org/whl/xpu`；`.tmp/_tc_run314.bat` 走这个 venv（Git Bash 里 `cmd //c` 给 bat **绝对路径**，否则找不到）。

⚠️ **free-threaded（cp314t）走不通**：opencv 只有 abi3 wheel，不适配 free-threaded。

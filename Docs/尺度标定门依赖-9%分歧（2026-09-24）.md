# 尺度标定：口径无影响，但一致性门带来 9% 分歧（2026-09-24）

**触发**：上一轮我判断「`scale_calib.json` 用了 `osc_policy="stop"`，所以 `cam_h=1.3056 m` 建立在少算 37% 的路程上」。本轮实读代码 + 实跑，**该判断错误，予以撤回**；但顺带查出两个真问题。

---

## 一、撤回：`osc_policy` 对 cam_h 无影响

### 代码依据

`scale_calib.py`：

```python
_build_dr()  ->  dead_reckon(run_dir, dt=0.05, yaw_sign=...)     # L82
                dead_reckon 内部用 osc.dist(..., policy=默认 "zoh")  # recorder/pose_graph.py L115
trans = fr["dist_zoh_m"] if p["osc_policy"] == "zoh" else fr["dist_stop_m"]   # L184
```

即：**驱动几何的航位位置 `C_i / C_j` 一直由 zoh 建立**，与 `osc_policy` 无关。
`osc_policy` 只影响两处：L185 的 `min_trans_m` 门槛、L252 的 `trans` 分箱统计。
而且 L181 先按 `max_gap_s=0.30` 把含大空档的帧对整个丢掉（`osc_hole=9713`），所以口径差异的可用区间本就很窄。

### 实测（`.tmp/scale_calib_{stop,zoh}.json`）

| policy | cam_h | IQR | n_valid | lowtrans | weak |
|---|---|---|---|---|---|
| stop | **1.3056** | 0.2731 | 1156 | 5675 | 3141 |
| zoh | **1.3049** | 0.2715 | 1218 | 5305 | 3449 |

**差 0.0007 m（0.05%）。** zoh 多收 62 对（`lowtrans` 少 370），中位尺度不动（0.86992 vs 0.87041）。

**结论**：`scale_calib.json` 里的 `osc_policy: "stop"` 是**标签错，不是数值错**。
`.tmp/_scale_calib_{stop,zoh}.json` 在 2026-09-21 22:08 就已存在 —— 上一轮已跑过该对比，只是没写进文档。

## 二、真问题 1：一致性门带来 **9% 尺度分歧**（`.tmp/scale_calib_gate_sweep.json`）

`max_resid_per_trans` 是「深度重投影位移」与「OSC 航位位移」的一致性门，默认 **0.5（允许差 50%）**。扫描它：

| `max_resid_per_trans` | cam_h | IQR | n_valid | n_trimmed |
|---|---|---|---|---|
| **0.50（当前默认）** | **1.3049** | 0.2715 | 1218 | 1218 |
| 0.30 | 1.3710 | 0.1747 | 805 | 805 |
| 0.20 | 1.4036 | 0.1318 | 545 | 542 |
| **0.15** | **1.4245** | **0.1014** | 376 | 373 |
| 0.10 | 1.4436 | 0.0820 | 179 | 179 |

- **cam_h 单调上升 1.3049 → 1.4436（+10.6%）**：松门放进来大量「两链位移相差最多 50%」的帧对，它们把 cam_h **拉低**。
- **IQR 同步收窄 0.2715 → 0.0820**（好 3.3 倍）⇒ 紧门下的估计**条件数更好**，不是过拟合。
- 紧门（0.15）逐窗稳定性：`1.4348 / 1.4251 / 1.3778 / 1.4019`，窗间差 ~4%。
- **`n_trimmed == n_valid` 在每一档都成立** ⇒ L275 的 3×IQR 裁剪**从未生效**，离群处理形同虚设。

**含义**：深度链（DA-V2 + 地板先验）与 OSC 链（路程积分）在尺度上**差 5–13%**，而 pipeline 静默采用了偏低的松门值。

**现成的独立锚点**：`run.json` 的 `hmd_height: 1.5`，`hmd_frames.jsonl` 里 HMD 位置恒为 `[0, 1.5, 0]` —— 头显被我们**注入在 1.5 m**。若相机在头部，则 cam_h ≈ 1.5 m，紧门值（1.4245）比松门值（1.3049）近得多。**但这条依赖「相机在头部」的假设，不足以定案。**

**未定案的部分（诚实声明）**：谁是准的（OSC 路程 vs 深度几何）需要一个**独立几何锚点**才能判。`s = |DR 位移| / |深度位移|` 的两个分量各有一份不确定度，本实验只能量出「它们差多少」，量不出「谁对」。

## 三、真问题 2：波及面与两处脆弱点

### 3.1 路线几何**不受** cam_h 影响（好消息）

`cam_h` 出现次数：

| 模块 | cam_h 出现 |
|---|---|
| `pose_graph.py`（2D 米制位姿图） | **0** |
| `nav_map.py`（导航图 21 节点/20 边） | **0** |
| `build_topo_map.py` / `place_group.py` / `loop_verify.py` / `world_model_build.py` | **0** |

⇒ **路线图的米制纯粹来自 OSC+HMD**（`osc_route_sum_zoh_m = 65.411`），与 cam_h 无关。
⇒ 那 9% 分歧影响的是**深度派生层相对路线图的配准**，不是路线几何本身。

### 3.2 受 cam_h 影响的层（∝ cam_h 严格线性）

| 模块 | 位置 | 作用 |
|---|---|---|
| `stage3_horizon.py` | L55 `k = a*cam_h*fy` | 地板/地平线归一 |
| `pointcloud_build.py` | L289-323 取值链 | 点云整体尺度 |
| `obstacle_map_2d.py` | L63/L101 | 2.5D 障碍层高度 |
| `local_avoid.py` | L250/L257/L349 | 三态避障 |
| `backend/realtime_depth.py` | L85-108 | 在线深度 |

### 3.3 两处脆弱点

1. **`obstacle_map_2d.py:36` 硬编码默认值**
   ```python
   return float(scale["k"]), float(intrinsics.get("cam_height_m", 1.3056))
   ```
   `intrinsics` 缺 `cam_height_m` 时**静默退回 1.3056**。重标定后障碍层会继续用旧值，且不报错。

2. **`map_from_capture.py:199` 把口径烤进文件名**
   ```python
   bundled_calib = REPO_ROOT / ".tmp" / "_scale_calib_stop.json"
   ```
   `pointcloud_report.json` 的 `cam_height_source` 就是 `cam_height_from:_scale_calib_stop.json`。
   文件名带 `stop` 会误导后人以为尺度解算用了 stop 口径（实际没有）。

## 四、建议

1. **口径标签改正**（低风险、消除误导）：`scale_calib` 的 `osc_policy` 默认改 `"zoh"`，bundled 文件重命名去掉 `stop`；并在 JSON 里显式记录「几何航位固定用 zoh，本参数只进门槛/分箱」。
2. **一致性门收紧**：`max_resid_per_trans` 从 `0.5` 收到 `0.15`（IQR 0.27→0.10），或改成「门扫描 + 取 IQR 最小且 n≥300 的工作点」。
3. **`obstacle_map_2d.py:36` 去掉硬编码**：缺失 `cam_height_m` 应报错，不得静默用 1.3056。
4. **先定案再改数**：cam_h 1.3056 → 1.4245 会整体缩放深度层 ~9%。**在拿到独立几何锚点之前，不建议直接改** —— 否则只是把一个未验证的数换成另一个未验证的数。
5. **独立锚点怎么做**：一次受控录制里，让 avatar 沿**已知长度**的路径走（例如地面上两个已知间距的标记，或已知尺寸的参照物），一次性给出与 OSC/深度都独立的米制参照。

## 六、本轮已实施的改动（选项 a：只改标签/门/硬编码，**不动数值**）

### 6.2 `obstacle_map_2d.py`（`recorder/`，离线侧）

```python
# 旧：缺键静默回退到历史值
return float(scale["k"]), float(intrinsics.get("cam_height_m", 1.3056))
```

**已验证**：真实 run 上仍返回 `1.305609568664099`（逐位一致）—— 该 run 的

去掉它今天不改变任何数值，只防止将来重标定后静默沿用旧值。

### 6.3 `map_from_capture.py`

| 项 | 改动 |
|---|---|
| bundled 文件名 | `_scale_calib_stop.json` → **`_scale_calib_bundled.json`**（口径中性；旧文件保留做兜底） |
| 新增 `_scale_calib_defaults()` | 从 `scale_calib.py` 读当前默认（单一真值源），读不到返回 `None`，**不猜** |
| 新增 `_apply_scale_calibration()` | 把尺度读取逻辑抽出成**可测函数**；当复用的历史报告的一致性门 ≠ 当前默认时，写入 `scale_calibration.gate_mismatch` 并追加进 `degraded_reasons` |

**「不动数值」是怎么保证的**：`map_from_capture` 优先用 run 内已有的
`scale_calib.json`（gate 0.5 → cam_h 1.3056），所以 shipped 数值不变；
但那个落差现在会**显式记录**，不再静默。

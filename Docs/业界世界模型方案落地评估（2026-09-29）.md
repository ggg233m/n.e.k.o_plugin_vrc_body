## 结论先行

1. **问法本身要先拆开。** 业界"世界模型"是三个不同的东西，只有第三个是你的对应物：
   - **A 生成式/预测式**（Cosmos、Genie、Marble、GAIA、Dreamer）——回答"接下来会看到什么"。**不做**，理由不是算力而是方向错：你需要"现在什么是真的"，用生成模型承载空间事实等于亲手制造硬约束禁止的幻觉。
   - **B 前馈几何**（VGGT、DUSt3R/MASt3R、CUT3R、MapAnything）——回答"现在的 3D 形状是什么"。**太重且尺度不可信**，线上不做。
   - **C 持久空间记忆**（拓扑地点图、VPR、场景图）——回答"我去过哪、什么在哪"。**这才是你缺的，而且你的设计方向本来就是对。**

2. ~~四条独立推理线收敛到"搞清镜像纹理几何"这一个实验~~ —— **已解决（2026-09-29）**：eye 渲染视口是**整张纹理经 mip 整数降采样**得到的（无裁剪、无非等比缩放）⇒ `getProjectionRaw` 的半角正切覆盖整张纹理 ⇒ 镜像路径 `fx@720 = 202.5` 正确。见第一节。

3. ~~已定位一处 1.428× 内参矛盾，且已渗进米制结果~~ —— **已撤回**。那是我把 **OBS 视频路径**（960×540，fx=257.07@640）与 **SteamVR 镜像路径**（720×405，fx=202.5@720）当成了同一条数据。两条路径本来就是两个 FOV，各自都对。详见第一节。

4. **业界能同时过「许可证干净 + 无需 CUDA + 有 OpenVINO/ONNX 路径」三关的候选非常窄**：XFeat / ALIKED+LightGlue / AnyLoc / Depth-Anything-V2-Small。三条筛选线指向同一批东西，见第三节。

5. ~~一条架构级线索待验证~~ —— **已实测证伪（2026-09-30 03:20，上机）**：`/usercamera/*` 子树存在且可读写，但 `/usercamera/Pose` 例外（`access=1`、恒返回全零、写入被忽略、从不推送）⇒ **OSC 拿不到世界坐标**。详见 §4.1 与 `Docs/自动到达能力差距清单.md` §零。**"OSC 只回传速度、没有位置"这条最硬的假设不移除。**

6. **命名风险，改文档前先处理**：`world model` 在本仓库**已经有两个含义**（W1 世界身份 / 建图产物），再叠业界含义这个词就废了。Bucket C 一律叫**「地点记忆」**。

## 1. ~~最高优先级：1.428× 内参矛盾~~ —— **已撤回（2026-09-29 二次补记）**

**本条原判断错误，撤回。** 我把**两条不同的采集路径**当成了同一条数据的"录制 vs 评估"。

### 事实：两个焦距属于两个路径，各自都对

| 路径 | 数据 | 内参 | 依据 |
|---|---|---|---|
| **OBS 视频**（桌面/窗口视图） | `offline_probe/recorder/runs/20260920-233456`（TUM，`mono_tum`，960×540） | **fx=257.07@640（102.45°）** | `estimate_video_offset.py:33,186`（`W,H = 960,540`、`--fx 385.6`）；`SLAM米制复测报告:262` |
| **SteamVR 镜像**（每眼渲染视口） | `.slam_probe/stereo_seq/run4…run7`（EuRoC，720×405） | **fx=202.5@720（121.3°）** | `record_stereo_euroc.py:23,27`；run5 `meta.json` |

⇒ 那次 `fx257` / `fx320` A/B 跑的是 **OBS 路径**，102.45° 在那里**胜出是对的**（fx320 轨迹 **0 字节**）。
镜像路径的 202.5 也没错。**两条路径本来就是两个不同 FOV，不存在 1.428× 矛盾。**

### 为什么 202.5 对镜像是对的（2026-09-29 用户澄清）

**eye 渲染视口是整张纹理经 mip 降采样得到的**——`_mip_for()` 从 2880×1620 沿 mip 链整数折半到
720×405，**无裁剪、无非等比缩放**（`record_stereo_euroc.py:30-33` 专门选 720×405 就是为了正好落在 mip 上，
省掉 CPU 那次 1.125:1 非整数缩放）。mip 降采样**不改变视场**，只改变分辨率
⇒ `getProjectionRaw` 的半角正切**覆盖整张纹理** ⇒ 任意 mip 下 `fx = W/(r−l)` 都成立
⇒ **fx@720 = 810/4 = 202.5 正确。**

支持性算术：镜像 `2880/1620 = 1.7778`；`getProjectionRaw` `tan_h/tan_v = 1.7778/1.0 = 1.7778`。
对称针孔视锥的 `tan_h/tan_v` 恰等于纹理宽高比 ⇒ 与"整张纹理即视口"一致。

**⇒ `GetRecommendedRenderTargetSize` 不再是阻塞项**，最后一个"未验证前提"由用户澄清消解。

### 真正剩下的问题（更小，但确实存在）

`config.CAMERA_HORIZONTAL_FOV_DEG = 102.45` 是 **OBS/桌面窗口路径**的标定值，却被**在线**的
`local_perception`（检测器方位角）与 `traversability`（扇区）消费
（`config.py:22,253,628-633` → `local_perception.py:34-36,405,1558`、`traversability.py:30-32,368,546`）。

| 状态 | 在线采集源 | 正确的 FOV |
|---|---|---|
| **现在**（发行配置 `source/capture = "wgc"`，`plugin.toml:212-213`） | WGC 窗口捕获（桌面窗口视图，与 OBS 同类渲染） | 102.45° **可能正确** |
| **移除 WGC 之后** | SteamVR 镜像（每眼视口） | **必须变成 121.3°** |

⇒ **不是现在的 bug，是一次由"移除 WGC"触发的耦合。** WGC 一走、直播画面换成镜像，
这个常数若不动，检测器方位与可通行扇区就会被压缩（线性映射下约 1.18×）。

**修法不是改数值，而是让它跟着采集源走**：`service.py:313` 已把
`horizontal_fov_deg=self.config.vision.horizontal_fov_deg` 向下传，改成**由当前采集源推导**
（镜像：`getProjectionRaw`；WGC：保留标定常数）。`nav_online.py:280` 已经在这么做。

### 附带发现：方位角用的是线性映射，不是 `atan`（独立缺陷）

`local_perception.py:1558`：`bearing = (center_x - 0.5) * self._horizontal_fov_deg`
（`traversability.py:368,546` 同形）。线性映射只在画面边缘与真值重合，帧内误差随视场变宽急剧增大：

| 视场 | x=0.75 处线性 | 针孔真值 `atan((2x−1)·tan(fov/2))` | 相对误差 |
|---|---|---|---|
| 102.45° | 25.6° | 31.9° | ~25% |
| 121.3° | 30.3° | 41.6° | ~37% |

`bearing_deg` 进 `world_salience.bearing_sector` 的八分方位量化、进导航器接近判据。
**这条与 FOV 取值无关，是独立的第二个问题。**

### 我这次错在哪（记录）

`record_stereo_euroc.py`（镜像，fx=202.5@720）与 `SLAM米制复测报告`（OBS run 233456，fx=257.07@640）
被我放进同一个表里当成"同一条数据的录制与评估"。二者其实是**两个目录、两种布局**
（`stereo_seq/run*/mav0` 对 `offline_probe/recorder/runs/233456`）、**两个分辨率**。

> 这是本轮**第二次**由本仓库既有事实纠正我的外部推论（第一次是 §4.2 的 playspace 假设）。
> 教训：涉及本仓库的数字，先查仓库再下结论。

## 3. 许可证 × 硬件联合筛选（等级 B/C 混合，逐行标注）

**能力筛选与许可证筛选收敛到同一批东西。**

| 候选 | 许可证 | 上 Arc 的现实性 | 裁定 |
|---|---|---|---|
| **XFeat** | **Apache-2.0**（C） | ONNX/C++ 移植存在，VGA CPU 实时 | ✅ 主选 |
| **ALIKED + LightGlue** | **Apache-2.0**（C） | **Intel 官方 OpenVINO 教程**（SuperPoint / LightGlue 两篇） | ✅ 主选 |
| **AnyLoc** | **BSD-3**（C） | DINOv2 需自行转 ONNX | ✅ 主选 |
| Depth Anything V2 **Small** | Apache-2.0（**Base/Large/Giant 据称为 CC-BY-NC**，C） | Intel 官方 OpenVINO + Embodied SDK 教程 | ✅ 已在用；**不能免费升 Large** |
| SuperPoint 权重 | ⚠️ 受限（MagicLeap 那套，C） | Intel 教程用的就是它 | ⚠️ 集成前必查 |
| DUSt3R / MASt3R / MonST3R | **CC BY-NC-SA**（B） | CUDA | ❌ |
| VGGT / VGGT-Ω | **非商用**（B） | 1.2B、单帧 7–8GB | ❌ |
| Fast-FoundationStereo | **NVIDIA Source Code License**（A，读 model_card） | TensorRT 导向、NVIDIA 优化 | ❌ |
| FoundationStereo | 同上（NVIDIA） | 秒级，超预算 | ❌ |
| DA3-SMALL / DA3Metric-Large | **元数据冲突（apache-2.0 vs CC BY-NC）**（C） | 有 ONNX | ⚠️ 待核 |
| MoGe-2 / MoGe-3 | 待核 | **官方 ONNX 导出**（opset≥14），ViT-S 可评估 5–15Hz | ⚠️ 候选 |

### 唯一推荐落地的改动

**把 `backend/nav_loop.py` 的 `cv2.ORB_create`（`:209`）+ `BFMatcher`（`:98`）换成 XFeat（或 ALIKED+LightGlue），并在 `_candidates()`（`:278`）前加一层学习型全局描述子做跨会话检索。**

四个条件同时成立：① 业界有成熟开源件；② 有明确失败样例（run7：0 接受 / 11 拒绝）；③ 有 Intel 官方 OpenVINO 路径，无需 CUDA、无需 torch；④ **不动架构**。

**根因不在"ORB 不够强"，而在 `_candidates()` 只按会话内路径距离（`c.min_path_m`）取候选 ⇒ 线上链路不存在全局地点检索入口。** 这正面回应 `Docs/世界模型导航方案-可行性评估.md` §17.8 那句"跨世界泛化才是下一个真正需要通用词表的理由"。

**下游不要动**：`nav_loop.py:305` 的"HMD 朝向不漂 ⇒ PnP 相对转角必须与它一致"比业界通用外点过滤更强（你有外部朝向真值）。业界补的是**上游**。

## 5. 明确不做

## 6. 便宜且值得记的清单

- **"Limbo" = 动漫微调的 Depth Anything 3 small**（TheAnimeScripter 的 commit）。VRChat 世界大量是二次元/toon，**域内微调可能胜过通用 SOTA**。同一项目在 Windows 上并用 DirectML 与 OpenVINO，**两边都撞上 grid_sample 问题**（手工拆解 grid_sample）——对你参考价值最高的域内经验。
- **DirectML 是没试过的第三条路**（`gpu_bench_result.json` 自记"无 DirectML EP"），专治 OpenVINO 处理不好的算子。
- **`benchmark_app -pc` 逐层性能计数**：信任任何 OV-GPU 结果前，先证明没有算子悄悄回退 CPU。"能跑" ≠ "被加速"，与你那次 INT8 惊讶是同一失效形态。
- **`gpu_bench_result.json` 必须开着 VRChat 重测**——仓库里**所有延迟结论都建立在这个未验证条件上**（该 JSON 自己就写了这句）。
- **FP16 口径**：OpenVINO GPU 对 FP32 权重模型**默认以 FP16 执行**。你那些 14–43ms 是 FP16 运行域的数字（JSON 里的 `output dtype float32` 是输出张量类型，不是内部计算精度）。**FP16 vs FP32 对米制尺度精度的影响尚未测过**——而那恰恰是你在意的。
- **DA V2-small 实测锚点（本机，未开 VRChat）**：252×448 **14.1ms** / 378×672 **22.8ms** / 518×518 **26.2ms** / 518×910 **43.5ms**；OV-CPU 150.9ms、ORT-CPU 414.7ms。
- **OSNet 正面线索**：ACM MM 2020（DOI 10.1145/3394171.3413815）——**随机 3D 角色作为 ReID 源数据，泛化优于真实世界数据**。对着渲染 avatar 微调 OSNet 有依据。
- **UI 遮罩**：2D UI 叠加层在任何 benchmark 里**零覆盖**，应**检测并遮罩**而非指望模型忽略。直接对应"一帧 7 个实体里 5 个是 avatar 菜单缩略图"。
- **语义地标通道的替代**：`Docs/世界模型导航方案-可行性评估.md` §21.3 自己留了豁免条件（"换 token 来源…更大或学习型编码器"）。业界答案是 **LM-Nav 范式**（LLM 解析出地标 → 特征把地标落到拓扑节点 → 图搜索）+ **AnyLoc 作节点身份**。合理解释是：**风格化先杀语义判别力、后杀几何/外观结构**——这正好解释网格 token 为何得零。**OpenVINO 有官方 CLIP / SigLIP notebook 可用。**
- **竞争情报**：精确组合**没有论文做过**（VRChat 内无世界坐标的具身导航未发表），但 novelty 威胁来自**开源项目**——`gamio-22/vrchat-ai-agent`、`HoppouAI/ProjectGabriel-Remastered`、`Pomelo32141/VRchat_api_agent`、`MLShukai/vrcpilot`。可辩护的是**约束集合**，不是"LLM 导航元宇宙"。
- **"查无此证据"本身是结论**：未找到任何 OpenVINO/Arc 上的世界模型导航工作；未找到生成式世界模型用于 VRChat/社交 VR 的工作；已有 LLM VR agent 都走符号/图/拓扑记忆，**不走预测式世界模型**。

## ② 视觉前端：内参接标定值 + 裁剪折算 + 实测帧率

**问题一：焦距假设错了 24.5%。**
`SlamConfig.horizontal_fov_deg` 默认 90° ⇒ `fx@640 = 320 px`。而正交性自标定给出的
是 `f@960×540 = 385.61 px`（良态帧对中位数，20 对，标准差 1.76 px），折算
`fx@640 = 257.07 px`，对应水平视场 **102.45°**。焦距高估 24.5% 会直接进 PnP 和
`Δu ≈ fx·tan(Δyaw)`，是"转头飘"的系统性来源之一。

⚠️ **`.tmp/_manual_run/fov_calibration2.json` 的顶层值不可用**：`fx_960=266.14`
（121.99°）是把 20 个解算失败样本一起聚合的结果——那些样本焦距全部撞到下界 152，
且无一例外都是 `|dyaw| ≥ 16.7°` 的帧对。良态帧对（defect < 0.05，`|dyaw| ≤ 14.8°`）
的中位数才是 385.61。

**问题二：中心裁剪改变了等效焦距，而内参不跟着变。**
`FrameGeometryNormalizer` 中心裁剪只切边缘、不改变每像素角度；缩放到同一目标宽度后
等效焦距要按 `source_width / crop_width` 放大。窗口比目标更宽时，不折算就会把内参算小。

**问题三：5 Hz 是写死的，不是实测的。**
`time_s = frame_idx / 5.0` 与导出 `frame_rate=5.0` 都假设 5 Hz。实际被处理帧的间隔经常
超过 0.8 秒（SLAM 慢于采集），导出的时间轴是假的，下游与 OSC 对齐会全错。

改动：

| 文件 | 改动 |
| --- | --- |
| `config.py` | `relocalization_horizontal_fov_deg` 默认 90 → 102.45（含来源与不可用值说明），解析 fallback 同步 |
| `.slam_probe/slam_core.py` | `SlamConfig.horizontal_fov_deg` 默认同步；新增 `set_intrinsics(K)` |
| `backend/frame_geometry.py` | `FrameGeometry` 增加 `crop_width/crop_height`、`focal_compensation`、`effective_fx(base)` |
| `backend/live_mapping.py` | 按实际几何折算内参（焦距变了就断段）、实测帧率 + `frame_rate_source`、snapshot 暴露 `intrinsics` |

## ③ 尺度校准：断档阈值与上游不同口径

`MetricScaleCalibrator(max_gap_s=0.5)` 与 `LiveMappingSession(max_timestamp_gap_s=2.5)`
不是同一个口径。实测帧间隔常 > 0.8 秒 ⇒ **每一帧**都被判成断档并清空样本 ⇒
`samples` 永远是 0，尺度永远不可辨识。

改动：默认 `max_gap_s` 改 2.5，并由 `service` 显式取 `live_mapping.max_timestamp_gap_s`
（单一真值源）；速度新鲜阈值参数化为 `max_velocity_age_s`；新增 `reject_counts` 与
`sample_dt_max_s`，下次在线跑能直接看出卡在哪个门，不用猜。

## ⑤ 重定位：禁止跨段确认与检索

每个 segment 在 SLAM 重新初始化后都从原点重新开始，是**另一套坐标系**。此前候选检索
是全地图混合检索（`_bank_des`），跨段匹配等于把两个坐标系强行对齐。

改动（`.slam_probe/relocalization.py`）：
- 解析每个关键帧的 `segment_id`（缺失为 0），检索库带段标记；
- 首次确认定位后锁定段，后续检索只在同段内做；
- 未确认阶段，跨段候选不互相累加确认（原来两段各一票就能凑够 confirmations）；
- `reset()` 解锁，`mark_lost()` 保留锁（看不见不等于坐标系变了）；
- 结果带 `segment_id`，新增 `locked_segment` 属性。

## ④ 导航图绑定在线视觉地图身份

在线建图期 `service._on_live_mapping_updated` 会把 `visual` 整个清空，于是导航图的
`meta.visual_map_revision` 恒为 None，而 `nav_target.binding_error` 要求它等于
`visual.revision` ⇒ 恒报 `navigation_map_frame_mismatch`。

改动：`LiveMappingSession` 提供 `visual_map_revision`——保存完成后与重定位观察器同口径
（文件 sha256），未保存时给稳定的 `live_building:<path>` 前缀（流式检查点不改写它，避免
导航图 revision 每 2 秒抖一次）。建图期传给导航图的是 `{loaded: False, revision: ...}`：
不冒充已加载的地图，但让导航图知道自己绑的是哪张图。

### 消费循环为什么只有 1 Hz

`VisionWorker._process_loop` 有一条捷径：`relocalization_provider` 返回
`state == "mapping"` 时置 `mapping_priority`，只 `cache_frame_only` 再 `continue`，
**跳过光流 / 深度 / 目标检测**。作者注释（`backend/vision.py:2549-2551`）写明：
"目标检测、深度和光流会把消费者拖到 1–2 Hz"。

而现在 `mapping.mode = "idle"`、`tracking_state = "stopped"` ⇒ `state != "mapping"`
⇒ **捷径不走**，每帧都跑全量感知重路径，于是回到注释说的那 1–2 Hz。

这也解释了第一轮那个 `capture.frame_rate = 5.593`：它是**建图期**的速率（捷径生效），
和现在的 0.97 Hz 并不矛盾，只是属于不同阶段。

### 建图为什么停了

`/worldmodel/mapping`：`reason = "mapping_stopped"`、`mode = "idle"`、
`last_reset_reason = "timestamp_gap_reset"`、`last_result.state = "LOST"`。

`"mapping_stopped"` 只在 `LiveMappingSession.stop()`（`live_mapping.py:281-289`）产生，
而 `stop()` 只被 `service.mapping_stop()`（`service.py:866`）调用 ⇒
**是一个 stop 动作结束了建图，不是崩溃**。停之前先吃过一次 >2.5 s 的断档
（`mark_tracking_gap` → LOST），旧地图保留。

`stats`（自上次 reset 起）：`frames=141`、`tracks_ok=33`、`tracks_lost=1`、
`keyframes=3`、`init_frames=43`、`reloc_rejected_weak=53`、`jumps_rejected=2`、
`points_moved_by_optimization=2874`。

⚠️ **141 帧里 43 帧花在建图初始化上（30%）**：在 1 Hz 输入下，初始化就要 43 秒，
`max_jump_rotation_deg=35°` 在 1 s 间隔下极易越界（`jumps_rejected=2`）。
推进顺序上，"先把消费帧率提上去"优于"继续调 SLAM 参数"。

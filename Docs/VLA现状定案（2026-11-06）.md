## 二、已定案的技术结论（无冲突）

1. **`wp` 是标签泄漏，不是导航输入。** 旧 `waypoint_body()` 沿录制轨迹取未来点：near 模式
   `horizon_s = K_STEPS × STEP_S = 1.2 s`，与动作块严格等长；far 模式前取 4 m。
   改用「只用过去轨迹外推」的因果 wp 后，跨会话 5 折 44 维二次特征
   **2.2066 → 3.2270（+46.2%，5/5 折一致变差）**，`body` 单用为 3.2744 ⇒
   旧 wp 贡献的约 0.87 MSE 全部来自未来信息。因果 wp 本身无信息（3.2738 vs 3.2744），
   但方向与未来 1 s 真实位移 `cos p50 = 0.986`、一步外推重建误差 p50 0.444 m ⇒
   **在线要拿回 wp 的价值，唯一合法路径是规划器当场给出的 A* 路径点（软先验），不是录制轨迹的未来段**。
   ⚠️ 边界：near 下 `|wp| p50 = 0.37 m`（不是 3.5 m），仅用 wp 两维线性预测残差占真实位移 **672%**；
   far 模式 `|wp|` 中位 3.532 m，但 near LWO 0.9429 vs far 1.0106 **只差 7%** ⇒ **far 也没去掉方向那一半，不能当「已修复」**。
   出处：`wp泄漏-推翻性发现-2026-11-04` §1、`VRChat具身agent训练方案v4` §0/§1、
   `.venv_xpu/runs/causal_wp/causal_wp.json`。

2. **视觉是真信号，跨会话增益约 26.6%，但当前模型没稳定取出来。** 会话隔离 5 折
   （`.venv_xpu/runs/kfold/kfold.json`，实测逐位核对）：
   `body` 2.8716 / `body+wp` 2.1182 / `body+wp+img` **1.5542** /
   置黑 2.0992 / 打乱 2.2038 / `img_only` 2.0046；`gain.pct = 26.63`。
   但在因果 wp 口径下，融合增益只有 3.6%（3.2211→3.1041），单独口径 17.5% 仅 3/5 折改善
   （配对差 0.577±0.96，不显著）⇒ **未达到「≥15% 且 5 折一致」判据**。
   出处：`VLA跨会话评测勘误` §1、`VRChat具身agent训练方案v4` §0、kfold.json。

3. **主要瓶颈是读出方式，不是主干大小。** 动作头读 `apply_chat_template` 后的末位 token hidden
   （1024 维），该位置在预训练语义里只是回答起点；`--quad-feats` 把 8 个数字扩为 44 维二次特征
   使 MSE 约 2.39 → 约 1.18；同 8 步口径 `ridge-quad 45 参数 1.2371` vs `w9_full r32 1.4523`（差 17.4%，成立）。
   ⇒ 下一版优先改数值/视觉读出（query 池化 / 时间池化 / 数值直连 / 分支融合），
   再谈扩大主干或 LoRA 容量。出处：`VLA跨会话评测勘误` §3、`VLA训练方法评审` §1–§3。

4. **LoRA 容量不是越大越好，停止 rank>8 扫描。** 同口径扫描 r8 5.41M 最好、r16 ≈10.8M 1.559、
   r32 21.65M 1.4849、r64 ≈43.3M 1.617；18k 样本约 80 min，r32 把 186 个 Linear 接入 LoRA、
   约 10.6M 参数落在 MLP ⇒ 用低容量 r8 + 每场隔离验证集早停。
   ⚠️ 原文限定：r8 `1.4823` ≈ r32 `1.4849`、r16 `1.5587` 反而最差、r64 best 是 ep1 的 `1.6171`（ep0 1.7438）
   ⇒ **组间差异接近噪声，只能说 r64 明显更差，不能读出 rank 的精确最优点**。
   ⚠️ 1.4849 出自 `w9_full`（带 4 m 泄漏 wp / 3 维含 ω / card prompt / val 1,471），
   **只能作容量扫描的历史读数，不能作能力证据**。出处：`容量与数据-LoRA容量扫描` §1、
   `VLA跨会话评测勘误` §2、`.venv_xpu/runs/w9_full/summary.json`（1.4849168）。

5. **ω 标签：mean 聚合会抹掉短转向事件，peak 才把召回拉回来；`omega_norm` 是必要的数值稳定措施。**
   30 Hz 区间平均让转向事件召回 **0.0962 → 0.0228（−76%）**、峰值保留 0.196→0.130、
   still 段 +89.6%；2×2 消融（ω 聚合 × omega_norm）中 peak 把召回拉到 **0.1171（×5.1）**，
   B3（peak + norm + 3 epoch）`mse_all` −1.0%、`move8` 2.0052 优于 A 的 2.0617，
   被定为**离线候选**（单一 seed、400 样本、无显著性检验、真机未验证）。
   ⚠️ `still +89.6%` 的分层 **n=7**（peak 标签下 n=0）统计上不可用，须打星号；候选门 = `event_recall` 与 `peak_ratio`
   均不低于 A 且 still/stop-look 退化 **≤+10%**，两者都过按 MSE 更接近 A 选 B（D 召回 0.1915 更高但
   `mse_all +2.7%`、`walk_straight +14.8%`、max loss 39.67、仅 1 epoch 不可比）。
   ⚠️ 存在 **300 条**（`omega30_eval/ab.json`）与 **400 条**（`omega30_eval_final/`、`final_matrix/`）两套子集：
   `−4.1% / −3.3%`、`still +65.6% / +89.6%` 差异由此而来；同数据集内比模型只差 **2.1%~3.3%**，
   `−20%` 是 ω 标签 + topo（`0/400` 不同）的**数据集口径差异**，不是模型能力。
   no-norm 组 max loss 34.28 / 39.67（A 28.40）⇒ 去掉 norm 有数值风险；
   `omega_norm` 只改梯度里的相对权重（chan_w[ω]≈0.5311，ω 占未加权损失 36.21% → 加权后 23.16%），
   **不是设计错误**。出处（⚠️ `omega30最终评测与审计` §12.5 是「设计错误」的**被推翻出处**，不可引）：
   `交叉评测与omega_norm审计` §4.4、`omega聚合与norm消融` §11、`.venv_xpu/runs/B_peak_norm_3ep/best`。

6. **性能链：减 kernel 数 / 手工 XPUGraph 双图重放，不升 PyTorch，不恢复逐 token 自回归。**
   单算子派发压不动（隔离底线 24–25 µs，真实负载仅 3.5–3.7 µs/kernel，~100 µs 里约 95 µs 是同步等待）；
   图重放让 policy 前向 **538 → 123.4 ms（4.4×）**；`CC=icpx` + oneAPI 入 PATH 后
   训练侧 `--compile` **2.16×**（1319.8 → 611.0 ms/step），decode 图经
   `specialize_float=True` + rope fp32 编译成功（算子 6258→1824、wall 338→132.1 ms），
   但 **12 步 × 2 轴 = 24 token**，`24 × 132.1 ms = 3.17 s`（每 token GPU 忙碌 39.8 ms、其余 92 ms 是 1824 次阻塞提交），
   即使提交成本归零 `24 × 39.8 ms = 955 ms` ⇒ **2 Hz（500 ms）结构性不可能**。
   官方对照：XPU launch host 成本 **~5.3 µs**（PR #200891）vs 本项目 CPU 侧 3.5–3.7 µs/kernel；
   ~100 µs 里约 **95 µs 是 per-op 同步等待**（可改的用法：整段结束一次 event 等待 / immediate command list），不是硬件税。
   ⚠️ 本项目单算子开销有 25.35 / 104 / ~100 / ≈50 / 40 µs 五个口径，**未澄清前不要混引**。
   `2^43` 是 `unbacked_symint_fallback=8192` 代入 `2×8×8192³` 的结果，
   `ic.unbacked_symint_fallback=1024` 绕开（batch 6/8 的 grid 断言），但**「不撞断言」≠「能训」**：
   `smk_b8` 实测 **3.08–3.12 s/step**、`smk_b8fb` **loss=NaN** ⇒ batch 8 只算「解锁」，不是已验证的加速手段；
   `accum=2` 省 step 数不省吞吐。
   PyTorch 2.15.0 对 5 个瓶颈零命中且换 XDE 2026.1.3 / Triton 3.9 会动到
   `SYCL_UR_USE_LEVEL_ZERO_V2=1` 这层（538→123 ms 全压在它上面）⇒ **不升级，等 Graph Trees**。升级触发条件（可检查）：PR **#194598 + #197866 同时 merged** 且出现在某版 XPU
   release notes（issue **#200478** 仍 open / milestone=null）；升级前三条验收：双图 `fallbacks=0`、
   `cos_min ≥ 0.999`（实测 0.99995）、p95 ≤ **123 ms（离线）/ 176 ms（并发）**；**必须保留 2.14.1 venv 快照**再升。
   另 Windows 冷编译并行须 `COMPILE_THREADS=8` + `WORKER_START=spawn` **成对设**（单独设前者会 `pass_fds` 崩），并行利用率 46%，不需升级。
   出处：`CPU派发开销剖析` §5/§15、`Inductor-maxGridSize根因` §2–§4、
   `Intel官方…答复核查` Q1/Q3、`PyTorch版本升级评估` §1/§6、`陪伴型agent是否需要自回归` §1。

7. **工程链路：B3 已可加载 / 可 dry-run 回放，但未闭环。**
   `policy_deploy.py` 提供 manifest / preflight / replay；`deploy/b3_peak_norm_3ep.deploy.json`
   记录 head/adapter SHA256 与 schema；跨 venv 采用 `.venv` 主进程 → `.venv_xpu` worker 的
   行 JSON（stdin/stdout，每拍约 0.9 MB / 2 Hz ≈ 1.8 MB/s），`to_policy_rgb` 抽到 torch-free
   `policy_resize.py` 并用 `assertIs` 锁死单一实现。后端优雅退出把停机从 20.46 s 压到
   **0.3 s（LAS2 空闲）/ 3.5 s（编译中被 3 s 预算截断）**。⚠️ **旧实例不自我更新，需重启一次**；
   `SHUTDOWN_HARD_LIMIT_S=20 s` / navmesh 3 s 预算 / Job Object `KILL_ON_JOB_CLOSE` 是敢提前截断的前提；MJPEG 仍 30 FPS 推流。
   跨 venv 握手（载模型）**46~49 s 同步阻塞后端启动**；`preflight` 纯只读、任一项不过非零退出，必须挡
   `omega_unit=deg_s`（差 57 倍）/ `history_frame_s=0.4` / `adapter` 缺失（静默用未训练权重，mse8 差 7 倍）/
   `act_dim=2` / `w_max=0` / 缺 `VRC_POLICY_STALE` / schema 缺 `drop_wp`。
   ⚠️ 「未定位时是否让策略继续驱动」仍是**产品决策**：11-06 只把停车来源换成 `decide_stop()`，manifest
   `localization_gate.stops_on` 仍含 `unlocalized/unknown/pose_stale`，「策略接管了但什么都不做」未解决。
   出处：`B3真机链路接入与dryrun` §1–§3、`B3跨解释器接入` §1–§3、`后端优雅退出` §一/§二、
   `deploy/b3_peak_norm_3ep.deploy.json`。

8. **A* 降级为软引导，VLA 独占移动与转向。** navmesh 仍建图 / 定位 / 规划，但不再替 VLA 发轴或转向、
   不再设置 `policy_hold`；引导片段 `[guide] requested valid confidence age sigma`，先看 requested；
   `/policy/state` 同时报 `astar_control_enabled` 与 `astar_guidance`。
   ⚠️ 该链路的 `--astar-guidance` / `--path-in` / `--traversability-head` 开关在代码中存在，
   但前置数据 `astar_guidance.jsonl` / `traversability.jsonl` / `nav.jsonl` 在当前 G 盘数据集下
   **实测 0 个** ⇒ 属「接口就绪、数据未就绪」。⚠️ **还有第三重：当前 B3 checkpoint 根本没学过软引导** ——
   其 `input_schema.json` 仍 `drop_wp=true`，会忽略 A* 航点，必须重训 `drop_wp=false` 的 hybrid checkpoint。
   控制模式 4 类：`memory_revisit` 请求 A*，`explore` / `prompt_local` / `idle-safety` 不请求且必须写
   `requested=false`（**不是规划失败样本，不能当坏路径增强**）；`valid=false` 在 `requested=true` 时才是过期/定位不稳，
   `requested=false` 时只是「本来就不该用 A*」；仅 `memory_revisit` 开 `path_in=true`，对 **30%** 有效引导做增强。出处：`VLA独立控制链路改造`、`VLA软引导与视觉自主避障建图方案`、
   `VRChat具身agent训练方案v4` §1.1。

9. **GameScaling 基础模型的边界。** 发布的 8 个 checkpoint 是
   `0.8B/2B/9B/27B × {S1,S3}`；S1 只有 Minecraft，S3 是 80 个 **canonical world label**
   （非 80 款独立游戏，Minecraft 占 27.1%、有效世界数 D=35.2）。官方 `600→3000 steps` 是
   **每回合环境决策步数上限**，不是流匹配的 ODE 采样迭代数（42.3%→59.3% 不能搬）。
   ⇒ 两句话同时成立：不能说基础模型完全没有游戏世界预训练；也不能说它已预训练了 VRChat 地图探索。
   本项目微调目标是后者。出处：`GameScaling官方页要点` §0.1、`VLA跨会话评测勘误` §0、
   `流匹配头实施方案` §二/§5.3。

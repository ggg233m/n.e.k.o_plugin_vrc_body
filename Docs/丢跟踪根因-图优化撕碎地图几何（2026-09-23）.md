# 【历史】在线"丢跟踪"根因：位姿图优化把地图几何撕碎了（2026-09-23）

> 结论一句话：**在线 SLAM 不是"偶尔丢跟踪"，而是丢了一次以后**永远**回不来；
> 卡住它的不是参数，而是**地图本身的三维几何已被图优化破坏**——描述子匹配依旧很好
> （179 个匹配），但 PnP 只能拿到 6 个内点，远低于重定位门槛 45。
> 每一帧因此在"注定失败的重定位"上烧掉 ~640 ms，建图被钉在 1.5 fps。

## 二、把"为什么回不来"逼到具体门槛

### 2.1 当前画面**在**图里，而且匹配得很好

从 `/vision/frame` 取当帧，按 SLAM 的同一套预处理（裁剪 top=23/bottom=1095 → 640×360 →
灰度）、同一套 ORB（nfeatures=1200 / scaleFactor=1.2 / nLevels=8 / fastThreshold=12）、
同一个 `BFMatcher(NORM_HAMMING)` + ratio 0.75，对地图 50 个关键帧逐个做匹配：

```
gate = 45 ratio-test matches (reloc_min_inliers)
how many keyframes reach 45 : 27
top: kid=24 (t=51.7s) 185 次 | kid=23 183 | kid=27 156 | kid=26 152 ...
```

⇒ **"相机走到没建过图的地方" 这个解释被排除**。27 个关键帧都过了第一道门。

## 三、根因定位与修复：搬点公式少一次求逆（2026-09-23 已定位并修复）

`slam_core.py:546-614`。两步：

1. `optimize_map()` 把位姿图结果写回**每一个**关键帧的 `kf.R/kf.t`
   （`ensure_node` 在 `_add_keyframe:1115` 对每个关键帧都建了节点，所以全覆盖）。
2. 然后搬地图点（**旧代码**）：

```python
kid   = max(obs[0] for obs in mp.observations)   # 最新观测它的关键帧
T_old = before.get(kid)                          # = inv(_Rt_to_T(kf.R_old, kf.t_old))  -> c2w
T_new = np.linalg.inv(_Rt_to_T(new_kf.R, new_kf.t))                                       # -> c2w
delta = T_new @ T_old                            # <-- BUG：少一次求逆
mp.xyz = (delta @ [x,y,z,1])[:3]
```

### 3.1 约定的硬事实

- `KeyFrame.R/t` 注释写明 **world->camera**；`kf.pts3d` / `MapPoint.xyz` 写明 **world points**
  ⇒ 投影 = `K (R X + t)`。
- `.tmp/_conv.txt` 实测：把存的 (R,t) 当 w2c 用，kid=5 自投影 **2.00 px**；当 c2w 用是 **422 px**
  ⇒ **约定没写反**。
- 因此 `T = inv(Rt_to_T(R, t))` 是 **c2w**，上面两行成立。

### 3.2 正确公式（推导）

相机位姿 c2w 由 `C_old` 变成 `C_new`。要让一个世界点在**相机系**下的坐标不变（观测不变），
点在"新世界系"里的坐标必须是

    X_new = C_new @ inv(C_old) @ X_old      <=>      delta = T_new @ inv(T_old)

旧代码 `delta = T_new @ T_old` 把**一个完整位姿**当成了增量，只有 `T_old = I` 时才碰巧相等。

### 3.3 证据 A：合成自洽数据（`.tmp/_movedelta.py`）

真值世界点 + 两个 c2w 位姿，kps 由 `C_old` 投影得到（自投影恒 0），再模拟一次位姿修正：

| delta | 自投影中位 | <2px 占比 |
|---|---|---|
| `T_new @ T_old`（旧，现状） | **167.59 px** | 0.00 |
| `T_new @ inv(T_old)`（新） | **0.000 px** | 1.00 |

**167.59 px 与离线参考图实测 170.3 px 几乎重合** —— 这就是这条 bug 的指纹。

### 3.4 证据 B：真实回放帧上的 A/B（`.tmp/_verify_repair.py`）

同一份真实回放地图快照，分别用修复版与旧公式各调 3 次 `_optimize_and_correct`：

| 阶段 | 关键帧 | 自投影中位 | <2px 占比 |
|---|---|---|---|
| BASE（优化前） | 5 | **0.73 px** | 1.00 |
| AFTER-FIX（修复版） | 5 | **0.73 px** | 1.00 |
| AFTER-OLD（旧公式，同快照） | 5 | **11.44 px** | 0.40 |

⇒ ① 三角化本身是**干净**的（0.73 px），所以 2.3 那张"投不回去"的表不是三角化的锅；
② 旧公式**每优化一次就把点撕一次**（3 次 ⇒ 11.44 px），真实运行调用几十~几百次
⇒ 累积到实测的 170–258 px。

### 3.5 顺带证伪："位姿图空转"

一度怀疑节点存 w2c 而残差 `(T_wi T_ij)^-1 T_wj` 假设 c2w ⇒ 残差恒为 I ⇒ 优化空转。
**已证伪**（`.tmp/_graphconv.py`）：边取自真值轨迹、节点初值加噪声时，`cost`
**3.6e-2 → 9.6e-32**，位姿被正确拉回。⇒ **位姿图优化本身是工作的**，与本 bug 无关。

### 3.6 修法与验收

- 修法：`delta = T_new @ np.linalg.inv(T_old)`（一行）。
- 回归门：`tests/test_slam_point_repair.py`。两条不变量：
  ①位姿不变时点必须**不动**；②位姿修正后关键帧自投影仍 **< 2 px**。修前两条都红
  （点被搬 3.000 m / 自投影 188 px），修后 2/2 绿。
- 该不变量本就是 `_add_keyframe` 关联点用的（`reproj < pnp_reproj_err_px*2 = 8 px`），
  现在被写进单测，比"闭环标量"敏感得多。

### 3.7 次级隐患（仍在，非主因）

同一个物理点只被"**最新观测它的那个**关键帧"的 delta 搬走。当位姿图**真的**改动多个关键帧
（有回环时），相邻点会用不同 delta ⇒ 仍有非刚性。修复后风险被大幅削弱（delta 现在是正确的
增量），严格做法仍是让点云跟随**单一全局 SE(3)**，或直接上真正的 BA。记为待办。

### 3.8 为什么"闭环指标看着挺好"却把地图搞坏了

闭环 5.243→0.002 m 是**轨迹标量**指标，只依赖位姿图；点云是在位姿图之后用上面那段 ad-hoc
代码搬的。位姿对了、点云毁了，两件事可以同时成立。

## 四、完整因果链

```
slam_optimize 单次 3.0–4.0 s（本轮已量到 max 3969 ms）
        ↓ 消费线程被卡住 ≥2.5 s
live_mapping.process() 的断档检测命中 → mark_tracking_gap() → state=LOST
        ↓   （mark_tracking_gap 只清 _reloc_candidate/prev_*，**不清 _pending_init**）
LOST 后每帧：_relocalize() 失败（因为地图几何已坏，PnP 上不去 45）
        ↓  _lost_frames ≥ 6 → 每帧再试 _start_new_segment() → _try_init() 失败
        ↓
每帧固定开销 ≈ 638 ms(relocalize) + 37 ms(start_segment) ≈ 675 ms
        ↓
建图 1.55 fps、82% 丢帧；metric_scale samples 永远 0
        ↓
scale_validated=false ⇒ 导航图 0 条 passable、49 条 unknown
```

补充两条**独立的次级缺陷**（都在 LOST 路径上，值得单独修）：

1. **`_pending_init` 锚点永不刷新**（`_try_init:671` `idx_a = 0` + 两处裁剪都保留下标 0，
   且只在成功时清空）。相机一旦离开锚点帧的匹配范围，"新建 segment"就**永远不可能成功**
   ——现场是 969 次尝试 0 次成功。而且 `_try_init` 只比 (最老, 最近×N)，从不试(最近, 最近)。
2. **失败的重定位没有退避**：`reloc_rejected_weak` 已 1181 并持续增长，每帧重跑
   40 个关键帧 × BF 匹配 = 638 ms。一旦丢掉跟踪，整条流水线就被这段注定失败的搜索钉死。

另：静止相机无 6 视差 ⇒ `_try_init` 的 `init_min_median_parallax_deg=1.5` 天然过不去。
现场画面实测：相隔 6 s 的两帧**视觉上完全一致**，仅 ~2% 像素变化（来自墙上的循环动画海报），
即用户当时是**站着不动**的。这不是 bug，但它让"丢跟踪后靠走动重新初始化"这条自救路径失效。

## 五、建议修复顺序（按性价比）

1. ✅ **已修（2026-09-23）：`_optimize_and_correct` 的搬点公式。**
   `delta = T_new @ T_old` 改为 `delta = T_new @ np.linalg.inv(T_old)`（证据见第三节 3.1–3.4）。
   回归门落成 `tests/test_slam_point_repair.py`（修前 2 红、修后 2 绿），验收口径就是
   **每个关键帧的有限 `pts3d` 用它自己的 (R,t) 投回自己的 kps，中位 < 2 px**。
   ⚠️ 位姿图相关改动**不能**用"回放逐位相同"当回归门（系统病态），但**自投影不变量**可以，
   而且比"闭环标量"敏感得多。
   待办：3.7 的"点云跟随单一全局 SE(3)"仍是更严格的收尾。
2. **给失败重定位加退避**：`_lost_frames` 超过 `relocize_grace_frames` 之后，
   按指数/固定间隔（如每 10 帧）才重试一次，并优先只试 BoW Top-N（现在是 40 个全过）。
   当前每帧 638 ms 是纯浪费。
3. **`_pending_init` 锚点滚动**：裁剪时改为保留**最近** N 帧作为候选池，
   `_try_init` 同时尝试 (最近, 次近) 等近距离配对，而不是永远拿"最老一帧"当锚。
4. **断档与 `slam_optimize` 的相互作用**：4 s 的 optimize 尖峰足以触发 2.5 s 断档
   （`slam_optimize` max 3969 ms，`max_timestamp_gap_s` 2.5）。要么把 optimize 挪到
   消费线程之外/异步，要么断档判据不要用"被处理帧之间的采集时间差"。

依赖侧（另一件事）：scipy 已正式加依赖，`pyproject.toml` 加 `scipy>=1.13,<2`、
`DEPENDENCIES.json` 记 `1.17.1`（py311 线；1.18.1 要求 py≥3.12）。详见
`Docs/在线建图停滞-根因与修复（2026-09-23）.md` 第五节。

## 2. 本轮实测到的 eager 数据（唯一一组完整数据）

口径：`warm=8 / iters=20`，取 p50；CPU 派发 = 不 sync 的返回时间。

| 部分 | 墙钟 ms | CPU 派发 ms | GPU ms | 总事件数 | GPU kernel 事件数 |
|------|---------|-------------|--------|----------|-------------------|
| **整模型** | 373.8 / 393.5 | **360.6 / 378.6** | 137.5 / 135.4 | 111,103 | **6,891** |
| **visual（ViT 塔）** | 126.6 | **120.8** | 24.1 | 16,038 | 957 |
| **language_model（推算）** | 247.2 | **257.9** | 111.3 | 95,065 | 5,934 |

（两次整模型测量分别在不同进程，用于核对稳定性；visual 用 `inner.visual(hidden_states=..., grid_thw=...)` 单独测，lm 为整体减 visual 的推算值。）

### 2.1 由此得到的两个结论

**结论 A：视觉塔是严重失衡的成本中心。**
- 占 CPU 派发 `120.8 / 378.6 = 31.9%`
- 但只占 GPU 时间 `24.1 / 135.4 = 17.8%`

ViT 只处理 112 个视觉 token（448×256、2 帧），却发出 **957 个 GPU kernel**、花掉 **120.8 ms CPU 派发**。
单位 GPU 工作的派发成本极高。**先把 visual 塔压下来，比在 LM 上调 compile 参数更可能有收益。**

**结论 B：`37 µs/op` 只适用于 eager 路径，不适用于编译路径。**
- eager：360.6 ms / 6,891 kernel 事件 ≈ 52 µs/事件（量级吻合 37 µs/aten op）
- Lead 实测 compile default：179 ms / 48,454 事件 ≈ **3.7 µs/事件**

两者差一个数量级，说明编译后**绕开了 dispatcher + 内存池 + 逐参数打包**这条昂贵路径。
所以「把 CPU 派发压到 150 ms 以下」在结构上不是不可能的——瓶颈不在单个 kernel 的提交成本，
而在于**还能剩下多少 kernel**。这正是本该由本轮扫描回答、但没能回答的部分。

## 3. 环境坑：`Failed to find C compiler`（已定位并修复）

任务描述给的环境变量**不完整**，直接照抄会 100% 失败：

```
RuntimeError: Failed to find C compiler.
Please specify via CC environment variable or set triton.knobs.build.impl.
```

根因链：
1. triton 3.8.0 编译 inductor 生成的 C launcher 需要 C 编译器。
2. `cl.exe` **不在 PATH**。MSVC 2022 Community 装在
   `C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.44.35207`，
   但会话里从未 `vcvars`。
3. 没有 gcc / clang / icx 在 PATH 上。

**修复（已验证可跑通，5 秒 smoke test 通过）：**
编译前先 `call "...\2022\Community\VC\Auxiliary\Build\vcvars64.bat"`。
封装脚本：`.tc_cache/sweep/pyenv.bat`

```bat
@echo off
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat" >nul 2>&1
set PYTHONUTF8=1
set TMP=<root>/.tc_cache/tmp
set TEMP=<root>/.tc_cache/tmp
set TORCHINDUCTOR_CACHE_DIR=<root>/.tc_cache/inductor_sweep
set TRITON_CACHE_DIR=<root>/.tc_cache/triton_sweep
set TORCHINDUCTOR_COMPILE_THREADS=1
set PATH=D:\Program Files (x86)\Intel\oneAPI\2026.0\bin;%PATH%
"<root>/.venv_xpu/Scripts/python.exe" %*
```

用法：`cmd /c "<root>\.tc_cache\sweep\pyenv.bat <你的脚本> 2>&1"`

> 关于 `CC=icpx`：Lead 建议设 `CC=icpx;CXX=icpx`。**本机未验证成功**——icpx 只在
> `D:\Program Files (x86)\Intel\oneAPI\2026.0\bin` 内，且 vcvars 路径已被证明有效。

（inductor 的缓存锁 + `TORCHINDUCTOR_COMPILE_THREADS=1` 在争用时无超时保护）。

**没能验证的怀疑点**（留给下一轮）：
1. 并发进程抢同一个 inductor 缓存锁 → 死等。
2. `chunk_gated_delta_rule` 走 PyTorch 参考实现（`flash-linear-attention` 未安装），
   动态形状 + data-dependent control flow 让 dynamo 反复 recompile / 卡在 guard 求值。

3. 整模型编译（C1）本来就要 60–300 s，我给的 20 min 窗口可能仍不足——但零缓存写入说明不是纯慢。

## 5. 明确回答：CPU 派发的下限

**本轮无法给出实测下限。** 诚实地说：我一组 compile 配置都没测成。

能给的判断分三层，按可信度排序：

**① 确定（实测）：XPU graph 不可用，`reduce-overhead` 无效。**
```
torch.xpu.XPUGraph() → RuntimeError:
  UR_DEVICE_INFO_GRAPH_RECORD_AND_REPLAY_SUPPORT_EXP
```
这是 Level-Zero 驱动能力查询失败，不是 PyTorch 开关。A770 + 当前驱动**没有** graph record/replay。
另外 cudagraph 即便开了也会被 inductor 跳过，日志明说：
`skipping cudagraphs due to multiple devices: device(type='xpu', index=0)`。
→ **`mode="reduce-overhead"` 在 A770 上不会有任何收益，不必再试。**

**② 有依据的推断（非实测）：150 ms 并非结构下限。**
Lead 实测 compile default 已经是 179 ms CPU / 48,454 事件 ≈ 3.7 µs/事件。
如果扫参能把 kernel 数再压 20–30%，CPU 派发自然落到 130–145 ms。
所以「能不能破 150」的答案是**取决于 kernel 数能压多少**，而不是被 37 µs 卡死。
但这个推断**没有得到本轮任何验证**，请勿当作结论引用。

**③ 本轮唯一可支撑的「收益上限」说法：**
> 在 compile 默认配置（179 ms CPU）之上，**本轮没有测出任何改进**；
> 因此截至本轮，**compile 配置扫描这条路已验证的收益上限是 0 ms**（相对默认配置）。

这不是说它没用，而是说**我没测出来**。

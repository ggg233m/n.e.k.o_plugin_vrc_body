## 契约口径变更（2026-09-23）

本报告上方「执行器契约」一行中的 `stale_revision_rejected: True` 是 **09-22 的快照**，当时的判据是
`stale["state"] == "failed"`（过期 revision ⇒ 转入终态 `failed`）。

**该判据已更正。** 过期 revision 的正确契约是「**拒绝但不推进**」——保持原状态、只置 `ok=False`，
调用方拿到正确 revision 后可以重试。现判据为：

```python
"stale_revision_rejected": stale.get("ok") is False and stale.get("state") != "moving"
```

变更理由（两条，均有代码依据）：

1. **上层本就是这个语义**：`service.confirm_nav_target()` 在调用执行器之前先做一层 revision 校验，
   返回的是「保持 nav_target 状态 + `ok=False` + `reason=route_revision_expired`」。
   执行器此前转 `failed` 与上层不一致，09-22 22:40 的改动是把两层对齐，不是回归。
2. **两种失败性质不同**：传错 revision 是**调用方参数问题**（可修正重试）；地图 revision 真变化是
   **环境变化**，已由 `service._on_nav_map_revision_changed()` 单独处理（moving → `stop_route`、
   prepared → `cancel_route`、nav_target → `rejected`），不该由执行器的参数校验用不可逆终态去惩罚。

安全性不受影响：confirm 被拒后状态不会变成 `moving`，`step()` 因 `state != "moving"` 直接返回，
不存在「状态看着是 prepared 就往前走」的风险。

新增回归：`tests/test_route_executor.py::test_stale_revision_rejected_then_correct_revision_succeeds`
—— 错 revision 被拒后，用正确 revision 仍能确认成功（钉住「可重试」这个契约）。

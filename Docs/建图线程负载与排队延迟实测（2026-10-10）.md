# 建图线程负载与排队延迟实测（2026-10-10）

> 接 `ROADMAP.md` **P5**（"延迟基准必须在真实负载下测"）。
> 起因：2026-10-10 把 `bow_candidates` 默认值从 0 改成 4（`nav_loop.py:64`），需要回答
> "这个改动在**建图线程**上要付多少代价" —— 因为**仓库里此前没有任何建图线程的负载数字**。
>
> ⚠️ **本文全部是离线回放**（`.tmp/map_budget.py` 等，按录制时间戳排队、逐事件跑在线同序），
> **不是 live 测量**。它回答的是"这份负载在单线程上要多久"，**不回答**"开着 VRChat 时还够不够" ——
> 后者仍是 P5 的未决项（`gpu_bench_result.json` 自记"未开 VRChat"）。

## 〇、一句话结论

1. **`bow_candidates=4` 的代价量清了**：`BowIndex.query` 随帧数**线性增长**，每关键帧 +25~50 ms。
   旧录制（3014 kf）线程占用 10% → **13%**；新录制（822 kf，288 s）**23~33% → 34~46%**。
2. 🔴 **排队延迟的 p99 从 0.2~0.4 s 涨到 1.0~2.9 s**，>1 s 的关键帧占 0~0.5% → **1~5.7%**。
   且**不是均匀分布**：见 §二·补 —— 延迟随关键帧**密度**走，`>1 s` 全部聚在密集段的窗口里。
3. **降级机制有效但要用精度换**：一批里关键帧 > 2 时只让最后一帧查词袋
   （其余仍入索引），lag_max 1334 → **898 ms**、>1 s **归零**；代价是留出残差中位 0.64 → **0.89 m**。
4. **3~7 s 的栅格化尖峰不是现行代码的问题**：定位到旧录制的 `cam_h_hyst_m=0.02`
   —— 这正是 **2026-10-05 已诊断并已修**的那一条（`cam_h` 在直方图相邻桶间反复翻转 ⇒ 全体关键帧重算）。
   按现行 0.06 重跑同一录制，raster max **6686 → 488 ms**。

## 一、方法与被测条件

`map_budget.py`：按 `events.jsonl` 的时间戳排队，在**单线程**上按在线同序处理每个事件
（回环 → 入图 → 回环后换位姿 → 每 `map_min_interval_s`(0.3 s) 栅格化 + `build`）。
量三个量：**线程占用率**（忙时/总时长）、**各阶段单次耗时**、**关键帧排队延迟**（处理完时刻 − 事件时刻）。

两场录制，代表两个极端规模：

| 录制 | 关键帧 | 时长 | 词汇树规模效应 |
|---|---|---|---|
| `20260929_045615` | **3014** | 4860 s | 每帧查询最贵 |
| `20261010_033237` | 822 | 288 s | 占用率最高（事件密度大） |

⚠️ **运行间波动不可忽略**：同一命令（`20261010_033237 bow4`）三次跑出
**线程占用 34% / 35% / 46%**、p99 排队 **972 / 1055 / 2937 ms**。
⇒ 下面所有"占用率 / p99 延迟"的数字都应按**区间**读，**不要把单次值当结论**。
（`bow0` 三次 23% / 33%，同量级；留出残差这类确定性输出不受影响。）

`bow0` vs `bow4` 是同一份负载的 A/B，**只有 `bow_candidates` 一个变量不同**。

## 二、★ 代价：每关键帧 +25~50 ms，占用率与排队延迟都抬高

| 录制 | bow | 线程占用 | 回环 中位/p99 | 入图 中位/p99 | 栅格化 中位/p99 | 排队延迟 中位/p99/max | >1 s 的 kf |
|---|---|---|---|---|---|---|---|
| 045615（3014 kf） | 0 | 10% | 37 / 81 | 2 / 36 | 146 / 296 | 39 / **329** / 4422 | 0.3% |
| 045615 | **4** | **13%** | 90 / 147 | 1 / 39 | 148 / 307 | 101 / **2121** / 5292 | **2.6%** |
| 033237（822 kf） | 0 | 23~33% | 18~22 / 53~74 | 3~5 / 18~22 | 92~148 / 225~432 | 22~33 / **220~402** / 775~1188 | 0.0~0.5% |
| 033237 | **4** | **34~46%** | 43~56 / 108~133 | 3~5 / 21~30 | 89~141 / 621~960 | 50~78 / **972~2937** / 1356~4621 | **1.0~5.7%** |

- **代价落在回环阶段**：中位 37→90 ms（旧）、22→43 ms（新）⇒ 每关键帧 **+25~50 ms**。
  入图 / 栅格化基本不动 ⇒ 不是建图本体变慢，是外观检索变慢。
- **`BowIndex.query` 随帧数线性涨**：旧录制 3014 kf 的每帧代价约为新录制 822 kf 的 2 倍，
  与"候选池更大"一致 —— 这也解释了为什么 gap 随录制变长而变宽（50 ms vs 25 ms）。
- 🔴 **排队延迟是最该看的一列**：`bow0` 时 p99 在 0.2~0.4 s（与 `map_min_interval_s=0.3` 同档），
  `bow4` 时 p99 到 **1.0~2.9 s**、max 到 **4.6~5.3 s**。
  ⚠️ 这个量**不单调于 kf 数**：822 kf 的场次反而比 3014 kf 更差（事件密度更高、线程本就 3 成占用）。
- **`_pending` 是无界列表**（`nav_online.py:667`，`_mapping_loop` 一次全取走 `:1071`）⇒
  **积压不会丢数据，只会让地图"停在过去"**。所以延迟的后果是**地图新鲜度**，不是丢帧 ——
  但 `map_min_interval_s` 的设计意图（0.3 s 一跳）在 p99 上已经失效。

### 二·补 ★ 延迟的时间结构：**随关键帧密度走**，不是"越跑越积压"

只看 p99/max 会误判成"录制越长越卡"。把 lag 按时间分桶（`lag_timeline.py`）后，结构完全不同：

**`20261010_033237`（287 s，60 s 桶）**

| 时段 | kf 数 | bow0 中位/p99/max | bow0 >1s | bow4 中位/p99/max | bow4 >1s |
|---|---|---|---|---|---|
| 0–60 s | 129 | 42 / 171 / 669 | 0 | 55 / 192 / 676 | 0 |
| 60–120 s | 157 | 56 / 185 / 202 | 0 | 95 / 244 / 370 | 0 |
| 120–180 s | 186 | 33 / 204 / 216 | 0 | 76 / 272 / 350 | 0 |
| **180–240 s** | 188 | 46 / 288 / 299 | 0 | **144 / 1945 / 1982** | **8** |
| **240–300 s** | 162 | 94 / 883 / 931 | 0 | **260 / 2195 / 2330** | **17** |

**`20260929_045615`（4858 s，600 s 桶）**

| 时段 | kf 数 | bow0 中位/p99/max | bow0 >1s | bow4 中位/p99/max | bow4 >1s |
|---|---|---|---|---|---|
| 0–600 s | 779 | 42 / 624 / 1296 | 3 | 70 / 721 / 1272 | 3 |
| **600–1200 s** | **1036** | 115 / 535 / 1022 | 1 | **200 / 2462 / 2714** | **78** |
| 1200–1800 s | 197 | 193 / 230 / 240 | 0 | 223 / 252 / 259 | 0 |
| 1800–2400 s | 196 | 197 / 217 / 232 | 0 | 244 / 271 / 282 | 0 |
| 2400–3000 s | 197 | 214 / 240 / 247 | 0 | 267 / 289 / 298 | 0 |
| 3000–3600 s | 196 | 233 / 902 / **6817** | 2 | 289 / 1003 / **6796** | 2 |
| 3600–4200 s | 197 | 254 / 276 / 298 | 0 | 315 / 337 / 349 | 0 |
| 4200–4800 s | 196 | 272 / 294 / 297 | 0 | 337 / 371 / 387 | 0 |

三条结论（与"线性积压"的直觉相反）：

1. **`>1 s` 是聚集的，不是均匀的**：033237 的 25 个 `>1 s` 全在最后 120 s；
   045615 bow4 的 83 个里 **78 个挤在 600–1200 s 这一桶**（该桶有 1036 个 kf，是全程最密的一段）。
   ⇒ **触发条件是"短时间内的关键帧密度"，不是"已经跑了多久"**。
2. **中位 lag 有一条缓慢的上行基线**（bow0：42 → 277 ms），这段**与 `bow_candidates` 无关**
   （bow0 同样存在）⇒ 它是"每 0.3 s 一次栅格化 + 图变大后 `_sync_acc` 变贵"的结构性成本，
   属于另一个问题，**不要算在词袋这次改动头上**。
3. **`bow4` 把簇发窗口的 p99 从 0.5~0.9 s 抬到 1.9~2.5 s**，但**不改变簇发的形状** ——
   即它放大峰值，不是制造积压。

⚠️ 因此"`bow4` 让建图线程在录制末尾会积压"这个说法**不成立**（我第一版这么写过，已改）：
正确说法是 **`bow4` 把密集段的峰值延迟抬过 1 s**，而**密集段本身在两种配置下都存在**。

## 三、降级机制：拿精度换延迟（`.tmp/bow_degrade.py`）

机制：线程空闲时取走**所有已到事件**为一批；`mode=degrade` 且**一批里关键帧数 > THR(2)** 时，
**只有最后一帧查词袋**（其余仍正常入索引与建图）。同一次运行里留出 30% 重访对（禁 ±3 帧邻域）评估精度。

`20261010_033237`，两个种子：

| 模式 | 留出残差中位 | p90 | <0.5 m 占比 | 回环数 | 占用 | 大批次 | 跳过的 kf | 排队 中位/p99/max | >1 s |
|---|---|---|---|---|---|---|---|---|---|
| `full`（现行） | 0.64 / 0.47 | 1.85 / 1.30 | 0.40 / 0.54 | 175 / 174 | 0.37 / 0.35 | 0 | 0 | 55 / 990 / 1334 | 1.0% / 0.4% |
| `degrade` | **0.89** / 0.47 | 2.29 / 1.31 | 0.28 / 0.54 | 173 / 172 | 0.34 / 0.33 | 9 / 6 | 24 / 17 | 52 / **687** / **898** | **0.0% / 0.0%** |

- 降级后 **lag_max 1334 → 898 ms、>1 s 从 0.4~1.0% 归零**，占用率小幅下降（0.37 → 0.34）。
- 代价：种子 0 的留出残差中位 **0.64 → 0.89 m**（种子 1 无变化 0.47）⇒
  **是"用地图精度换地图新鲜度"**，不是白捡。
- 被跳过的 kf 只 17~24 次（占 822 的 2~3%），所以代价没有失控；但**两个种子的结论不一致**，
  要作为默认策略还需要更多场次与更多种子。

## 四、栅格化尖峰：3~7 s 的那几次，根因是**旧录制**的 `cam_h` 滞回

`spike_prof.py` 给每一步与 `rasterize` 内部各段计时（同一排队模拟，无留出）。
`20260929_045615` 上按三种配置跑：

| 配置 | 排队 中位/p99 | 排队 max | 栅格化 max | 关键帧 中位/最大 |
|---|---|---|---|---|
| `bow0` | 39 / 257 | 4110 ms | **7075 ms** | 38 / 548 |
| `bow4` | 89 / 950 | 3840 ms | **6687 ms** | 89 / 662 |
| `bow4` + **`cam_h_hyst_m=0.06`** | 86 / 653 | **887 ms** | **488 ms** | 86 / 880 |

- **尖峰的主因不是词袋，是 `cam_h`**：只把滞回从 0.02 改到 0.06（其余不动），
  栅格化 max **6687 → 488 ms**、排队 max **3840 → 887 ms**。
- 单次尖峰的构成（`bow4` 下最大一次 487.8 ms）：
  `_sync_acc` 286 · `_sync_ray` 98 · `build` 46 · `_ray_veto` 18 · `_rotated` 15。
  `_sync_acc` 正是 `_update_cam_h` 变更后**全体关键帧重算**走的那条路径
  （`rasterize()` 内 `keys = set(self._pts)` 全量重建，`nav_mapping.py:1142`）。
- ✅ **这与 `Docs/虚假障碍-根因与分层修复（2026-10-05）.md` §8.1 是同一条**：
  该文实测 044153 的 `cam_h` 在 1.745/1.765 间翻转 9 次、单次最大 1529 ms，
  修法（滞回 0.06 + ±2 桶平滑 + 按规模限流）已进代码 `nav_mapping.py:62`。
  **本次只是在新录制上再确认了一次**：045615 是 09-29 录的，`meta.json` 里
  `cam_h_hyst_m = 0.02` ⇒ 它带着旧配置，尖峰是**历史配置的产物**，
  **不是现行代码的缺陷**（033237 的 meta 已是 0.06，`spike_prof` 实测 raster
  max 1060 ms、无 3 s 级尖峰）。
  > 045615 在 0.02 下的 `cam_h` 变更记录（`camh_events.py`，5 次）：
  > `1.730→1.785(k0) → 1.755(k46) → 1.735(k298) → 1.755(k439) → 1.775(k2562)`
  > —— 注意 **k0/k46 两次发生在第 1 帧和第 47 帧**，那时重建还便宜；真正贵的是
  > **k2562 那次（2563 个关键帧的全体重算）**，正对应 §四 表里最大的那几次尖峰。
- ⚠️ 别把这句读成"现行代码没有尖峰"：033237 bow4 的 raster max 仍有 **1060.6 ms**（p99 726 ms），
  只是**不再有 cam_h 造成的秒级尖峰**（对比 045615 的 6687 ms / 7075 ms）。

## 五、还没做的

1. **live 测量**（P5 本体）：以上全是离线回放。开着 VRChat 时这些数字会怎么变，**没有数据**。
2. **降级机制是否该默认开**：两个种子的留出残差结论不一致（一个 0.64→0.89、一个不变），
   样本太少。且它**没有在线实现** —— `nav_online._mapping_loop` 目前一次取走全部 `_pending`，
   没有任何"大批次只查最后一帧"的逻辑。
3. **`_pending` 无界**：积压只影响新鲜度、不丢数据，但**没有上限也没有监控**。
   是否要加水位/告警，本文不做裁定。
4. **`BowIndex.query` 的线性增长**是否有可压的常数（目前只知其存在，未查可否优化）。
5. **中位 lag 的上行基线**（§二·补 第 2 条：bow0 也从 42 → 277 ms）**未查**。
   它与词袋无关，是栅格化/`_sync_acc` 随图变大的成本，值得单独一轮。

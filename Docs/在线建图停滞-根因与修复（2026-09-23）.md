## 一、一句话结论

建图期消费循环慢**不是算力不够、也不是采集不够**，而是四处**重复计算 / 求解器选型错误**：

1. `pose_graph.optimize()` 建**稠密** Hessian 并用 `np.linalg.solve` 做 O(n³) 求解 —— 单次 `optimize` 占**整轮墙钟 63%**，这才是"建图停滞"的直接原因；
2. 每次 LM 内层 λ 重试都**白算一遍完整雅可比**，只为拿到一个代价；
3. 有限差分雅可比里的 `se3_exp(±ε·e_k)` 与位姿无关却反复重算（4.49 ms/边）；
4. `slam_core` 每帧把同一份局部地图窗口算 2–3 次、把同一个关键帧的回环检测重跑 N 次 —— 这是**在线** 468 ms/帧的直接来源。

> 与本文件相关的上一轮结论互不冲突：上一轮的症状是"**停止建图后**（`mode=idle`）`mapping_priority` 捷径失效、重路径拖到 1 Hz"；本轮查的是"**建图进行中**（`mode=mapping`）单帧 SLAM 本身就是瓶颈"。两者是不同模式下的两个瓶颈。

## 二、测量口径（先说清，否则数字会互相打架）

- ⚠️ **本机 numpy 用 scipy-openblas，`MAX_THREADS=24`**。`time.process_time()` 会把 24 个线程的 CPU 时间**加总**，用它测多线程 BLAS 会得到约 20 倍虚高。本轮所有结论**只用 `time.perf_counter()` 墙钟**，且机器空闲、单进程测。
  - 踩坑记录：先用 CPU 时间测出"1434 阶稠密解要 21 s"，改成墙钟后是 **1.77 s**。凡多线程 BLAS 都不可用 CPU 时间。
- 回放口径：`.slam_probe/offline_probe/gray_640x360_s3_full.npz` 取前 700 帧；`SlamConfig(width=640,height=360,horizontal_fov_deg=102.45,target_fps=5)`；`n_features=1200`、`local_window=12`、`retry_window=30`；逐帧给 `slam.process()` 计时，埋点经 `set_profiler` 走 `StageProfiler`。
- 该回放**能离线复现**在线量级（首次测得单帧 353–471 ms，与在线 468 ms 同量级）⇒ 后续可在离线快速迭代。

### R1　`_optimize_and_correct`：稠密 Hessian + O(n³) 求解

- `pose_graph.optimize()` 里 `H = np.zeros((6*n, 6*n))`，随后 `np.linalg.solve(Hd, b)`。
  第 419–421 行的注释写着 *"Assemble sparsely … building it densely and running an O(n³) solve wasted ~1.8 s per iteration at 120 nodes"* —— **注释是意图，代码从未稀疏化**。
- 239 关键帧 → dof = 1434：**单次稠密解 1 769 ms**；一次 `optimize` = **31 遍完整雅可比 + 30 次求解** ≈ 76 s。`_optimize_and_correct` 每 40 个图节点触发一次，700 帧里触发 6 次 ⇒ 448 s。
- 实测（墙钟，真实规模系统）：

  | | dof=720 | dof=1434 |
  | --- | --- | --- |
  | 稠密解 `np.linalg.solve` | 1 099 ms | 1 769 ms |
  | 稀疏解 `scipy.sparse.linalg.spsolve` | **43 ms** | **18 ms** |
  | 加速 | **×25** | **×100** |
  | 相对误差 vs 稠密 | 1.5e-13 | 1.9e-13 |

  一次完整 `optimize`：稠密 45.7 s / 72.4 s → 稀疏 **8.3 s / 15.8 s**；`final_cost` 两者**小数点后 8 位完全一致**。
- **修法**：Hessian 装配为 `{(bi,bj): 6×6}` 稀疏块，走 `scipy.sparse.linalg.spsolve`；**scipy 缺失时自动回退原稠密解**（行为不变，只是慢）。
- 稀疏化后 `optimize` 的剩余成本 **80% 是那 31 遍雅可比**（15.8 s 里 12.7 s）⇒ 见 R3。

### R2　内层 λ 重试白算完整雅可比

- LM 内层每次换 λ 都要判断"新代价是否更小"，原实现用 `evaluate()`，包含每条边的完整 `_edge_jacobian_analytic`（12 次 SE(3) 求值 + 雅可比），而重试时**位姿被回滚、雅可比根本没变**。
- **修法**：新增 `_edge_residual()`（只 1 次 `se3_log`），重试只算残差；只有**接受**该步时才 `assemble()` 建一次 Hessian。实测残差一遍 99 µs/边 vs 完整 4 489 µs/边。接受判定所用的代价公式**逐字未变**，因此接受/拒绝序列不变。

### R3　`_edge_jacobian_analytic` 4.49 ms/边

- 其中 `Jj` 走 6 组中心差分 = 12 次 `se3_exp`+`se3_log`，`Ji` 还要一次 `_se3_left_jacobian_inv`（再 6 次）。
  但 `se3_exp(±ε·e_k)` **只是 (ε,k) 的函数，与任何位姿无关**，却每条边每次调用都重算 18 次。
- **修法**：模块加载时预计算两组基方向常量（ε=1e-7 / 1e-6）。**代数上完全等价**，实测 4 489 → **1 718 µs/边**（2.6×）。
- 剩余成本的 ~85% 是 18 次 `se3_log`（单次 82.7 µs，被 numpy 微矩阵调用开销主导）⇒ 见"下一步"。

### R4　`slam_core` 每帧重复劳动（**在线** 468 ms/帧的直接来源）

| 问题 | 修法 | 实测 |
| --- | --- | --- |
| `_local_map(30)` 是**逐点 Python 循环**（18 308 个点 ⇒ 86 ms），且**同帧被调 2 次**（`_track_local` + `_associate_map_points`），而地图在这两者之间不可能变 | 改为"掩码 + `np.concatenate`"向量化；并按新增的 `Map.revision`（关键帧增删 / 图优化移动点位时自增）**记忆化**，同帧同窗口直接复用 | 重复调用 **0.00 ms**（命中缓存）；`associate` 中位 **177.7 → 59.0 ms** |
| `_try_loop_closure(self.last_kf)` **每帧都对同一个 `last_kf`** 重跑候选匹配 + 200 次 RANSAC，而 `(kf, cand)` 一旦失败结果就是确定的（描述子与 3D 点都没变） | 新增 `_loop_tried` 备忘集；仅当**点位被图优化移动**（`_points_moved_revision` 变化）才清空 | median **35.8 ms → 0.50 ms**（全段）/ **106.6 → 0.39 ms**（12 帧夹具），71× |
| `bow.index_keyframe(kid, des)` 每帧对已索引的同一个 kid 重算 BoW 直方图；`bow.query(kf.des, …)` 又算一遍同一个 | `index_keyframe` 对已存在 kid 直接返回（描述子不可变）；`query` 新增 `vec=` 参数复用已算好的向量 | `index_keyframe` 中位 **0.00 ms**（提前返回） |
| `_add_keyframe` 里 "把窗口点挂到新关键帧" 的**逐点写回循环** | 掩码后一次性 `kf.pts3d[sel_i] = wpts[sel_o]`（numpy 对重复下标为 last-wins，与原循环语义一致） | keyframe 阶段由 71.8 → 48.4 ms |

## 五、重要副作用与风险（必读）

- ⚠️ **位姿图变更后，回放不再逐位可复现。** 该系统**病态**：整个图的 gauge 只靠 node 0 上一个权重 1e2 的**软锚定**，`H + λ·diag_scale·I` 仍接近奇异，条件数极大。因此任何求解器替换都会在 1e-9 ~ 1e-6 量级扰动解，经 SLAM 混沌放大后**关键帧排程会变**（同一 300 帧处：pre-fix 92 kf、稀疏解 103 kf）。
  ⇒ **位姿图相关改动不能用"回放逐位相同"当回归门**，只能比质量指标（kf 数、`tracks_ok`、`loop_closures`、`map_points`）。
- 这也解释了**为什么 CG 不划算**：试过 Jacobi 预条件共轭梯度，`rtol=1e-8/maxiter=400` 时相对稠密解仍有 **2.6% 误差**（根本没收敛）；要收敛到 1e-10 需 ~2000 次迭代、5.8 s，比多线程稠密解还慢。**已放弃 CG，改用精确稀疏直接解**（代码里只留 `_DENSE_SOLVER` 开关供测试对照）。
- ✅ **scipy 已正式加依赖（2026-09-23 定）。** 宿主允许清单 `plugin/core/python_dependencies.py:HOST_PROVIDED_REQUIREMENT_NAMES` **实测只有 `{"n-e-k-o"}`**，所以任何声明项都会被 vendor —— 这正是 onnxruntime 那条注释的由来。
  - `pyproject.toml`：`dependencies` 加 `scipy>=1.13,<2`（安装包已 95.5 MB，vendor scipy 后约 155~175 MB）。
  - `DEPENDENCIES.json`：`"scipy": "1.17.1"`。**版本受 py311 约束**：`scipy 1.18.1` 的 `Requires-Python` 是 `>=3.12`，而本包目标是 **CPython 3.11**（`-windows-x64-py311`），因此 py311 上可解析的最新线是 **1.17.x**（宿主 `N.E.K.O\.venv` 实测 1.17.1：`Requires-Python >=3.11`、`numpy>=1.26.4,<2.7`，与 vendor 的 numpy 2.4.6 相容）。开发 `.venv`（py3.12）装的是 1.18.1，二者只差 `spsolve` 之外的边角，`_solve_sparse` 用到的 `csc_matrix`/`spsolve` API 稳定。
  - 残留风险：插件在宿主进程内运行，宿主本身已 import scipy 1.17.1 ⇒ 进程里可能存在两份 scipy 模块。与 numpy（宿主 1.26.4 / vendor 2.4.6）同构，属既有模式；scipy 无 onnxruntime 那种 `DllMain 1114` 问题，风险等级低于 onnxruntime。
  - 待办：`vendor/` 目前是空的（本地未跟踪、构建前才装），**下次 `build.bat` 之前需把运行依赖（含 scipy）装进 `vendor/`**，`DEPENDENCIES.json` 由 `build_neko.py` 从 vendor 的元数据自动重写。
- ⚠️ 上述**全部是离线回放结论**，尚未在在线实例上复测。在线复测方法见下。

## 六、下一步（按收益排序）

1. **`_edge_jacobian_analytic` 的原语级优化**（收益最大、风险最高）：
   目前 1 718 µs/边，其中 ~85% 是 18 次 `se3_log`（82.7 µs/次，由 numpy 微矩阵调用开销主导，`skew()` 单独就要 3.9 µs）。
   把这几个 SE(3) 原语改成纯 Python float 运算，预计再降 5–15× ⇒ `optimize` 15.8 s → ~2 s。
   风险：属于 core 数学，必须复用 4.1 那套校验（exp/log 往返 + 雅可比对参考差分）。
2. **在线剩余大头**：`track_local` 110 ms、`relocalize` 208 ms（157 次）、`keyframe` 48 ms、`detect` 12 ms。
   `relocalize` 次数多说明丢跟踪频繁 —— 与上一轮"`max_jump_rotation_deg=35°` + 5 Hz 下转头必然丢跟踪"的假设相互印证，值得单独查。

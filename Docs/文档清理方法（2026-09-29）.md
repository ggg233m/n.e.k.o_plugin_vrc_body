## 零、核心原则

> **仓库是权威，文档不是。** 文档说 X，就去代码里看 X 是否成立。
> 文档之间打架时，**不要问哪份文档对**，去问代码。

这条不是口号。本次清理里，凡是"我认为"的推断，**两次被仓库既有事实推翻**
（一次是 1.428× 内参"矛盾"，一次是 playspace 速度假设）。

---

## 一、阶段 1：建立"真值集"——从文件系统，不从别的文档

**产出最高、零判断成分的一招。**

```powershell
# 思路：把文档提到的每个 *.py 文件名，与仓库里实际存在的 basename 做差集
# 实现见 research/tools/doc_health.py --refs
```

- 文档提到 **798 个 `*.py` 提及** → 对 **2717 个实际文件** → **48 个不存在**
- 同一招用在 `backend/*.py` 上，一次捞出 **11 个被文档当作"活跃"却全仓不存在的模块**

**为什么有效**：存在性**可判定**，而"这个说明对不对"不可判定。
先把可判定的部分清掉，剩下的才是需要读代码的。

---

## 二、阶段 2：区分「已删除 / 已迁移 / 从未存在」

同一个"不存在"，成因不同，**修法完全不同**：

| 判据 | 结论 | 修法 |
|---|---|---|
| 有**孤儿 `.pyc`**（且 `cpython-311` + `312` 两版都在） | 曾经存在、**后被删除** | 标"针对已删除实现"，不改路径 |
| `importlib.util.find_spec()` 返回 `False` | 孤儿字节码**无害**（Py3 不把 `__pycache__` 当模块源） | 垃圾而非隐患，可清理 |
| 同名文件在 `research/` 或别处 | **已迁移** | 改路径 |
| 全仓无同名、无 `.pyc` | **从未存在**（或文档引用有误） | 标失效引用 |

**这一步改变结论**：14 个模块是**被删除**的 ⇒ 那些 09-23～09-25 的报告
把它们当"当前实现"写，**在当时是对的** ⇒ 不该说它们"写错了"，
而该标"针对已删除实现，不等于现状"。

---

## 三、阶段 3：按**类别**修，不逐条修

| 类别 | 处理 | 理由 |
|---|---|---|
| **可执行命令里的路径** | **就地改正** | 命令路径不是实验结论，写错直接让人跑失败 |
| **叙述性引用** | **只加顶部日期化横幅，正文一字不动** | 这些是**日期化实验记录 = 证据**，改写等于销毁证据 |
| **结论已被取代** | 横幅必须写成**本文专属**，不能用通用话术 | 通用横幅「不影响本文的实验结论」对 **5 份**文档是**假的** |

**横幅用脚本插入**，不手工转写 —— 这些文件名含中文全角字符，
经控制台管道会乱码（实测连 `repr()` 都逃不过）。用内存里的精确字符串。

---

## 四、阶段 4：不只清症状，去找**漂移的原因**

清到一半发现所有路径问题同源：一次**迁移**。顺着查下去，发现迁移**打断了编排器**：

```
map_from_capture.py:  _run("scale_calib.py")  →  HERE/scale_calib.py
HERE = .slam_probe/offline_probe/recorder/     ← 该文件已迁到 research/recorder/
_step() 用 except Exception 捕获 → 只记 status=failed，流水线"看起来跑完了"
```

⇒ **静默降级**：两个步骤必然失败，下游连带跳过，最后交出一个"跑完了"的 manifest。

**还有一处独立缺陷**：`REPO_ROOT = HERE.parents[3]` 指错一层。
**没有靠数 `parents` 推**，而是写脚本实测 —— 算错方向会让整份修复都错。

然后读**历史 manifest** 判断流水线当年能否跑通，并诚实标注：
它**证明不了**何时坏的（09-20 那次复用了 run 内已有报告，没走这条路径）。

## 五、阶段 5：建单一入口 + 冲突登记表

**横幅是局部的**。agent 打开任意一份文档，不知道别的文档被更正过。

所以建 `Docs/README.md`：**优先级规则 + 权威矩阵 + 冲突登记表 + 全部文档状态总表**，
接成四向闭环（根 `README` ↔ 索引 ↔ 勘误清单 ↔ `ROADMAP`）。

**冲突要分类，因为危险程度不同**：

| 类型 | 特征 | 危险度 |
|---|---|---|
| **真矛盾**（两条不能同真） | 会让人起疑 | 中 |
| **旧断言未撤** | 已修或已标注即可 | 低 |
| **同词异指**（两条都对，但说的不是一回事） | **看起来两条都对** | **最高** |

本次 15 组里 **6 组是同词异指**，真矛盾只有 4 组。
**同词异指才是最能把 agent 绕进去的**：它不会触发怀疑。

> 📌 **2026-10-04 追记**：这句话至今成立，而且**又多了两类**——
> ① **「定位失效」**（新增 C20）：行号漂了，agent 跳过去读到无关代码，**却不觉得自己错了**，
> 这是同词异指的极端形态——**"看起来像结论的句子，其实根本不是结论"**；
> ② **「代码默认 vs 发行配置」**（新增 C19）：同一个键两个值，不问第四个问题就会取错。
> 登记表现为 **20 组**，分类见 `Docs/README.md` §三元结论。

## 六、五条教训（都付出了代价）

| 教训 | 具体代价 |
|---|---|
| **搜索要覆盖全部文件类型** | 第一次清假断言只搜 `*.py`，**漏掉 `README.md`** |
| **同一错误要用不同表征各搜一遍** | 按 `reason_code` 搜到 3 处，按**字面短语**再搜才捞出另外 2 处 |
| **自动审计只产候选，不是结论** | 报了 `body_freeze`/`body_sequence` "不存在"，**实为误报**（面板专属，本就不在 LLM 工具表里）；"深度""重定位"两组候选冲突也全是误报 |
| **动笔前先查本仓库有没有规定过改法** | 假断言我改成**无条件断言**，而 `可行性评估.md:214` 早写了「**只能改成"深度可用时"的条件句**」—— 我正好犯了它预警的反向错误 |
| **改完要扫全量，不只扫自己碰过的文件** | 正因如此才扫出 `丢跟踪根因…md` 那处**既有**的 markdown 失衡（167 个 `**` 为奇数） |

## 七、调试自己的脚本：`faulthandler` 定栈

写 `doc_health.py` 的 `--refs` 时它**卡死**。profile 显示每一步都很快（读码仅 3.4s），
说明是**挂住**而不是慢。用 `faulthandler` 25 秒后打印栈，直接定位到行号：

```python
import faulthandler, runpy, sys
faulthandler.dump_traceback_later(25, exit=True)
sys.argv = ["doc_health.py", "--refs"]
runpy.run_path("research/tools/doc_health.py", run_name="__main__")
```

⇒ 病因：`all_code += p.read_text(...)` 在 **4000+ 个文件**上循环累加，
是 **O(n²) 的字符串拷贝**（≈120 GB memcpy）。
改成 `list` + `"".join()`，并把范围收窄到插件面 ⇒ **3.2s**。

**教训**：脚本"慢"和"挂"要用不同手段查；**别用 profile 猜，直接看栈**。

### 附：同日第二次调试 —— 门禁抓到了**工具自己的误报**

写完工具后跑门禁，它报**我新写的方法文档本身** `**` 失衡（173，首个奇数行 L119）。
去看那一行：

```
| **改完要扫全量** | ……那处**既有**的 markdown 失衡（167 个 `**` 为奇数） |
```

**那是行内代码里的 `` `**` `` —— 反引号内的星号不构成加粗。** 工具把代码 span 也数进去了。

**修法选择**：**改工具，不改文档**。
- 若改文档（把 `` `**` `` 换个写法），工具下次照样对**任何讲解 markdown 语法的文档**误报；
- 改工具（先剔除围栏代码块与行内代码 span，用空串占位以保持行号）才治本。

改完后同一份文档通过；而 `丢跟踪根因…md` 的计数从 **167 → 165**
（少了 2 个原本藏在行内代码里的星号）—— **更准了**，说明剔除是必要的。

> **这一条本身就是 §六 第 3 条教训的实例**：自动审计只产候选。
> 门禁报了 FAIL，正确的下一步是**去看那一行**，而不是去改被报的文档。
> 另外：**修工具时用空串占位、不要删行**，否则行号全错位，定位信息就废了。

## 八、刻意**没做**的事

- **不改写历史报告的结论** —— 只加日期化更正，保留证据
- **不猜作者意图** —— `丢跟踪根因…md` 的 markdown 失衡有两种都说得通的改法，**报告不选**
- **改 gitignore 目录里的代码前先同名备份**并校验 SHA-256（那里没有 git 回退网）
- **不为 29 份文档各加状态行**，而用单一索引 —— 编辑面越小越安全
- **不声称穷尽** —— 只做了四类横向扫描（路径／数值／状态／同词异指），
  **没有逐行读**；这一点在 `Docs/文档勘误与过时清单（2026-09-29）.md` §7.6 写明

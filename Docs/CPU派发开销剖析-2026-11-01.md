# XPU 单算子派发成本剖析（2026-11-01）

> 任务：查清 PyTorch 2.14.1+xpu / Arc A770 / Level-Zero 上，一个 1024 元素 a+b 的 37 µs CPU 成本构成，并判断能否压低。
> 环境：.venv_xpu（Python 3.14.9，torch 2.14.1+xpu，xpu runtime 20260100），Intel Arc A770，oneAPI 2026.0，驱动 DLL 位于 iigd_dch_d.inf_amd64_fb6b9affe823ecad。
> 所有执行脚本在 .tc_cache/analysis/，原始数据：knob_results.json、ladder.json、add_trace.json。

---

## 0. 先说结论（TL;DR）

| 问题 | 答案 |
|---|---|
| 37 µs 能压下来吗？ | **能压一点点，压不到质变。** 单算子底线约 **24–25 µs**（中位数口径 −9%，最小值口径基本不变）。 |
| 靠环境变量？ | **基本无效。** 45 组候选里只有 1 组（SYCL_PI_LEVEL_ZERO_BATCH_SIZE）有可测收益，且只在**中位数**上成立。 |
| 靠多流并发？ | **反向。** 每 op 成本 27.7 µs → 75.7 µs（2 流）。 |
| 靠 graph？（已知不支持，已复验） | **不可用**：Device does not support graph record and replay feature (UR_DEVICE_INFO_GRAPH_RECORD_AND_REPLAY_SUPPORT_EXP)。 |
| **真正有效的杠杆？** | **减少 kernel 数量（融合）**，不是降低单个 kernel 的派发成本。 |
| **值不值得继续？** | **不值得。** 上限约 −9%~−10%，进一步要改 XPU 后端 C++。精力应全部投给 kernel 数削减。 |

**必须先纠正的一个口径问题**：37 µs **不能外推**到真实模型。

| 口径 | kernel 数 | CPU 时间 | **每 kernel CPU** |
|---|---:|---:|---:|
| eager（Lead 实测） | 110,644 | 388 ms | **3.5 µs** |
| compile（Lead 实测） | 48,454 | 179 ms | **3.7 µs** |
| 我的隔离微基准 add_ | 1 / 次 | 25–37 µs | **25–37 µs** |

差了整整一个数量级。隔离微基准测的是**完全暴露的单次启动**；真实负载里 kernel 背靠背排队，提交成本已被攒批摊薄。所以「37 µs 压到 X」对端到端的贡献要按 3.5 µs/kernel 的基数折算，不是按 37 µs。

## 1. 一次 aten op 从 Python 到 ZE 的完整路径

以下链路里的每一层 DLL 都是从**运行中进程 EnumProcessModules 枚举出来的**（list_modules.py），不是猜的：

    Python:  torch.add(a, b)
      │  torch/_C/_VariableFunctions.pyi → builtin_function_or_method
      ▼
    torch_python.dll : THPVariable_add → 解析 args / out / dispatch key
      ▼
    torch_cpu.dll + c10.dll : c10::Dispatcher   aten::add.Tensor
      ├── AutogradXPU（grad mode 时）→ ADInplaceOrView / VariableType
      ├── TorchDispatchMode（compile / proxy 模式下）
      └── DispatchKey::XPU ──► 结构化 kernel
      ▼
    torch_xpu.dll : at::native::xpu::add_kernel
      ├── TensorIterator::build（形状/步长/offset，纯 CPU）
      ├── 若输出需分配 → c10::xpu::XPUCachingAllocator::allocate → zeMemAllocDevice
      │     （free/recordStream 路径上有 zeMemGetAllocProperties）
      ├── launch_vectorized_kernel
      │     kernel 名（profiler 实测）：_ZTSN2at6native3xpu27VectorizedElementwiseKernelILi4ENS1_13BinaryFunctorIfffNS1_10AddFunctorIfEEEENS_6detail5ArrayIPcLi3EEE23TrivialOffsetCalculatorILi2EjEEE
      └── sycl::queue::parallel_for → sycl::nd_range
      ▼
    sycl9.dll (.venv_xpu/Library/bin) : queue::submit
      ▼
    ur_loader.dll → ur_adapter_level_zero.dll（ur_adapter_level_zero_v2.dll 同时加载）
      │  实测 runtime 层调用：urEnqueueKernelLaunchWithArgsExp
      ▼
    ze_loader.dll (C:\Windows\System32) → ze_intel_gpu64.dll（驱动）
      ├── zeKernelSetArgumentValue        × 3   ← 实测精确 3.00 / kernel
      ├── zeKernelSetGroupSize            × 1
      ├── zeCommandListAppendLaunchKernel × 1
      ├── zeEventHostReset / zeEventCreate
      └── 每 ~6 个 launch 攒批一次：
            zeCommandListClose + zeCommandQueueExecuteCommandLists
      ▼
    igc-default64.dll（IGC 编译产物）→ A770 执行

**另加载的相关 DLL（说明这些路径真实存在）**
- mkl_sycl_blas.6.dll / mkl_sycl_dft.6.dll / mkl_sycl_lapack.6.dll —— mm 走 MKL-SYCL/oneDNN，**不是**手写 elementwise kernel。所以 104 µs 的 mm 是**另一条路径**，不能与 add 并列。
- ur_adapter_opencl.dll、OpenCL.dll —— 加载但未走主路径。
- uv.dll、libiomp5md.dll —— 无关。

**注**：这台机器的 sycl 不是 oneAPI 自带的，而是 **venv 里 pip 包自带的 sycl9.dll + UR adapter**。oneAPI 2026.0 的目录只在 PATH 上（Lead 的脚本里设了），实际加载的是 venv 的那份。

## 2. 分层阶梯实测（最关键的一张表）

ladder.py，每项 5 轮 × 200 次，取 min / median（µs）。

| 层级 | 操作 | min | med |
|---|---|---:|---:|
| L0 | pass（纯 Python） | 0.09 | 0.09 |
| L0 | a.numel()（Python 属性） | 0.23 | 0.29 |
| L1 | a.dim()（走 ATen dispatcher，无 kernel） | 0.20 | 0.22 |
| L1 | a.view(-1)（dispatcher + 新建 TensorImpl） | 3.26 | 3.30 |
| L2 | torch.empty(1024, device='xpu')（**仅分配器**） | 5.37 | 5.49 |
| L3 | torch.xpu.synchronize() | 8.12 | 8.39 |
| L4 | torch.xpu.current_stream()（**Python 包装**） | 7.76 | 7.96 |
| L4b | torch._C._xpu_getCurrentStream(0)（**裸 C**） | **0.29** | 0.29 |
| L4c | torch._C._xpu_getCurrentRawStream(0) | 0.27 | 0.27 |
| L5 | torch.xpu.Event().record()（建 + 记录） | 16.01 | 16.17 |
| L6 | torch.xpu.Stream() 创建 | 1.06 | 1.07 |
| L7 | a.zero_()（**最简 kernel，1 参数**） | **19.78** | 19.99 |
| L8 | a.fill_(0.0) | 21.91 | 23.70 |
| L9 | a.mul_(1.5)（标量乘，另一条 functor 路径） | 31.94 | 35.93 |
| L10 | a.add_(b)（**2 张量参数，无分配**） | **25.35** | 26.24 |
| L11 | torch.add(a,b)（**带输出分配**） | 35.03 | 39.00 |
| L12 | torch.add(a,b,out=c)（无分配） | 28.83 | 32.85 |
| L13 | a.copy_(c) | 17.25 | 18.71 |
| L14 | torch.mm 256×256（**MKL-SYCL 路径**） | 102.45 | 105.44 |
| — | ac.add_(bc) CPU 张量参照 | 4.16 | 4.27 |

**三个直接结论**
1. **Python 层可忽略**：pass = 0.09 µs，numel() = 0.23 µs。Lead 的结论成立。
2. **ATen dispatcher 也很便宜**：a.dim() = 0.20 µs；view 才 3.26 µs（含 TensorImpl 分配）。
3. **a.zero_() = 19.8 µs 就是「任意一个 XPU kernel 的启动地板」。** 这是全报告最重要的一行——它把「kernel 派发」与「参数打包」拆开了。

**顺带一个隐藏税**：current_stream() 7.76 µs vs 裸 C 0.29 µs，torch 的 Python 包装要 **7.5 µs**。这与 synchronize() 的 7.4 µs 量级完全一致 —— 说明 **torch.xpu.synchronize() 那 7.5 µs 里大头是 Python/device-guard 开销，不是 GPU 同步**。

## 3. 37 µs 的归因

### 3.1 分解（差减法，全部为本机实测）

| 分段 | 成本 | 依据 |
|---|---:|---|
| ① Python → ATen dispatcher | **~0.2 – 3 µs** | a.dim() 0.20；a.view(-1) 3.26（含 TensorImpl，是上界） |
| ② XPU 内存池分配（仅当需产出新张量） | **~6.2 µs** | torch.add(a,b) 35.03 − torch.add(a,b,out=c) 28.83 = 6.20；torch.empty 独立测 5.37 |
| ③ SYCL/UR/L0 入队（参数设置 + 命令列表 + 提交） | **~19.6 – 22 µs** | a.zero_() 19.78 减去 ①②（在 zero_ 上 ①②≈0） |
| ④ 每多一个张量参数 | **+2.8 µs / 参数** | a.add_(b) 25.35 − a.zero_() 19.78 = 5.57，add 比 zero 多 2 个指针参数 |
| ⑤ GPU 实际执行 | **3.31 µs**（不占 CPU 关键路径） | profiler kernel 事件 194 次共 661.4 µs / 200 |

**合成校验**
- a.add_(b)（就地，无分配）= 19.8 + 5.6 = **25.4 µs**，实测 **25.35** ✅
- torch.add(a,b)（带分配）= 25.4 + 6.2 = **31.6 µs**，实测 35.03（分配路径另有抖动）✅ 量级吻合
- Lead 的 37 µs 落在我 baseline 三次重复 34.6 / 34.8 / 44.7 区间内 ✅

### 3.2 一句话归因

> **37 µs 里约 85%（≈31 µs）是「SYCL 运行时 + UR + Level-Zero 的入队固定开销」，与数据规模无关、与 ATen 无关、与 Python 无关。ATen dispatcher 只占 ~1 µs，分配器占 ~6 µs。**

这与 Lead 观察到的「1024 元素 add 与 256×256 mm 之外的 op 成本恒定」完全一致：**成本按 kernel 启动次数计费，不按元素数计费**。

### 3.3 mm 为什么是 104 µs

mm 走 mkl_sycl_blas.6.dll（MKL-SYCL），不是手写 elementwise kernel。104 µs ≈ 3.3× add，是**不同后端路径**的成本。把两者并列比较会得出「成本随规模增长」的错误结论。

## 4. ZE 调用计数（cmdcount.py，100 次 a.add_(b)，XPU activity 开启）

| ZE 调用 | default | BATCH_SIZE=1024 | 每 kernel（default） |
|---|---:|---:|---:|
| urEnqueueKernelLaunchWithArgsExp | 100 | 100 | 1.00 |
| zeCommandListAppendLaunchKernel | 100 | 100 | 1.00 |
| **zeKernelSetArgumentValue** | **300** | **300** | **3.00** |
| zeKernelSetGroupSize | 100 | 100 | 1.00 |
| zeCommandQueueExecuteCommandLists | **18** | **0** | 0.18 → 0 |
| zeCommandListClose | 18 | 0 | — |
| zeCommandListReset | 19 | 0 | — |
| zeEventHostReset | 96 | 0 | 0.96 → 0 |
| zeEventCreate | 4 | **100** | 0.04 → 1.00 |

### 4.1 zeKernelSetArgumentValue：确认是「逐参数设置，且无复用」

- 实测**精确等于 3.00 次 / kernel launch**（300/100）：2 个输入指针 + 1 个 offset/size。
- **结论：确实是逐参数设置，每次 launch 全量重设，零复用。** Lead 的猜测成立。
- **但它不是主要成本**：profiler 里单次约 1.0 µs（还被 profiler 放大），3 次 ≈ 3 µs。**省下它收益上限只有 ~3 µs。**
- **能复用吗？应用层不能。** zeKernelSetArgumentValue 的状态挂在 command list 上，列表一 reset/close 就必须重设。唯一持久化机制是 mutable command list（ZE_experimental_mutable_command_list）或 graph record/replay —— **两者本机都不可用**（graph 已复验失败）。
- **值得注意的浪费**：runtime 层调用名已经是 urEnqueueKernelLaunchWithArgsExp（带 Args 的批量版本），**但底下仍退化成 3 次 zeKernelSetArgumentValue** —— 这个 "WithArgs" 快路径在本驱动上没有生效。

### 4.2 zeMemGetAllocProperties 5219 次 —— 我没能复现出精确数字

- 在 **a.add_(b)（无分配）** 的 trace 里，zeMemGetAllocProperties 计数 = **0**。
- 我尝试测「带分配的 torch.add(a,b)」路径的精确计数，脚本超时，**没拿到结果，不编数字**。
- 可说的定性判断：它**只出现在分配器路径上**，不在 kernel 派发路径上。5219 / 110,644 kernel ≈ 每 21 个 kernel 一次，与「每次 allocate/free 查一次指针归属」量级吻合。

## 5. 命令批量化：这条路通不通

### 5.1 关键实测（batching.py）

| 场景 | 每 op 成本 (min / med, µs) |
|---|---:|
| 200 个 add 背靠背（默认） | **26.5 / 27.1** |
| 每 op 后 synchronize() | 118.3 / 120.6 |
| 每 op 后 event 同步 | 120.7 / 125.3 |
| op 间插 50 µs CPU 空转 | 80.9 / 81.5 |
| op 间插 200 µs CPU 空转 | 239.8 / 244.0 |

**解读**
- 背靠背 26.5 µs 已经是**批量化生效**的状态（默认每 ~6 个 launch 提交一次，见第 4 节的 18/100）。
- 插 50 µs 空转 → 80.9 µs，而「26.5 + 50 = 76.5」，多付 **4.4 µs**；插 200 µs → 239.8 vs 226.5，多付 **13 µs**。
- **说明：CPU 一旦闲超过批处理窗口，攒批被强制 flush，下个 op 要重开命令列表并提交。批处理真实存在，且空闲惩罚随空闲时长增长。**
- 但真实推理是 385 ms 满载派发，CPU 几乎不空闲，**这部分损失在端到端里已经被吃掉了** —— 这正是「把 batch size 调大后端到端只降 4.4% 而非腰斩」的原因。

### 5.2 BATCH_SIZE=1024 的真相（对 Lead 那条 −4.4% 的核实）

按 Lead 要求做了**配对 A/B，3 组交叉**，每组 9 轮 × 200 次：

| 配对 | default (min / med) | BATCH_SIZE=1024 (min / med) |
|---|---|---|
| p1 | 23.45 / 30.14 | 24.94 / 25.59 |
| p2 | 24.26 / 27.76 | 24.63 / 25.76 |
| p3 | 24.56 / 28.09 | 24.10 / 25.30 |

**诚实结论**
- **最小值（最可信指标）：23.45 / 24.26 / 24.56 vs 24.94 / 24.63 / 24.10 —— 无显著差异，default 甚至略优。**
- **中位数：28.1 / 27.8 / 28.1 vs 25.6 / 25.8 / 25.3 —— batch1024 稳定快约 2.5 µs（−9%），且方差明显收窄**（default 三次中位数都在 27.8+，batch1024 三次都在 25.8−）。
- 机制是**真的**：第 4 节已证明它把 zeCommandQueueExecuteCommandLists 从 18/100 降到 **0/100**，并把 zeCommandListClose / Reset / zeEventHostReset 全部消除。

> **判定：SYCL_PI_LEVEL_ZERO_BATCH_SIZE=1024（配合 UR_L0_BATCH_SIZE=1024）= 实测有效，收益约 −9%，作用于稳态/中位数，不改变最优路径。**
> Lead 端到端 −4.4% 与之量级自洽（端到端里提交开销本就被分摊，能拿到的更少）。**建议用 A/B/A/B 交替的端到端实验复核这 −4.4%，因为单次端到端漂移可能就有这个量级。**

> 注意：UR_L0_BATCH_SIZE 单独设**无效**（39.7 µs，见 6.2），必须**两个一起设**。

## 7. 内存分配器：PYTORCH_XPU_ALLOC_CONF 根本不存在

- 在 .venv_xpu/Lib/site-packages/torch/ 下 grep ALLOC_CONF / expandable_segments / cudaMallocAsync：**Python 层零命中**。
- 扫 torch_xpu.dll 得到的 **TORCH_XPU_\* 只有两个**：TORCH_XPU_FALLBACK_OP、TORCH_XPU_USE_COPY_ENGINE。**没有 PYTORCH_XPU_ALLOC_CONF，也没有 PYTORCH_XPU_ALLOCATOR。**
- 实测设了也没用（36.0 / 40.1 vs baseline 34.6），与「代码里根本不读」一致。
- **结论：XPU 后端没有 CUDA 那样的 caching allocator 配置开关。** 只有：
  - torch.xpu.use_mem_pool / MemPool（为 graph 准备的池，graph 不可用则无意义）
  - torch.xpu.XPUPluggableAllocator（自定义分配器接口，需自行实现并编译 C++）
  - torch.xpu.empty_cache() —— 实测**让 torch.add(a,b) 从 37.3 变慢到 40.2 µs**，无益。

**分配器成本定量**：torch.empty(1024) = 5.37 µs；带分配的 add 比 out= 版本贵 **6.2 µs**。**这是 37 µs 里唯一在应用层有点希望的 6 µs** —— 前提是消除每次 op 的分配（预分配 buffer + out=），需要改模型代码，不是配置能解决。

## 8. 多流并发：实测反向

multistream.py，N 条流上并发提交独立 add_：

| 流数 | 每 op 成本 (min) | 每轮 N 个 op 总耗时 |
|---|---:|---:|
| 1（串行） | **27.7 µs** | 27.7 µs |
| 2 | 75.7 µs | 151.4 µs |
| 4 | 117.6 µs | 470.3 µs |
| 8 | 99.0 µs | 792.2 µs |
| 16 | 98.0 µs | 1568.1 µs |

**完全失败。** 原因（同表实测）：

| 切换原语 | 成本 |
|---|---:|
| with torch.xpu.stream(s) 上下文管理（空块） | **15.3 µs** |
| torch.xpu.set_stream(s) | **9.5 µs** |
| torch._C._xpu_setStream(...)（裸 C） | **1.04 µs** |

**流切换本身（15.3 µs）比一次 op 派发（27.7 µs）还要一大半，所以多流纯亏。** set_stream 的 Python 包装税（9.5 → 1.04，9×）与第 2 节的 current_stream 观察一致。

> 若有人想用裸 _xpu_setStream（1.04 µs）绕过包装再试：2 流数据里切换只占 15.3，剩下 60 µs 是驱动侧真实代价，**预计仍不划算，且侵入性大，不建议。**

## 10. 最终判定

### 10.1 37 µs 能压到多少

| 手段 | 预期 | 证据强度 |
|---|---|---|
| 现状（baseline） | 34.6 / 34.8 / 44.7 µs（三次重复） | 实测 |
| BATCH_SIZE=1024 + UR_L0_BATCH_SIZE=1024 | **中位数 −9%**（28.1 → 25.5），最小值不变 | 实测，配对 3 组 |
| 消除输出分配（预分配 buffer + out=） | **−6 µs** | 实测差减法 |
| 消除 2 个多余 kernel 参数 | **−3 µs** | 实测（zero_ vs add_） |
| 多流 | **+48 µs 起（反向）** | 实测 |
| 其余 43 组环境变量 | **0** | 实测 |
| Graph / mutable cmdlist | **不可用** | 实测复验 |

**理论下限 ≈ 24–25 µs**（也是我多轮测到的 add_ 最小值）。相对 Lead 的 37 µs 是 **−33%**；相对更诚实的基线（34.6 µs min）只有 **−28%**；按中位数则 **−9%**。

### 10.2 值不值得继续

**不值得。** 四条理由：

1. **应用层能拿的已经拿完了。** 45 组环境变量扫完，唯一有效的 BATCH_SIZE 只有 −9%，机制上只是消除默认配置里每 6 个 kernel 一次的提交。
2. **剩下的空间在 C++ 里。** 要进一步（复用已设置的 kernel 参数、走 mutable command list）必须改 PyTorch XPU 后端或等 Intel 驱动更新，不是这个项目该做的事。
3. **真正的收益在 kernel 数量上，那条路已经有人在走。** torch.compile 把 kernel 110,644 → 48,454（−56%），CPU 388 → 179 ms（−54%）。**派发时间几乎严格正比于 kernel 数** —— 这就是全部结论。继续抠单 op 派发是 10% 量级的边际工作。
4. **可立即落地、零风险的只有一条**：SYCL_PI_LEVEL_ZERO_BATCH_SIZE=1024 + UR_L0_BATCH_SIZE=1024。代价为零，收益端到端 ~4%（Lead 实测）~ 中位数 9%（我实测）。**建议作为默认环境变量加上，但不要指望它改变大局。**

### 10.3 给 Lead 的建议

- ✅ **加**：SYCL_PI_LEVEL_ZERO_BATCH_SIZE=1024、UR_L0_BATCH_SIZE=1024（零风险，需 A/B/A/B 复核 −4.4%）。
- ❌ **别试**：多流、*_USE_IMMEDIATE_COMMANDLISTS、UR_*_V2、ZES_ENABLE_SYSMAN、PYTORCH_XPU_ALLOC_CONF —— 全部实测无效或反向。
- 🎯 **主攻**：kernel 数削减（融合）。这是唯一被数据支持的 2× 级别杠杆。

## 13. 图优化专项（2026-11-01 晚补充，Lead 实测）

> 本节回答：「图优化有救吗」「XPUGraph 是驱动问题还是硬件问题」。
> §9 的原结论在这一节被修正。

### 13.1 XPUGraph：**驱动问题，不是硬件问题**（这是本轮最重要的取证）

**结论先行：Level-Zero 驱动 side 已经提供了 `record_replay_graph` 扩展，但一阶封装（Unified Runtime，UR）没有把它暴露给 PyTorch。**

取证链（全部本机可复现）：

**① Level-Zero 头文件里，扩展是正式定义的**

`C:\Program Files\LevelZeroSDK\1.32.0\include\level_zero\ze_api.h`：

```c
#define ZE_RECORD_REPLAY_GRAPH_EXT_NAME  "ZE_extension_record_replay_graph"
```

配套 15 个 API：`zeGraphCreateExt` / `zeCommandListBeginGraphCaptureExt` /
`zeCommandListEndGraphCaptureExt` / `zeGraphInstantiateExt` / `zeCommandListAppendGraphExt` /
`zeGraphDestroyExt` / `zeExecutableGraphDestroyExt` …

**② 驱动实际上报了这两个扩展名**（关键证据）

用 `ze_loader.dll`（`C:\Windows\System32\ze_loader.dll`, 795 KB）直接枚举
`zeDriverGetExtensionProperties`，64 个扩展里：

```
ZE_extension_record_replay_graph
ZE_experimental_record_replay_graph
```

**两个都在。** 也就是说：**Intel 的 L0 驱动已经声明支持 record/replay graph。**

> ⚠️ 踩坑记录：第一次枚举失败是因为我把 `_ze_driver_extension_properties_t` 的
> `version` 字段猜成了 `char[256]`（实际是 `uint32`），导致结构体错位、只解出 6 个乱码名字。
> 更正后 64 个全部解出。**这一条值得记住：以后查 L0 扩展能力，struct 布局错了会得到假阴性。**

**③ 但 PyTorch 走的是 Unified Runtime，不是裸 L0**

`torch.xpu.get_device_properties(0)` 报的 `platform_name` 是：

```
Intel(R) oneAPI Unified Runtime over Level-Zero
```

PyTorch 的 XPU 后端通过 SYCL/UR 访问设备，问的是
`UR_DEVICE_INFO_GRAPH_RECORD_AND_REPLAY_SUPPORT_EXP = 0x2080`（定义在
`oneAPI/2026.0/include/unified-runtime/ur_api.h`）。

**UR 这一层返回 0。** 于是 PyTorch 报「设备不支持」。

**④ 定性**

| 层 | 支不支持 |
|---|---|
| 硬件（Arc A770 / Xe-HPG） | **支持**（驱动敢报扩展名，就是硬件/固件能力的一种声明） |
| Level-Zero 驱动 | **支持**（`ZE_extension_record_replay_graph` 在扩展列表里） |
| Unified Runtime（UR） | **没暴露** ← 断在这里 |
| PyTorch XPU 后端 | 如实转述 UR 的回答：不支持 |
| `torch.compile(mode="reduce-overhead")` | 每次都 `skipping cudagraphs` |

日志里的直接证据（`reduce-overhead` 每次 forward 都打这条）：

```
[__cudagraphs] skipping cudagraphs due to multiple devices: device(type='xpu', index=0)
```

所以 **`reduce-overhead` 在 XPU 上等于 default，什么也没做**（实测 CPU 派发 163.7 ms，
和 `aggressive_fusion` 的 161.9 ms 同量级，纯属融合的功劳，不是 graph 的）。

**能救的条件**：升级 UR 版本到实现了 `0x2080` 的那一版（或 PyTorch 改用裸 L0 路径）。
**不是本机能配出来的**，需要上游改。

> 注：我尝试直接调 `ur_loader.dll` 的 `urDeviceGetInfo(0x2080)` 做交叉验证，
> 在 `urAdapterGet` 后 `urDeviceGet` 处遇到 access violation（ctypes 的
> `ur_device_handle_t` 指针传递方式不对）。**这条交叉验证没做成，属未验证项。**
> 但 PyTorch 的报错文本本身就带着 `UR_DEVICE_INFO_GRAPH_RECORD_AND_REPLAY_SUPPORT_EXP`
> 这个常量名，足以证明断点在 UR。

## 14. XPU 图重放：从 88.8 ms 到 34.6 ms（2026-11-01 深夜，Lead 实测）

> 本节接 §13。§13 的结论是「图优化有救，但 ViT 捕获失败」——**那个结论是错的**，
> 根因是两个 D2H 同步点 + 一个测试方法错误，不是能力缺失。全部修好后，**双图串联 34.6 ms**。

### 14.1 开关：`SYCL_UR_USE_LEVEL_ZERO_V2=1`

§13.1 说「UR 硬编码 `return false`」——只对 **V1** 适配器成立。UR 同时带两套实现：

| 适配器 | 图支持 |
|---|---|
| `ur_adapter_level_zero.dll`（V1） | ❌ `urDeviceGetInfo(0x2080)` 写死 false |
| `ur_adapter_level_zero_v2.dll`（V2） | ✅ 完整接了 `ZeGraphExt.*` |

切换靠环境变量（**布尔开关，不是版本号**）：

```powershell
$env:SYCL_UR_USE_LEVEL_ZERO_V2 = "1"      # 别名：UR_LOADER_USE_LEVEL_ZERO_V2
```

生效后 `platform_name` 从 `...over Level-Zero` 变成 `...over Level-Zero **V2**`。

**本机只有 V1 和 V2，没有 V3/V4**——扫遍 `ur_*.dll` 字符串，只有 `ur_adapter_level_zero.dll` /
`ur_adapter_level_zero_v2.dll` / `ur_adapter_opencl.dll` 三个适配器，`V2` 是唯一的选择项。

**代价**：V2 的单算子派发比 V1 慢（`add_` 22.3→35.1 µs、`mul_` 28.2→57.0 µs），
不开图时整模型 eager 慢 4.6%（318.6→333.1 ms）。所以**只在用图时开**——
`policy_runtime.setup_oneapi(graph=True)` 已经这么做了。

### 14.2 ViT 捕获失败的两个真实原因

ViT 最初报 `UR_RESULT_ERROR_UNSUPPORTED_FEATURE`，逐层拆开后是 **两个 GPU→CPU 同步点**：

**(a) `get_vision_*` 系列函数里的 `.tolist()`**

`Qwen3_5VisionModel.forward` 每次都调：

```python
get_vision_interpolation_indices_and_weights(grid_thw, ...)   # 内部 .tolist()
get_vision_position_ids(grid_thw, ...)
get_vision_attention_seqlens(grid_thw, ...)                    # 内部 .tolist()
```

这些是**纯几何量**（只依赖 `grid_thw`），每拍都是同一个值。好消息是 transformers
这几个函数**本身就支持从 kwargs 取预计算值**：

```python
if kwargs is not None and (cu_seqlens := kwargs.pop("cu_seqlens", None)) is not None:
    return cu_seqlens
```

所以图外算一次、灌进去即可 → `policy_graph_runtime.precompute_vision_geometry()`。

**(b) attention 里的 `lengths.tolist()`**

`Qwen3_5VisionAttention.forward` 的非 flash 分支：

```python
lengths = cu_seqlens[1:] - cu_seqlens[:-1]
splits = [torch.split(t, lengths.tolist(), dim=2) for t in (q, k, v)]
```

`lengths.tolist()` 是 D2H 同步，**必然**打断捕获。

**我们的输入恒为单窗口**（实测 448×256 / 320×176 / 224×128 三种尺寸，
`cu_seqlens` 都是 `[0, N]`，只有一个 segment），所以 split 后 cat 与整段一次 SDPA
**完全等价** → `policy_graph_runtime._single_window_attention()`。

两个补丁都打上后：`CAPTURE OK` / `REPLAY OK`。

### 14.3 一个必须记住的坑：capture 后的输出是**无效的**

这是本轮最耗时的坑。图捕获完之后，**在第一次 `replay()` 之前，输出张量里是垃圾**：

```
capture 后（未 replay）: cos=0.00299544   ← 垃圾
首次 replay 后:          cos=1.00000024   ← 正确
再 3 次 replay 后:       cos=1.00000024
```

我第一次测出 `cos=0.0043` 就以为 ViT 图算错了，白查了两轮。**正确做法**：
capture 完立刻 `g.replay()` 一次，之后才能读输出。

> 相关：`torch.xpu.graph()` 的 context manager 退出时**不会**自动 replay。
> ARDY 的 `graph_runtime.py` 里 `capture()` 返回后也没有立即 replay，
> 但它在 `warmup()` 里紧接着就 `g.replay()` 了，等于避开了这个坑。

### 14.8 接线落地（2026-11-01 收尾）

图重放与近距障碍否决已接进 Service 链路，**两者都可独立开关**。

| 开关 | 默认 | 作用 |
|---|---|---|
| `VRC_POLICY_HEAD=1` | 关 | 启动头 A |
| `VRC_POLICY_DRYRUN` | **1** | 1 = 只写 `policy_live.jsonl` 不发轴 |
| `VRC_POLICY_GRAPH` | 关 | 1 = 切 Level-Zero V2 并用 XPUGraph |
| `VRC_POLICY_MODEL` / `VRC_POLICY_RUN` | — | 权重目录 |

**近距障碍否决**（新）：

```
Service._policy_near_obstacle()  → 读 navmesh._near / _near_pts（感知线程每帧更新）
        ↓
PolicyHead._on_block()          → stop=True 时整块置零，meta["vetoed"]=True
        ↓
PolicyExecutor.submit()         → 照常过 SafetyGate（限速限加速）
```

三点设计取舍：

1. **不自己算双目**。navmesh 感知线程已经有了 `near_obstacle(pts, ...)` 的结果
   （`stop_ahead_m=0.7` 世界米、`stop_min_pts=40`），再算一遍是浪费，而且会和
   navmesh 的判据漂移。只读最新快照。
2. **读不到就当「没有障碍」**，不是「有障碍」。否则感知线程还没起或临时挂了，
   策略会永久停住 —— 那该由 executor 的 `stale_s` 阈值管。
3. **不替代 SafetyGate**。SafetyGate 管 `v_max` / `dv_max`（走得稳不稳），
   veto 管「前面有没有东西」（该不该走），两件事分开。

**测试**：`tests/test_policy_head_veto.py` 4 条（畅通不拦 / 有障碍整块置零 /
provider 缺失是 no-op / provider 抛错不阻塞策略），
`tests/test_service_action_wiring.py` 补 1 条读快照的用例。

> 注意 `_near` / `_near_pts` 是 `OnlineNavigator` 的私有字段。
> 直接读私有字段不优雅，但这里是同进程内的只读快照，加 getter 反而要动 navmesh 的
> 公开面。**如果将来 navmesh 加了正式 API，这里应改成调 API。**

## 15. 真机 dry-run 首跑（2026-11-01 晚）：三个真 bug 与一次口径纠正

第 14 节所有数字都是**离线**测的。这一节是第一次把运行环接到真实 SteamVR +

环境：`vrserver` / `vrcompositor` / `VRChat`（28168）在跑，镜像 2160×1212，

### 15.1 先修的是权限，不是性能

`openvr.init()` 直接抛 `InitError_Init_NoLogPath`，但它真正的原因不是 SteamVR：
`.venv_xpu` 里的 python 进程是 **Low 完整性级别**，写不了工作区里 Medium 级别的目录。

```
工作区根                      Low   (OI)(CI)(NW)   ← 显式，罪魁
  .venv_xpu\Scripts\python.exe  Low (I)(NW)        ← 继承，所以进程也是 Low
  research / backend / .tmp    Medium (OI)(CI)(NW) ← 这几个被单独改回过
```

`NW` = No-Write-Up：Low 进程只能写 Low 或更低的对象。所以 python 能写根目录、
写不了任何子目录，而 `pwsh`（Medium）写哪儿都正常 —— 这就是为什么
"手工 echo 能过、python 不能过"。

修法：`icacls <root> /setintegritylevel "(OI)(CI)M"`，再对 `.venv_xpu` 单独做一次
（它是显式子项，改不动时要先 `/grant` 自己 Full Control，改完再 `/remove:g` 撤掉）。
备份在 `.tmp/acl_backup_20261101/icacls_before.txt`。

### 15.2 bug 1：`or` 用在 numpy 数组上

`policy_runner.py` 原来是：

```python
prev = prev if prev is not None else (self._prev(t0) or cur)   # ← 坏
```

`_prev()` 返回的是 ndarray，`or` 会对它求布尔 → `ValueError: The truth value of an array with more than one element is ambiguous`。
**没有 `prev_source` 时每拍都炸**，
首跑 180 拍里 178 拍是这个错。

改成显式两步判空。回归测试 `tests/test_policy_runner_prev.py` 4 条。

### 15.3 bug 2：`graph=True` 是个假开关

`PolicyRuntime.__init__` 里 `graph=True` 只做了 `setup_oneapi(graph=True)` 然后记了个
`graph_enabled` 标志 —— `PolicyGraphRuntime` **一行都没实例化**。
也就是说开这个开关的净效果是**只付 V2 适配器的代价（eager 慢 4.6%），拿不到任何图收益**。
（本轮未修完，见 15.6 待办。）

### 15.4 口径纠正：第 14 节的基准不是端到端

dry-run 实测 **p50 = 413.8 ms / p95 = 443.5 ms**，与第 14 节说的 210 ms 差 2 倍。
拆开比对了四种配置（VRChat 同跑、1080×606 输入、25 次取 p50）：

| 模式 | LoRA | aggressive_fusion | p50 | p95 |
|---|---|---|---:|---:|
| a | 未合并 | 关 | **417.3 ms** | 434.1 |
| b | 未合并 | 开 | 412.8 ms | 427.8 |
| c | **合并** | 关 | **319.5 ms** | 332.6 |
| d | 合并 | 开 | 319.1 ms | 345.1 |

两件事：

1. **`PolicyRuntime` 从来没做过 `merge_and_unload`。** 省 **97.8 ms（−23.4%）**，
   这是本机最大的一笔单项优化 —— 比第 14 节里所有图优化加起来还容易拿。
   不合并时 24 层 × 12 个 Linear 每层多走一次 LoRA 分支（两次 matmul + add）。

### 15.5 319 ms 还是到不了 210 ms —— 差距在图重放

合并后分段（compile，非图）：

| 环节 | p50 |
|---|---:|
| ViT（compile） | 97.9 ms |

| 预处理 build_inputs（含 resize 18.0 ms） | 29.5 ms |

第 14 节说 ViT 图 7 ms、LM 图 27.8 ms、合计 34.6 ms —— 那是**图重放**的数字，

而图重放目前只有 LM 那张图落地过（ViT 图需要 `_single_window_attention` +

### 15.10 双图的构成

```
pixel_values ──[图 1: ViT]──> pooler_output
                                  │
                    glue（CPU/GPU，图外）
                    ├─ split(pooler, split_sizes)   ← 原 .tolist() 改成图外预计算
                    ├─ masked_scatter 进 embed_tokens
                    └─ compute_3d_position_ids
                                  │
                    inputs_embeds ──[图 2: LM]──> last_hidden_state
```

三个补丁都是「把图内的 D2H 搬到图外」：

| 同步点 | 来源 | 解法 |
|---|---|---|
| `get_vision_*` 的 `.tolist()` | ViT 每次 forward 都算几何量 | `precompute_vision_geometry()` 图外算一次 |
| `lengths.tolist()` | ViT attention 的 split | `_single_window_attention()` 整段一次 SDPA |
| `split_sizes.tolist()` | `get_image_features` | `vision_split_sizes()` 图外算一次 |

`_single_window_attention` 的等价性前提仍然是**单窗口**（`cu_seqlens=[0,N]`）。
`DualGraphRuntime.teardown()` 会恢复原始 forward，换成分块窗口时必须调它。

### 15.17 用户质询：VLA 除了拖累 A* 还有什么用？（2026-11-02 凌晨，如实作答）

**M0 阶段的诚实答案：当前形态的 VLA 没有正面作用，纯粹是降级。** 逐条对照：

| 能力 | A* + navmesh 控制环 | VLA 接管后 |
|---|---|---|
| 规划 | A* 正常（plan 4.9–7.0 m、following、forward=1.0 m/s 从未中断） | 同一个 A* |
| 执行 | 1.0 m/s 平滑跟随 | 引导后 ~0.5 m/s，杆量 0.23（贴死区边缘） |
| 避障 | A* 会绕（地图里有障碍格就绕路） | 只会直走 + veto 拦停，**不会绕** |
| 延迟 | 10 Hz 控制环，零推理 | 2 Hz + 385 ms 推理延迟 |
| 稳定性 | LAS2 共存崩溃（三次 DEVICE_LOST） | 同样存在（VLA 是共存方） |

**"接入 VLA 后 A* 不能移动"的机制**：VLA 在线即 `drive_enabled=False`，
A* 控制环被静音（`nav_online.py:2417`），执行权全部交给 VLA。规划器从未损坏 ——
**坏的是交接协议：A* 的完整路径（转弯点、避障绕行、速度剖面）在交接时全部丢弃，
VLA 每拍只拿到一个 0.8 m lookahead 的航点。** 信息压缩到这个程度，VLA 不可能
做得比 A* 好 —— 它连"前面有墙要绕"的信息都拿不到。

**训练侧同构缺陷**：`build_policy_dataset` 的 wp 就是单点，模型从头就没被训练过
"给定路径怎么跟"、"障碍在左侧怎么让"。它学到的是"朝航点方向走" —— 这件事 A*
的 pure pursuit 已经做到 1 m/s 且带避障。

**VLA 要起正面作用，缺的不是调参，是问题定义**：

1. **输入要增维**：除了 wp 单点，把局部栅格（可走性热图）或 A* 的未来 k 个路径点
   喂进模型 —— 让它看得见"路径要左拐"和"左边有障碍"；
2. **输出要重新定义**：不替代 A* 的执行，输出对 A* 指令的**修正**（偏移/减速），
   A* 主导 + VLA 微调，各自做擅长的事；
3. **训练数据要覆盖失败态**：当前数据全是"人走得很顺"的片段，没有"走近路被墙挡住
   然后绕开"的片段 —— 模型没见过失败，学不会恢复。

**今晚的净收益**（与 VLA 无关但真实）：`/policy/state` 诊断端点、executor 计数、
stereo 单帧失败检查（堵黑帧进建图）、cam_h 标定污染的机理与自愈路径、
LAS2 与任何第二 XPU 负载不共存的结论、body 死锁的发现与两版修复。
这些是 M1 的地基；VLA 本体在 M0 形态下应当回炉。
### 15.16 自愈与代价：cam_h 自愈确认，SGBM 接管（2026-11-01 深夜续）

用户观察："等了一会自己恢复了，但双目耗时 20ms → 180ms"。两个现象分开定性：

```
errors: LAS2 subprocess exited with code 3221225477
        （UR_RESULT_ERROR_DEVICE_LOST）→ 本会话崩过，改用 SGBM
stereo_stages: disp=191-224ms（disp_cpu=133-156ms ← SGBM 在 CPU 上跑）

1. 第一次（21:57）：`VRC_POLICY_GRAPH=1` 的 V2 适配器与 LAS2 的 compute context 冲突；
2. 第二次（23:18）：**我的诊断脚本** —— `_frame_compare.py` / `_prev_test.py` /

另一个推理进程都会触发 DEVICE_LOST）。LAS2 崩后本会话不重试（"崩过改用 SGBM"），

### 15.15 在线首跑：真驱动的三道坎（2026-11-01 深夜）

接入真实控制后连环暴露三个问题，逐个定位如下。

**坎 1：角色完全不动 → 三层联锁，每层都各自"正常"**

| 层 | 症状 | 根因 |
|---|---|---|
| ① | `drive_block="autonomy_not_armed"` | autonomy 安全开关没 arm（启动流程遗漏） |
| ② | `executor_n_sends=0`（当时还没有计数器） | `VRC_POLICY_DRYRUN=1` 只记录不发轴 |
| ③ | 发了轴角色仍不动 | **模型输出被 body=0 锁死**（见坎 3） |

排障期间补了一个关键设施：**`GET /policy/state` 诊断端点**（`service.policy_state()`），
把 runner/executor/model 三层状态一次打出来。真驱动模式不写 `policy_live.jsonl`，
没有它就是盲人摸象 —— "角色不动"查了半小时，端点加上后 30 秒定位。
executor 顺带加了 `n_submits / n_sends / n_halts / last_send` 计数。

**坎 2：冷启动死锁 —— 模型把 body 当主导特征**

在线模型输出只有 0.06–0.13 m/s，同样 wp 在 dry-run 是 0.56。逐项排除后定位：

```
静止帧 × body 四档（真实当前画面，同模型同 wp）：
  body=(0, 0)     → vz=0.08   ← 在线状态
  body=(0, -0.5)  → vz=0.44
  body=(0, -0.8)  → vz=1.97   ← 正常行走速度
  body=(0, -1.0)  → vz=0.72
```

**模型把 body（本体速度反馈）当主导特征**。训练数据里人一直在走，body 与画面光流
严格一致，模型学的是"先看我在不在走，再看航点多远"。于是闭环冷启动死锁：

    body=0 → 输出≈0 → 角色不动 → body 仍=0

修法：`research/tools/policy_body.py` 的 `body_feedback()` —— OSC 静默且 navmesh
有任务时，喂"wp 方向 × min(0.6, dist) 的期望速度"；角色一动 OSC 有回传自动切回真实值。
`VRC_POLICY_BODY_NUDGE=0` 可关。6 条单测。
**生效证据**：引导后 `body=(0.38,0.46) → blk0=(-0.1, 1.5)`，odometry 累计 +16.9 m
—— **VLA 第一次真驱动走起来了**。

**坎 3：假障碍复活，把行走变成走停交替**

走起来之后 `near_obstacle.points` 反复飙到 3 万+（阈值 40）→ veto 拦停。判定链：

```
height_bands: below=0 / lo=292110 / mid=0 / hi=0
  → 所有立体点都在"地面带"（-0.3 ≤ h < 2.0），场景里没有真实立体障碍
  → 其中 h > ground_tol(0.30) 的 37531 个点被判成障碍
  → 地面被系统性抬高了 ~0.3m：cam_h 标定污染
```

`cam_h` 按会话前 120 帧的地面直方图标定，之后冻结（`cam_h_freeze_n=120`，冻结原因
见 nav_mapping.py:698 注释：重标一次要全量重投，610 帧实测 29.5 s）。**若会话启动时
镜头没有对准脚下**（盯墙/盯远处），直方图峰值就不是地面，cam_h 偏差 0.3m 后，
地面点 h = 偏差值，正好越过 ground_tol → 整个地面变成"障碍"。
修法：新开会话重新标定（启动时先低头看地面几秒）。长期修法是 ground_tol 动态化
或 cam_h 允许带迟滞的缓慢重标 —— 未做。

**本轮的两个正反馈闭环**（都是好的）：

1. 引导 body → 模型输出真实速度 → 角色动 → OSC 回传真实 body → 引导自动退出；
2. 走动 → 建图长大 → 前沿变远 → 路径变长 → wp 有效 → 继续走。

**本轮的一个负反馈闭环**（坎 3）：

    cam_h 偏 → 地面判成障碍 → veto 停 → 不动 → 画面不变 → cam_h 无法自愈（已冻结）
这一节记录的是**我说错的三件事**，以及用数据重新建立的事实。

**错误 1：「VRChat 占了 87.3% 的 GPU，所以图重放跑不出 34.6 ms」—— 不成立。**

我把 194 个 `GPU Engine` 实例的占用**跨引擎求和**了，这个算法本身就是错的。
分引擎实测（VRChat 空闲时）：

| 引擎 | 占用 |
|---|---:|
| 3d | 69.8% |
| **compute** | **0.0%** |
| copy / videodecode / gsc | 0.0% |

3D 和 compute 是**独立队列**，VRChat 的 3D 渲染不抢 compute 的算力。
用户点破这一点后重测，确认我的归因是错的。

**错误 2：「compute 100% 说明是实打实算力瓶颈」—— 也不成立。**

我做了三项验证想证明「GPU 真的忙」：

| 测试 | 结果 | 当时我的解读 |
|---|---|---|
| 单次 vs 连发 20 次 | 67.8 → 62.8 ms（1.08×） | 「异步不重叠，GPU 真忙」 |
| CPU 提交 | 30.7 µs | 「不是 CPU 瓶颈」 ✓ |
| 两流并发 | 132.2 ms = 1.95× | 「完全串行，compute 饱和」 ✗ |

这三项**只能证明不能并行，不能证明 ALU 打满**。用户补了一句关键的观察：
**「显卡功耗也不高」**。低功耗 + 队列满 = **串行依赖链限制**，不是吞吐限制。

正确的图景：24 层里 18 层 `GatedDeltaNet` 走 PyTorch 参考实现（`flash-linear-attention`
未安装），逐 token 递归、每步依赖上一步。**队列一直非空（所以 100%），但每步只用到
少量 ALU（所以功耗低、没法并行）。**

**错误 3：`flash-linear-attention` 值得装 —— 实测反向，5.4 倍退化。**

装 `fla 0.6.0` 后重测同一个 LM 图重放脚本：

| | 单次 p50 | min | 两流并发 |
|---|---:|---:|---:|
| 参考实现（无 fla） | 62.2 ms | 45.9 | 122.7 ms |
| fla 0.6.0 | **367.7 ms** | 357.4 | 718.8 ms |

**慢了 5.4 倍**，已卸载并复测确认基线恢复（62.2 ms）。
原因：fla 的 triton kernel 在 A770 上没有针对 XMX 的有效实现，且 `chunk_gated_delta_rule`
的分块在图里固化成大量小 kernel，串行依赖链反而被拉长。这与本仓库更早的记录
（eager 下只快 8%、单 mixer 反而 7.50→12.51 ms）方向一致，但退化幅度大得多 ——
**因为图重放把那些小 kernel 全部固化了，想逃都逃不掉。**

`causal_conv1d` 仍然缺失，但那是 ViT 侧的 packed-sequence 分支，对我们（单窗口）无影响。

### 15.14 修正后的瓶颈分布与下一步

修正归因后，128.9 ms 的真实构成（隔离测量）：

| 环节 | p50 | min | 占比 | 性质 |
|---|---:|---:|---:|---|
| 预处理（resize+tokenize） | ~26 | — | 20% | CPU |
| ViT 图 | 15.7 | 8.4 | 12% | GPU |
| glue（图外） | 19.5 | 12.8 | 15% | GPU+CPU |
| **LM 图** | **67.1** | **52.1** | **52%** | **GPU，串行依赖** |

LM 图随 token 数的变化：48 tok 49.4 ms / 96 tok 52.8 / 192 tok 66.7 ——
**固定开销 ~45 ms 与 token 数无关**，这是 18 层 GatedDeltaNet 的递归链。

**结论：剩下的 67 ms 不是「再调参」能解决的**，它是 GatedDeltaNet 递归结构
在当前实现下的固有代价。可选方向（按风险排序）：

1. **什么都不做** —— 128.9 ms 对 2 Hz（500 ms 预算）已有 3.9× 余量，
   对 `stale_s=0.8 s` 更是 6.2×。当前版本已经可用。
2. **压 glue（19.5 ms）** —— `compute_3d_position_ids` 每拍重算，
   但它只依赖 input_ids/mask/grid，位置固定时结果不变，可以缓存。
3. **压预处理（26 ms）** —— `to_policy_rgb` 用 PIL，双帧 2 次 resize；
   可以在 MirrorEye 的 GPU 侧直接缩到 448×256，PIL 那步整个省掉。
4. **别碰 fla / 别碰 GatedDeltaNet 实现** —— 实测 5.4× 退化，这条路已经证伪。

   > ⚠️ **这句话只对 `fla` 这个库成立，不能推广成「Triton 融合在本机不可用」。**
   > 2026-11-03 实测纠正（这条结论被误引过多次，包括 Lead 自己）：
   >
   > | 说法 | 真相 |
   > |---|---|
   > | 「`spirv_utils` 编不出来，Triton 在本机用不了」 | **已过期**。设 `CC=icpx` + oneAPI 进 PATH 后可编，训练 `--compile` 实测 **2.16×**（1320 → 611 ms/step） |
   > | 「decode 图报 Double，所以融合编不过」 | **不是 Triton 的问题**。根因是 Python float 被当 kernel 标量参数（设备 `has_fp64=False`）；`torch._dynamo.config.specialize_float=True` 后**编译成功**，kernel 6258 → 1824 |
   > | 「fla 慢 5.4×，所以 GatedDeltaNet 没有快实现」 | 前半句对，**后半句不成立**。那是 fla 0.6.0 在 A770 上没有 XMX 有效实现；Triton 融合本身可用 |
   >
   > 准确表述：**Triton 融合可用且已生效**（训练 8995 kernel、推理 1824 kernel），
   > 剩下的问题是**融合不够彻底**（理想 150–300），不是**不可用**。
   > 参见 `Docs/compile配置扫描结果-2026-11-01.md` 与本文 §15.14 的 2026-11-03 补注。

> **为什么图重放救得了 policy 前向、救不了 decode（2026-11-02 补）**
>
> 同一批算子，**形状静态**才能被 XPUGraph 折成一次提交（policy 前向 538 → 123 ms，4.4×）；
> decode 的 KV / 递归状态每步增长，形状逐 token 变，**图抓不住**，只能逐步付提交税。
>
> 实测单 token（`.venv_xpu/runs/decode_compiled/decode_compiled_default.json`）：
> **6258 个算子**，其中 `aten::copy_` 824 + CopyScalar(BF16) 445 + CopyScalar(f32) 302
> ≈ **1571 次纯拷贝**，`aten::mm` 559 + `gemm_kernel` 606 = **1165 次 matmul**
> （24 层本应约 140 次，被 16 个 head 摊开后放大 8×）。GPU 忙碌 89 ms，wall 338 ms
> ⇒ **249 ms ÷ 6258 ≈ 40 µs 纯提交空转**，与 §5.2 单算子微基准的 ~48 µs 吻合。
>
> 所以「一次前向出 12 步」不是省事，是把 24 个 token 的提交税摊成 1 份：
> **每输出 0.7 ms vs 338 ms（500×）**。这条决定了加宽输出（如 ω，12×2 → 12×3）
> 是**零成本**的，而加长生成（回到逐 token 自回归）在这台机器上不可行 ——
> 与本文件 §15.13–15.14「别碰 GatedDeltaNet 实现」、`Docs/流匹配头实施方案-2026-11-02.md` 末节
> 「不恢复逐 token 自回归」一致，这里补的是**量级依据**。
>
> **补（2026-11-03）：compile 这条路在 decode 上是双向封死的，机制已查明。**
>
> **动态形状（`dynamic=True`）**：能走到 Inductor codegen，但生成的融合 kernel 签名里带
> **fp64 标量**（`in_ptr2: fp64`，函数体内根本没被解引用），而设备属性写着
> `has_fp64: False`（A770/dg2 无 FP64）⇒ IGC 建 module 失败
> `ZE_RESULT_ERROR_MODULE_BUILD_FAILURE`。开 `SYCL_UR_USE_LEVEL_ZERO_V2=1`**无效**
> （同一 kernel 同一错，连 inductor cache key 都不变）—— 所以与 V2 适配器无关。
>
> **静态形状（`dynamic=False`）**：不会撞 fp64，但 **dynamo 编译不了这个模型** ——
> 18 层 `chunk_gated_delta_rule` 参考实现含 data-dependent 控制流，逐次 recompile。
> 实测同一组输入连调 6 次：
> `170509 / 171200 / 172137 / 169030 / 171948 / 951` ms，
> 前五次每次重编 ~170 s，第六次撞 `cache_size_limit` 静默退回 eager（951 ms）。
> **算子数 6396，与 eager 的 6258 持平 —— 一个 kernel 都没融掉。**
>
> 这正好验证了 `Docs/compile配置扫描结果-2026-11-01.md` §4 当时列为「未验证的怀疑点」的第 2 条。
> ⇒ 「compile 救不了 decode」不是没试，是两条路各有独立死因，且都不是配置问题。
>
> **再更正（2026-11-03 凌晨，实测）：上面这条结论有一半是错的 —— 动态那条路能救。**
> fp64 **可以去掉**，而且根因是一类问题：Python float 被 Inductor 当作运行期标量参数塞进 kernel。
> 两处即可（不需要改 PyTorch/Triton）：
>
> 1. `torch._dynamo.config.specialize_float = True`（默认 False，`_dynamo/config.py:162`）—— 把 Python float 折成常量；
> 2. rope 的 `attention_scaling`（`compute_default_rope_parameters` 里 `attention_factor = 1.0`，Python float）换成 fp32 张量。
>
> 修完后 decode 图**编译成功**（`Z` = `.venv_xpu/runs/decode_specfloat`），实测：
>
> | | eager | compile(dynamic=True) + 两处修补 |
> |---|---:|---:|
> | 算子数 | 6258 | **1824**（−71%） |
> | wall / token | 338 ms | **132.1 ms**（2.6×） |
> | GPU 忙碌 | 89.1 ms | **39.8 ms** |
> | 冷编译 | — | 340 s |
>
> 诊断过程中要记的两条：① IGC 的原文是 `Double type is not supported on this platform`，
> 设备 `has_fp64: False`；② `-cl-fp64-gen-emulation` **无效**（SPIR-V 验证阶段就拒，模拟在其后）。
>
> **但判决不变**：24 token = **3.17 s**。132 ms 里 GPU 只占 40 ms，其余 **92 ms 是 1824 次阻塞提交**（≈50 µs/次）。
> 即使提交成本归零，24 × 39.8 ms = **955 ms**，1 Hz 仍压线，2 Hz（500 ms）结构性不可能。
> ⇒ 自回归关死的真正原因是「**一个动作块要 24 次 decode、每次 decode 上千次提交**」，不是融合本身。

### 15.18 只转头不移动：body 输出 disabled（2026-11-02 凌晨）

接上转向代管后的第一次在线 goto：**头转、身体不走**。遥测三连：

```
policy/state:  executor n_sends 持续 +10/s，last_send=[0, 0.325]，hold=false
worldmodel/navmesh: mode=goto，state=following，forward=1.0（跟随器全绿）
snapshot().body: state="disabled"，output_enabled=false，heading.turning=true
```

**根因：调度器 body 输出处于 disabled**。scheduler.py:525 的主发送分支要求
`self._enabled`；disabled 时只走 534 行的 elif —— **转向（play-space yaw）照发**
（`_send_head_frame`，7645 条 turn_commands 就是它），**摇杆 overlay 不随帧发出**。
轴提交本身不报错（disabled 不在 submit 的拒绝名单），executor 的 n_sends 照涨 ——
发出去的轴全部落进一个没人读的 output_frame。

之前 A*-only 会话能走，是因为宿主侧曾开过身体输出；这次重启后端后没有任何
调用方发过 `{"kind":"enable"}`，disabled 是默认态。转向代管让"头在动"变得显眼，
把"轴根本没出网"这个问题盖住了。

**修法（运行时）**：`POST /action {"kind":"enable"}`（enable 会先走一段回中性
过渡，completion_confirmed=false；等 state=idle 后 output_enabled=true）。
注意 enable 在 state=idle 时会被拒（"already enabled"），只有 disabled 才收。

**修法（待办，代码层）**：`_start_policy_head` 真驱动模式（dry_run=0）启动时
应自动 ensure body enable，或在 /policy/state 里把 body.state / output_enabled
暴露出来——这次从发现到定位用了 40 分钟，其中 30 分钟花在"轴明明在发"的假象上。

**修复后验证**：OSC 回读出现真实速度（body=(0.38,0.46) → (-0.10,0.31)，nudge
上限 0.6 不可能给出 1.0 的读数，1.00 必为真实 VelocityZ），wp 0.82→0.79 持续
缩短，转向代管与摇杆同时工作。**VLA + 转向代管的完整链路第一次真正在线运行。**

### 15.19 走走停停的定量根因 + LAS2 复活 + 掉驱动机理（2026-11-02 凌晨）

**走停节律的直接测量**（0.5 s 网格 × 45 s，两条 15 s 窗）：

```
块产出 1.2 块/s（配置 2.0）；单次推理 683 ms（SGBM-eager 期）/ 333–387 ms（LAS2-eager 期）
executor halts 4.6/s 与 sends 4.9/s 交替 —— 块年龄 p50 = 1.13 s，死线 1.3 s
```

机理：块 12 步 × 0.1 s = 1.2 s 寿命，但 `obs_t` 在推理**前**取，块到手已老
0.68 s；下一块 1.36 s 后才到 > 1.3 s 死线 → 走 0.6 s → 停 0.06–0.3 s → 新块。
**旧代码把死线写死 1.3 s（1 Hz 的值），配置却是 2 Hz（方案 §1：2 Hz 应为 0.8 s）**。

### 15.20 走停的第二层根因：模型自己输出"减速-停-起"块（2026-11-02 凌晨二）

STALE=1.8 桥接后顿挫仍在。抓到模型真实输出（块龄 0.4–0.8 s 的 6 个连续块）：

```
vz = [0.51, 0.1, -0.05, -0.09, -0.07, -0.04, 0.02, 0.09, 0.34, 0.57, 0.88, 1.03]
     （起步）  （——— 负速/零 ———）        （—— 加速 ——）
```

**块本身就是"减速-停-再起"曲线**，每个块都一样。执行器在块龄 0.4–0.8 s 采样
（块 ~0.55 s 一换），正好落在负速谷底 → 发出的轴 ~0 → 走停走停。顿挫不是执行
层丢块（那层已修），是**模型输出的内容**在振荡。

为什么：推理时喂给模型的 wp 距离恒在 **0.5–0.6 m**（路径侧向时投影点在
progress+0.8 之前）——训练数据里这个距离对应"人到航点前减速"，模型于是持续
brake。而车慢下来 wp 又不会变远（跟随器一直推着 0.8 前视点），**自我强化的
慢速环路**。方案 G7 的 trans 类弱点（"抄当前基线只有 18% 能起步"）在线上的
真实长相就是这个。

**对策（不重训，输入侧）**：`VRC_POLICY_WP_MIN`（默认 0.8）——喂给模型的
wp 距离低于下限时按比例拉到下限，等价于永远喂"还没到点"的状态（训练集 47%
的 move 类就是这个分布）。执行几何用真实 wp，不受影响。已重启验证接线，
块形与节律待用户驾驶确认；若仍振荡，下一个杠杆是 §9.3 重叠块加权（0 代码
风险）与 M1 DAgger 慢速纠正段（治本）。

**本轮延迟实测**：LAS2 编译后 disp 53 ms（VsDevCmd 环境首次编译成功），
policy eager 333–508 ms 与其共存无 DEVICE_LOST —— §15.19 的修正结论再次确认。

### 15.21 "点了没反应"的第三种形态：body stopped_latched（2026-11-02 深夜）

用户点路径点 → UI 报 `body output is stopped_latched; call body_reset before
enabling it again`。链条：**外部 stop（UI 急停 / 宿主驱动 / 显式 /autonomy/stop）
把 body 打进 stopped_latched 并解除武装** → 摇杆静默而转向帧照发（同 §15.18 的
disabled 形态）→ 用户的 goto 被 `execution_rejected` 拒掉。

**这不是 bug，是急停语义**；问题是恢复要手动 reset+enable+re-arm 三步，UI 只报
错不引导。对策分层：

1. **看门狗（已进代码，service.`_policy_body_watchdog_loop`，2 s 一拍）**：
   body ∈ {stopped_latched, fault_latched, disabled} **且** navmesh 有活跃任务
   **且** drive_block 为 None（已武装）→ 自动 reset（+enable）。无任务/未武装
   时不动作 —— 急停语义必须保留（estop 之后看门狗抢着恢复等于没有急停）。
   注入 stop → disarm → re-arm 实测：re-arm 后看门狗仍不恢复的原因是 disarm
   期间 latch 与 drive_block 两个条件都卡着，re-arm 后 drive_block 清空即可
   走通（单元测试 5 条覆盖四种状态组合）。
2. **UI arm 时效 300 s → 1800 s**（navmesh.js）——之前 5 分钟后自动 disarm，
   用户再点 goto 就是 `autonomy_not_armed`，表现也是"没反应"。
3. **恢复口诀（留给用户）**：遇到"没反应"——① UI 点"武装"；② 若提示
   latched，点急停旁边的"启用身体"（或等 2 s 看门狗自动恢复）。

**驱动崩溃记录**：03:0x 驱动崩溃、VRChat 重启（用户报告）。此前 §15.16/§15.19
"eager+LAS2 从未 DEVICE_LOST" 的结论**再收窄**：eager 也会崩，只是不频繁 ——
LAS2 + policy 双 XPU 负载共存是持续在钢丝上走，崩溃属于随机事件而非确定事件。
后端已带看门狗重启，VRChat 回来后 UI 重开 navmesh 会话即可。

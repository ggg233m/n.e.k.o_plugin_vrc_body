# 标定录制 SOP：一次录制解决 cam_h / recenter 检测 / action_timeline（2026-09-24）

**背景**：`Docs/尺度标定门依赖-9%分歧（2026-09-24）.md` 查出深度链与 OSC 链在尺度上差 **5–13%**，
而 pipeline 静默采用了偏低的松门值（1.3056 vs 1.4245）。要定案，需要一个**与 OSC 和深度都独立**的米制参照。

**本 SOP 的核心发现**（读 AnyaDance 驱动源码得出）：**HMD 的局部位移本身就是那把尺子。**

---

## 一、驱动层已确认的事实（源码依据）

| 事实 | 依据 |
|---|---|
| 位姿**逐字上报**，无 world-from-driver 旋转 | `src/driver/virtual_device.cpp:712-718`（`vecPosition`/`qRotation` 直接赋值）；`:619-621` `qWorldFromDriverRotation.w = 1.0f`、`qDriverFromHeadRotation.w = 1.0f`（identity） |
| 单位是**米**，帧是 driver pose space | `docs/protocol.md:411`「Positions are in **metres** in the driver pose coordinate space」 |
| HMD 复位高度 = **1.50 m** | `src/core/constants.h:43` `kResetHmdY = 1.50f` |
| HMD 的 Y 只被夹到 **[0, 25] m** | `constants.h:33/39` `kMaxDeviceY=25.0f`、`kMinHmdY=0.0f`；只有 HMD 有地板（`:34-38` 注释） |
| 位置分量上限 **±30 m** | `constants.h:32` `kMaxAbsPositionMeters = 30.0f` |
| 流率 **60 Hz**，**无位姿超时失效** | `constants.h:41` `kStreamRateHz = 60`；`udp_pose_receiver.cpp:17` `kSocketTimeoutMs=100` 只是 socket 超时 |
| 发送方**应重复同一姿态**，驱动有去重 | `udp_pose_receiver.cpp:37-41`「A sender holding a pose repeats the identical command at its stream rate」+ `IsRepeatOfLast`/`SamePoseCommand`（`:91-105`） |
| 驱动**不读**任何真实设备/相机（写-only） | 上一轮全量 grep `GetDeviceToAbsoluteTrackingPose\|IVRSystem\|IVRTrackedCamera` 零命中 |
| 我们记录的是**驱动实际接受**的位姿 | `driver_log.py:90-117` `_hmd_pose_from_payload`（docstring：「提取驱动实际接受的 HMD 位置和四元数」），来自多播 `239.255.39.71:39571` |
| `.nya` 片段可回放驱动虚拟设备 | `nya.py`（clip 加载/采样）；AnyaDance `scripts/blender_export_mmd.py` 可authoring ⇒ **扫掠可自动化** |

**推论（本 SOP 的支点）**：avatar 静止时，相机的世界位移 **=** HMD 的局部位移。
两者都在米制下已知（我们下发、驱动逐字接受），**不含 OSC，也不含深度模型**。

## 二、录制分段

总时长约 **3.5 分钟**。全程 OBS 录制，全程 60 Hz 推 HMD 流。

### 段 A — 静置基线（10 s）

| 项 | 内容 |
|---|---|
| 动作 | avatar 不动；HMD 恒定 `pos=(0,1.50,0)`、`rot=identity` |
| 目的 | 通道自检 + 深度噪声地板 + 建立 offset 锚点 |
| 验收 | `check_recording_channels.py` 全 PASS；HMD 姿态方差 ≈ 0；`action_timeline` 有记录 |

### 段 B — HMD 扫掠：**cam_h 的独立锚点**（60 s）★核心

| 项 | 内容 |
|---|---|
| 动作 | **avatar 完全不动**（全程不发任何 `/input/*`）；HMD 沿 **X 轴**慢速往返：`x: 0 → +1.0 → −1.0 → 0`，做 2 个往返 |
| 速率 | ≈ **0.2 m/s**（单程 10 s）。慢到深度模型跟得上、运动模糊可忽略 |
| 约束 | **Y 固定 1.50、rotation 保持 identity** ⇒ 纯平移、无旋转 ⇒ 把 yaw 误差从这条测量里彻底排除 |
| 目的 | 相机世界位移 = HMD 局部位移（已知米制）⇒ 反解 `cam_h`，**零 OSC 参与** |
| 验收 | HMD 位置流 60 Hz 完整无洞；`action_timeline` **证明**全程无 `/input/*`；画面里地面可见 |
| 分析 | **新脚本** `research/tools/calib_hmd_anchor.py`：把 `scale_calib` 的位移源从 `dead_reckon` 换成 `t_ij_cam = R_iᵀ(p_j − p_i)`（HMD 位姿直接算），复用同一套 `s` 解算 |

**为什么是 X 轴**：沿 X 平移产生强视差、`near_min..near_max`（0.3–6 m）内可用点多；且 `R_ij = I`，
退化为 `s·(P_j − P_i) = t_ij_cam`，条件数最好。

**为什么这条测量是独立的**：`scale_calib` 现在的 `t_ij_cam` 来自 `dead_reckon`（= OSC 积分）。
换成 HMD 位姿差后，OSC 完全不出现在解算里 ⇒ 与 OSC 链独立；同时它直接用深度重投影 ⇒ 是"深度链的尺度"
对"驱动已知米制"的比对。两条链的差从此**可判定**，而不是只能量出"差多少"。

### 段 C — 原地分步转向：复核 yaw 符号 + 建立"无 recenter"基线（30 s）

| 项 | 内容 |
|---|---|
| 动作 | avatar 不动；HMD yaw 分步：`0 → +90° → 0 → −90° → 0`，每步停 2 s |
| 目的 | ① 复核 `yaw_sign`（图像内容移动方向）；② 作为段 D 的**阴性对照** |
| 验收 | 每步图像 yaw 变化与 HMD 同号同量（比例 0.9–1.1）；`yaw_sign_check` 结论与现有一致 |

### 段 D — 故意触发 recenter：recenter 检测的**阳性样本**（20 s）

| 项 | 内容 |
|---|---|
| 动作 | HMD yaw 转到 `+45°` → 停 3 s → **在 VRChat 里按 Recenter** → 停 5 s |
| 目的 | 造出「**图像突然转向、但 HMD 流没变**」的阳性样本 |
| 验收 | 检测器在 1 s 内报出事件；段 C **不误报** |
| 分析 | **新脚本** `tools/recenter_detect.py`：逐帧比「图像 yaw 率」与「HMD yaw 率」，残差超阈值即报 |

**为什么只能靠图像**：驱动是**写-only**（不读回 SteamVR 的 universe/recenter 状态），
所以 recenter 不会出现在我们的 HMD 流里 —— 它只会让**画面**转。当前项目对此**只有人工纪律**
（`受控录制操作手册.md:162`「确认无手柄/头显 recenter 事件」；`世界模型导航方案…md:2489`「无 recenter 事件」），
**代码里零检测**。段 D 就是为了把这条纪律变成可验证的检测。

### 段 E — `/input/Vertical` 阶梯：`action_timeline` 验收 + 可选速度曲线（60 s）

| 项 | 内容 |
|---|---|
| 动作 | 依次下发 `/input/Vertical` = `0.1 / 0.3 / 0.5 / 1.0`，每档保持 **8 s**（够 VRChat 加速到稳态），档间停 3 s |
| 目的 | ① 验证 `action_timeline` 与 OSC 回传能对齐；② 得到 input→稳态速度 曲线（**可选**） |
| 验收 | 每档稳态段 OSC 速度稳定；`action_timeline` 每条指令都能对上 |

> **速度曲线的优先级已下调**：只要 `action_timeline` 打开，OSC 静默期的速度就能由
> 「指令未变 ⇒ 速度未变」直接推定（zoh 精确成立），**不需要曲线**。
> 曲线只在「完全没有 OSC 回传」时才必需。所以段 E 的主要目的其实是**验收 `action_timeline`**。

## 四、已知陷阱（录制时别踩）

0. **⚠️ 段 B 的 HMD 扫掠是「标定动作」，不是「建图模式」。**

   **先澄清一个结构性事实（已核实，不是假设）**：本管线的录制**不可能产生 room-scale 走路**。
   `model.py:98` 把 HMD 中性位姿硬编码为 `(0.0, 1.50, 0.0)`；插件只**推**不**读**驱动
   （驱动写-only），没有真实 HMD 输入通路。实测全部录制（2 个有数据的 run）：
   X span **0.0000**、Z span **0.0000**、Y 恰好 **1.5000..1.5000**。

   所以「OSC 前进 + HMD room-scale」的混用**按构造不会发生**。
   当前两个 DR 都不用 HMD 的 `position`（`dead_reckon` 只用 `hmd.yaw` + `osc.dist`；
   `OnlinePose2D` 只用 `vx/vz/yaw`），在这条事实下**是正确的**，不是隐患。

   **唯一残留**：`motion.py` 的手势/舞蹈回放**会扰动 HMD 位置**
   （`:409` 鞠躬 −0.16 m Y / −0.10 m Z；`:403/:421` 还会旋转）。这是**有界、脚本化**的
   ~0.1–0.2 m 扰动，不是人走动。

   **录制纪律**：
   - 段 B（标定）：**只动 HMD、不动 avatar**（`action_timeline` 必须证明全程无 `/input/*`）。
   - 用于建图的段：**只用 OSC 移动**；**不要在手势/舞蹈回放期间扫图**。
   - 可选 QC：把 HMD 局部位移当**"手势是否误触发"**的检测（阈值建议 **0.25 m**，
     因为手势本身就有 ~0.16 m），数据现成（`driver_log.py:453` 收 `_last_hmd_position_xyz`、
     `time_alignment.py:87` 存 `position_xyz`、`service.py:653` 已读）。**优先级低** ——
     0.1–0.2 m 相对 cam_h 的 1.3 m 不确定度是二阶量。

1. **HMD 的 Y 被夹到 [0, 25] m**，位置分量 |·| ≤ 30 m（`constants.h:32/33/39`）。扫掠范围要留余量；段 B 的 ±1.0 m 安全。
2. **不要因为"姿态没变"就停发**：驱动期望发送方按 60 Hz 重复（`udp_pose_receiver.cpp:37`），
   重复有去重、代价很低。停发会让段 A/C/D 的静置期变成数据空洞。
3. **段 B 的"avatar 不动"必须靠 `action_timeline` 证明**，不能靠"OSC 没报文" ——
   OSC 速度是**变化驱动**的：静止不发包、**匀速也不发包**（本轮已量化：这造成 24.03 m / 37% 路程歧义）。
4. **同一 run 不要混用 HMD yaw 与 OSC `LookHorizontal`**：后者失真 2.2–4.14×，两个通道叠加会污染朝向。
5. **不要用 `kResetHmdY` 以外的值当锚点假设**：1.50 m 是驱动的复位常量，不是可调参数。
6. **段 D 的 recenter 必须真的按下去**，否则拿不到阳性样本；同时要确认它**没被误按在段 C**。

## 七、这份 SOP 修正了什么

上一轮我把「**HMD yaw 零点标定**」列为待办 —— **那是错的，已删除**。
理由（见对话记录）：驱动层面 yaw 是绝对的（源码级：位姿逐字上报 + identity 的 world-from-driver），
本 run 注入首帧即 identity、`HmdYaw.yaw[0] = 0.0000°`；而**常数零点偏移对地图内部一致性无害**
（整张图一起转，且建图与执行同源时自动抵消）。

真正需要标定的是**符号**（镜像不像旋转那样无害）—— 而符号**已经标定过**（`yaw_sign_check.json`，8/8）。
真正会「错位」的是**阶跃**（recenter）—— 本 SOP 的段 D 就是给这条目前只有人工纪律的风险加自动检测。

## 八、`research/tools/calib_hmd_anchor.py` 的验证记录（2026-09-24）

### 8.1 验证策略（为什么不是合成场景）

原打算用合成场景（已知 `cam_h_true`）验证尺度反解，**结果发现合成场景构造不出有效测试**：
平面场景的反深度图只依赖像素行，且投影行里的 `s` 被约掉 ⇒ `d_i ≡ d_j`、**`s=1` 恒为不动点**，
迭代从 1 出发永远返回 1.0。加一面墙也不行（墙的 `d` 是常数，两张深度图仍几乎相同）。

**这个退化本身值得记住**：它说明这条测量**依赖非平面结构**提供尺度信息，
纯平面（地板为主）场景对尺度近乎不可辨识 —— 与 `scale_calib` 的强门依赖（0.5→1.3049 / 0.15→1.4245）
在定性上一致。

于是改用**两条互补验证**：

### 8.2 验证 1：位移源的解析检查（自检 A，5/5 通过）

| 用例 | `t_ij_cam` | 期望 |
|---|---|---|
| 纯横移 +0.4 m，无旋转 | `(-0.400, 0, 0)` | ✅ |
| 纯横移 −0.5 m，无旋转 | `(+0.500, 0, 0)` | ✅ |
| 纯前移 +0.6 m，无旋转 | `(0, 0, −0.600)` | ✅ |
| 转 90° 后横移 +0.4 m | `(0, 0, +0.400)` | ✅ |
| 转 90° 后前移 +0.6 m | `(−0.600, 0, 0)` | ✅ |

> 注：`yaw_sign=-1` 会把驱动 `+90°` 映射成 `−90°`，所以第 4 项是 `(0,0,+0.4)` 而非 `(0,0,−0.4)`。

### 8.3 验证 2：在真实数据上与 `scale_calib` 逐位对齐

脚本支持 `--translation-source dr`（位移源换成 `dead_reckon`/OSC，即 `scale_calib` 的原样），
用来证明**解算与门与 `scale_calib` 等价**：

```bat
.venv\Scripts\python.exe tools\calib_hmd_anchor.py ^
  --translation-source dr --max-dyaw-deg 50 ^
  --run .slam_probe\offline_probe\recorder\runs\20260920-233456 ^
  --cache .tmp\_depth_cache20.npz
```

| 实现 | cam_h | n_valid | IQR |
|---|---|---|---|
| `scale_calib.py`（门 0.15） | **1.424527** | 376 | 1.3710–1.4724 |
| `calib_hmd_anchor.py --translation-source dr` | **1.4245** | **376** | 1.3710–1.4724 |

⇒ 解算与门**等价**。因此 HMD 模式与 `scale_calib` 的**唯一差异就是位移源**，而位移源已由 §8.2 解析验证。

### 8.5 仍未验证的部分（诚实声明）

# 逐点 3D 帧支持过滤：唯一被用户确认的导出侧干预（2026-10-28）

> 接 `点云拖影-导出侧干预全否与指标陷阱（2026-10-27）.md`（该篇裁定所有导出侧干预全否）
> 与 `跨趟错位量级与来源（2026-10-28）.md`（裁定错位主因是跨趟位姿漂移）。
>
> 本文记录唯一一个逃出「全否」结论的干预：**逐点 3D 帧支持过滤**（`--min-frame-support`）。
> 它不是「修正」，是「删除」；不是新算法，是把用户的一句话
> **「正确深度肯定占大多数，一合并不就算出来了」** 变成了可执行的判据。

## 〇、一句话结论

1. **判据**：把所有点按 0.15 m 立方桶分桶，统计每桶被多少个**不同帧**看到；
   不同帧数 < N（实测 N=2）的点剔除。保留点的**位置不变**——不引入任何新几何错误。
2. **实测（`20261026_184318`，体素 0.09 m，629,100 点）**：
   竖向叠层 p50 **14.00 → 10.00 cm（−29%）**、p90 48.0 → 42.0；
   两块飞板（k=293 z=1.58 等）**133 → 0 点**；
   代价是**点数 −27%**（860,349 → 629,100）+ 只被 1 帧看到的真实细节（灯具/边缘）被剔。
3. **用户目视确认「还可以」**——这是全部 7 种导出侧干预中唯一获此评价的。
4. **为什么之前 6 种都失败、这个活了**：它们全都隐含「表面假设」
   （地面/平面/xy 投影单峰），而帧支持数**不依赖任何表面假设**——
   真物体被多帧从不同角度确认，飞点通常只有 1 帧。

## 一、设计动机：三次失败的教训

| 失败方案 | 隐含假设 | 死因 |
|---|---|---|
| 逐帧 gc / 身高门 | 地面可见 | 15% 帧 gc 误差 >5cm，且只管地面带 |
| xy 格 + z 众数（共识表） | 竖直面在 xy 投影里单峰 | **墙在 xy 投影里是多峰的**——把墙/屋顶删了（cons3d.html，否） |
| 局部 VO 修正（localfix） | 相邻帧误差可外推 | 相邻帧本来就好，坏的是跨趟（用户：「几乎没有区别」） |

帧支持数把「这里是不是表面」换成「这里被看了几眼」：

* 真实表面：只要被 ≥2 帧扫过（哪怕同一趟），桶内不同帧数就 ≥2；
* 飞点/伪影：来自单帧的深度噪声，落在错位置上，后续帧不会再命中同一桶；
* **它不知道也不需要知道表面朝向**——地面、墙、屋顶、飞板一视同仁。

## 二、实现（`research/tools/pointcloud_view.py`）

`load_session(..., min_frame_support: int = 0)`，**默认 0 = 关闭，老路径逐位不变**。

1. **预扫**（`min_frame_support>0` 才有开销）：对每帧（过 range_m 距离闸、过 z 窗）
   的点做 3D 网格哈希（0.15 m 立方桶，`bx*4096²+by*4096+bz`），
   `_sup_frames[key].add(kf)` → 桶 → 不同帧集合 → 帧数。
   实测开销：预扫一遍 759 帧约 +40%（总 43 s → 同量级，因为主循环本来就要逐帧读 npz）。
2. **主循环**：每个候选点查自己桶的帧数，`< min_frame_support` 剔除（`sel &= ~bad`）。
3. **统计输出**：`[cons3d] 3D 桶 366,926  其中 >=2 帧支持 204,820（56%）`；
   HTML 统计里带 `min_frame_support / support_cells / support_dropped`。
4. **CLI**：`--min-frame-support N`（默认 0）。

⚠️ **桶边长 0.15 m 的取舍**：约等于体素 0.09 m 的 1.7 倍。太小（0.05）会把同一表面的
相邻桶分开、每桶帧数都掉到 1，真点也被剔；太大（0.3）会把飞点和真实表面并进同一桶、
飞点借表面的帧数过关。0.15 是本场实测的可用值，没做全扫。

⚠️ **指标陷阱提醒**（接 2026-10-27 那篇）：p50 改善 ≠ 拖影修好。
叠层的主因是**跨趟位姿漂移**（见 `跨趟错位量级与来源（2026-10-28）.md`），
过滤只是把「没有多视角确认的错位点」删了——**留下来的点同样带着漂移错位**，
只是密度低了以后视觉上不再叠成「帘子」。

## 四、盲区与代价（必须说清）

1. **点数 −27%**：包括只被 1 帧看到的**真实**细节（灯具、栏杆边缘、远处掠过的面）。
2. **单趟录制的天然上限**：一趟扫过的地方只有 1-2 帧支持，N=2 已经在删真点；
   N=3 会更干净但丢得更多（实测未获用户确认，不作默认）。
3. **它是导出侧的过滤器，不是建图侧的**：在线 mapper 看不到这些飞点的害处
   （占据栅格会被多帧真点淹没），所以**不往 nav_mapping 里搬**——
   导出视图的视觉效果不等于导航的几何正确性。

## 五、与 z 口径修复的关系

本次提交同时带着 `9cac3c0` 引入的两个修复（此前未提交到 view 侧的完整版）：

1. **导出读 T[2,3]**（`t_z` 自动切换：非零位姿表加 z，全 0 老表逐位不变）；
2. **0.15 m 桶哈希的 min_frame_support 预扫**（本文主角）。

`Z维进图-代码支持与单层录制不该开（2026-10-28）.md` 的结论不变：
单层录制里 z 真值恒 0，`enable_z` 只放大噪声（zon2.html 实测变差）——
本文的过滤器与 z 无关，对老位姿表同样有效。

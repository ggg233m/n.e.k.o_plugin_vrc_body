## 一、先钉三个前提

### 1.1 主样本是 **VRChat 官方 Home**，不是自有世界

`%USERPROFILE%\AppData\LocalLow\VRChat\VRChat\output_log_*.txt`（4 份，2026-10-05 15:58 → 10-06 06:43）
覆盖了 `navmesh_recordings/` 与 `navmesh_memory/` 里全部 10-05/10-06 场次，里面：

```
[Behaviour] Going to Home Location: wrld_4432ea9b-729c-46e3-8eaf-846aa0a37fdd
[Behaviour] Entering Room: VRChat Home
[AssetBundleDownloadManager] [100] Unpacking World (wrld_4432ea9b-…)
```

* 4 份日志里出现的 `wrld_` id **只有两个**：`wrld_4432ea9b-…`（31 次，Home）
  与 `wrld_1c74a5ce-…`（"スケーリングテスト2 scaletest"，只在 15:58 那份里）。
* `navmesh_memory/wrld_home-7cf435ea/world.json` 的 `world_source = "manual_id"`、
  `world_name = null` —— 身份是**手填的 key**，不是从世界 id 推出来的（符合"不猜世界"铁律）。

⇒ **结论**：当前建图链路的验收样本，落在**别人（VRChat 自己）的世界**里。
这对"解包"这件事的性质判定是决定性的（§二）。

### 1.3 2026 年"解包"已经不是免费午餐

本机 `F:\vrchat-cache\Cache-WindowsPlayer`（VRChat 自定义缓存路径，30 GB 配额，日志 `21:23:02` 行证实）：

* **40** 个 bundle，合计 **2.65 GB**；结构 `<HASH16>/<HASH32>/{__data,__info}`。
* **40/40 个 `__data` 头部的 `unityRevision` 都带 `-DWR` 后缀**
  （见到 `2022.3.22f2-DWR` 与 `6000.0.67f1-DWR` 两种）。
  `UnityFS` magic 本身仍是明文可读 —— 所以"能读头 ≠ 能读内容"，
  **正文是 VRChat 自家加密变体**，别被 magic 骗了（我第一遍就差点这么判）。
* VRChat Home 对应的是 `848B7EAD1099E4F3`（**96.9 MB**，`__info` 时间戳 1791206599
  = 本机 2026-10-05 21:23:19，与日志 `21:23:20 Unpacking World` 对齐）。

> **外部核实（🟡 片段级，见 `vrchat-cache-world-extraction-2026.md`）**：
> 这层加密是 **2025-03 下旬（27→30 日之间）** 加上的，社区认定为 **UnityCN**
> （Unity 自带的 AssetBundle 加密，非 VRChat 自研），社区另称 AES-GCM；
> 标志就是 `unityRevision` 的 `-DWR`（"DWR" 是 VRChat 加密体系的内部代号），
> 且**头部的时间戳/大小是伪造的**。
> AssetRipper 维护者已在 issue #1731 明确拒绝支持（原文："There is nothing to be done."）。
> ⚠️ 两个细节值得记住：
> ① **加密在客户端侧**：VRChat 服务端仍提供**原始明文包**（"security variant" 之外的普通 file URL），
>    所以"能不能拿到几何"在技术上取决于你愿不愿意绕保护措施，而不是取决于数学；
> ② **EAC 不拦读文件**：它拦的是对**游戏进程**的注入/内存 dump（那才是封号路径），
>    事后用普通进程拷贝 `__data` 不受影响。

## 二、解包的三条通路，与各自的真实代价

| 通路 | 技术上 | 代价 / 风险 |
|---|---|---|
| **A. 本地缓存直接解** | ⚠️ **老工作流已死，但不是数学上不可能**。40/40 是 `-DWR`；AssetRipper/UABEA/AssetStudio/ SARS 全部不行（AssetRipper 已明确拒修）；但 **UnityPy 自带 UnityCN 解密接口**（`set_assetbundle_decrypt_key`），社区工具（`udon-decompiler`、`VRChatStudio`）都在按 BPID 推密钥 | 🔴 这**是绕过 VRChat 主动施加的内容保护措施**；对别人的世界更是直接撞版权 |
| **B. 用你自己的账号从 API 拿原始包** | 🟡 外部线索：加密只在客户端侧，服务端文件仍是原始明文；VRChat 自家 feedback 也承认"加密包是 security variant，普通 URL 的原始包仍在" | 🔴 同上：绕保护的意图没有变。**对**自己上传的**世界，语义上是"取回自己的作品"，但没有官方通路** —— 官方对一个"下载自己上传内容"的请求的回复是"建议你自己备份" |
| **C. 作者路线**：自有工程的 Unity 导出 / SDK build 产物 | ✅ 最全、最准、零风险 | 只覆盖自有世界（`ROADMAP` 第 10 条已经点名"不通用"） |

**法律侧（🟡 逐条核过 ToS/指南原文，仍不构成法律意见；见 `VRChat-asset-ripping-research-2026-10-06.md`）**：

* ToS §12：不得 "decompile, reverse engineer…" / "**interfere with or circumvent any feature of the Platform, including any security, or access control mechanism**"；
  §13.2：(c) 未经许可复制他人 User Content、(f)(i)(ii) 绕过防复制与逆向、(j) 用非官方工具 **extract data**、(k) **decipher, reverse engineer, decompile, or disassemble**；
  社区指南 §5：**"Circumventing anti-tamper software is strictly prohibited and will result in enforcement actions."**
* **VRChat 自己的"ripping"定义（2024-08-08 官方 Dev Update）**已经覆盖到本案最关键的情形：
  *"downloading an asset … that does not belong to you using tools prohibited by our rules.
  This includes extracting and converting avatars or **worlds** gathered from your **game cache**, memory, or our API."*
  —— 同一次公告给出 **约 2400 个账号**的封禁；2024-07-25 另有约 1900 个。
* 逐案：

| 情形 | 裁决 |
|---|---|
| (a) **你自己上传的世界** | **不在 VRChat 的 "ripping" 定义里**（定义限定 "does not belong to you"），但**官方没有任何下载通路**（Help 站 2026-09-10 的原文是"我们不能提供你上传过的文件，建议自己留备份"；`Future Proof Publish` 已于 2025-04-30 被官方移除）。⇒ **风险落在"方法"上**（解密/改客户端）；**用你自己的 Unity 工程 = 零风险** |
| (b) **别人的公开世界** | 🔴 **明文禁止且已实际执行**（ToS §13.2(c)(j)(k) + 指南 §5；封禁 + DMCA + 重复侵权终止账号） |
| (c) **本地缓存里别人的世界** | 🔴 **同一个结论**：官方定义**逐字点名 "your game cache"**。"它已经在我硬盘上"不改变答案（§13.2(c) 看的是许可，不是位置） |

⚠️ **本文实测补一条公开记录里没有的**：公开讨论的加密说明基本只提 `.vrca`（avatar），
世界包是否同待遇"未证实"。**本机实测是：世界包同样被加密** ——
VRChat Home 的 96.9 MB 包（`848B7EAD1099E4F3`）与全部 39 个同类都是 `-DWR`。

**关键判断**：**对当前主样本（VRChat 官方 Home）来说，A 要做就是解密、B 越线、C 不适用。**
"解包 VRChat 地图"这条命令式想法，在 2026 年剩下的唯一形态就是 A/B —— 那是**政策选择**，不是工程选择。
（`ROADMAP` 已经替它做过裁决：第 10 条只留"自有世界评估 oracle"。本文认为**这个裁决维持**。）

  那种世界**一个字节的烘好的 navmesh 都不带**。⇒ "普遍没有 navmesh"不成立，"普遍有"也不成立，
  只能当运气。
* **这条路有成熟文献背书**：CAD/BIM-as-prior-map 一脉是标准做法——
  `rmcl`（UOS，直接把建筑师给的 3D 网格当定位先验）、**MICP-L**（IROS 2024，直接配准到三角网格）、
  **BIM-Loc**（专门处理"图纸 ≠ 现实"的差异）；"游戏引擎世界当真值"另有一脉（GTA V → SLAM/导航数据集）。
  ⚠️ **但查不到任何"用 VRChat 世界几何当机器人定位先验"的工作**：真要做是**空白区**
  —— 既是机会，也意味着没有前人的坑可以抄。最接近的 `Cyzzz19/vrchat_robot` 是在 VRChat **里面**
  跑 SLAM/导航（用虚拟 HMD 驱动），**不是**把世界几何当先验。

## 四、它**不能**解决什么（别抱不切实际的期望）

外部调研（`research/prior-map-localization-vs-slam-2026.md`，六个问题全查）给出的三条硬边界，
直接套到本项目的场景里：

1. **退化不是地图能修的**。点-面 ICP 的平移可观测性**只来自对应法向的张成**：
   走廊沿轴、空房间里的 yaw，**结构上不可观测**——
   "网格走廊还是走廊"。Zhang/Kaess/Singh 的结论是：**退化方向的误差是几何与残差的函数，与观测无关**。
   ⇒ 本仓库的低纹理走廊/平行墙场景，**换成真值地图照样滑**。
2. **初始全局定位是另一个更难的问题**。先验地图把"跟踪"变得容易，把"我在哪"变得更难；
   而且**错锁比漂移更坏** —— 它会稳定、自信地跟在一个错误位姿上。
   （本项目有一个结构性便利：**spawn 点是场景里的静态对象**，会话又从 spawn 开始 ⇒
   起点并非"绑架机器人"问题。但那只是起点，回场/被移动后仍然要重定位。）
3. **可走性/语义/动态物是另外三条链路**。碰撞体给的是"物理碰撞"，不是"这个运动模型能不能过"
   （台阶高、缝宽、坡、摩擦、传送 locomotion）。动态玩家在静态先验里**只是外点**，要被剔除而不是被理解。

**VRChat 特有的三个坑**（外部调研 Q3 的传感器部分 + 本仓库已知事实）：

* **镜面**：双目读到的是**镜子后面的虚像**，深度"合理但错"。自有世界 31 个镜面 ⇒ 必须处理。
* **平面着色/无纹理墙**：被动双目在**无光度匹配**的表面上直接失效 ——
  而 Unity 渲染的平墙恰好就是这个病态情形，**这正是 `few_matches` 那 318 次拒绝的物理原因**。
  所以"有了真值地图"并不会让**特征提取**变好；它只是让你**不再需要那么多特征**。
* **地图会变**：世界更新（自有世界更会天天改）⇒ 先验过期。外部调研里"定位器会安安静静锁到旧几何上"是有实例的。

## 六、推荐：把"解包"换成"自有世界真值化"，并先用它判方向

# 回环那一步为什么慢（2026-09-29 剖析）

**被剖析的现象**：`.tmp/nav_replay_run6/log.txt` 里，有回环的步 单步耗时中位 **6856 ms**（max 11323 ms），
无回环的步只有 **81.3 ms**，差约 84 倍。

---

## 0. 结论先说（含一处更正）

1. 🔴 **更正上一轮的归因**：这 6.8–11.3 s **不在 `backend/nav_loop.py`，也不在在线链路上**。
   它出在 `.tmp/nav_incremental_replay.py` **自己那份 `PoseGraph4.optimize()`**（scipy `least_squares`，
   **4 自由度** x/y/z/yaw）。而随插件运行的 `nav_loop.LoopCloser.optimize()` 是
   **2 自由度 + 拉普拉斯线性解（`_solve_laplacian` + splu）**，实测 **3.3–12.5 ms**，根本不慢。
   ⇒ 上一轮写的「当前在线链路最硬的实时性瓶颈」**判断有误**，已在 run5–7 文档里改正。
2. **慢的直接原因**：`PoseGraph4` 的残差函数 `res()` 是**纯 Python 逐边循环**，
   每次调用 **9.5 ms**；而 `least_squares` 因为用**数值雅可比**，一次优化要调用它 **722 次**
   ⇒ 722 × 9.5 ms ≈ **6.9 s**，与实测吻合。
3. **已验证的修法**：把 `res()` 向量化。**残差最大绝对差 1.6e-13（等价）**，
   单次 **9.5 → 0.157 ms（60×）**，`least_squares` 整体 **7126 → 469 ms（15×）**。
4. ❌ **不能靠降 `max_nfev` 省时间**（实测是负结果，见 §4）。

---

## 1. 归因（全图 55 节点 / 110 边 / 216 参数）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 边列表构造（含每条 odom 边的 `inv` + `norm`） | 1.3 ms | ~0% |
| `lil_matrix` 稀疏结构构造 | 12.9 ms | ~0.2% |
| **单次 `res()` 求值** | **9.5 ms** | — |
| **`least_squares` 整体（nfev=50，res 调用 722 次）** | **7260 ms** | ~100% |

⇒ **时间几乎全在 `res()` 被调用了 722 次上**（722 × 9.5 ≈ 6.9 s）。

**为什么是 722 次**：给了 `jac_sparsity` 但没给解析雅可比 ⇒ scipy 用**有限差分**估雅可比，
按分组每次雅可比约 13 次 `res()`，加上每次迭代 1 次，50 次迭代 ≈ 722 次。

**为什么 `res()` 单次就这么贵**（每条边、每次调用都在重复算常量）：

```python
def res(x):
    v = unpack(x)
    r = []
    for a, b, Z, st, sr in edges:          # 纯 Python 循环，110 次
        Ta, Tb = self.pose(a, v[a]), self.pose(b, v[b])
        E = np.linalg.inv(Z) @ (np.linalg.inv(Ta) @ Tb)   # ← inv(Z) 是常量，每次重算
        ...
```
- `np.linalg.inv(Z)`：**每条边每帧重算**，Z 是常量；
- `self.pose()` 里 `rz(-yaw_of(T)) @ T[:3,:3]`（即 `_tilt`）：**每节点每帧重算**，也是常量；
- 每次迭代 4 个 4×4 numpy 调用，单次几 µs，乘 110 边 × 4 = 约 440 次 numpy 调用 ⇒ 9.5 ms。

且它**随图增长**：res 耗时随节点数线性上升（13 节点 1.0 ms → 55 节点 8.3 ms），
这解释了日志里 ms 从 2407（step 32）爬到 11323（step 54）。

---

## 2. 已验证的修法：向量化 `res()`

常量只算一次（每边 `inv(Z)` 的旋转/平移、每节点的常量 `tilt`），整批 `einsum`：

```
E_R = inv(Z)_R @ (Raᵀ Rb)
E_t = inv(Z)_R @ (Raᵀ (t_b − t_a)) + inv(Z)_t
r   = [E_t/s_t (3), atan2(E_R[1,0], E_R[0,0])/s_r (1)]
```

实测（全图 55 节点）：

| | 原实现 | 向量化 | 变化 |
|---|---|---|---|
| 残差与实现的一致性 | 基准 | **最大绝对差 1.645e-13** | **等价** |
| 单次 `res()` | 9.498 ms | **0.157 ms** | **÷60** |
| `least_squares` 整体 | 7126 ms | **469 ms** | **÷15** |
| 末值 cost | 301.93 | 302.23 | 一致（0.1%） |

代码在 `.tmp/_prof_res_vec.py`（`res_new`），可直接搬进 `PoseGraph4.optimize()`。

> 踩过的坑（写公式时两次算错，都是靠「与原 res 逐元素比对」抓出来的）：
> 第一次把 `inv(Z)` 的旋转部分又转置了一次；第二次把 `E_t` 写成 `R(t − t_Z)` 而 `t_Z` 取的是
> `inv(Z)` 的平移（应当是 `Zi_R @ t + Zi_t`）。**向量化必须与原实现对拍，错了不报错、只会把解算器带到别处**
> （第一次比对残差差 205、cost 从 302 跑到 13028）。

## 3. 向量化之后剩下的 469 ms 是什么

| 项 | 数值 |
|---|---|
| res 调用 | 722 次 × 0.157 ms ≈ **113 ms（24%）** |
| 其余（稀疏雅可比装配、信任域线性代数、huber 缩放） | **约 356 ms（76%）** |

⇒ 剩下来主要不再是我方代码，而是 scipy 的数值雅可比机制。
**下一步要压，得给解析雅可比**（722 次 → 约 50 次），这一条**未实现、未测量**，只作为候选。

## 4. ❌ 不能靠降 `max_nfev` 省时间（实测负结果）

| max_nfev | 耗时 | res 调用 | **末值 cost** |
|---|---|---|---|
| 50 | 475 ms | 722 | **302.2** |
| 20 | 177 ms | 286 | 551.1 |
| 10 | 96.8 ms | 136 | 725.5 |
| 5 | 38.5 ms | 61 | 851.4 |

⇒ **迭代次数是真在收敛，不是在浪费**。降到 20 时间省 63%，代价是 cost 从 302 涨到 551（劣化 82%）。
**别拍脑袋降这个参数。**

## 5. 线上路径到底快不快（澄清）

| 组件 | 内核 | 实测 |
|---|---|---|
| `backend/nav_loop.py` `LoopCloser.optimize()` | `_solve_laplacian`（bincount 装配 + `splu`），2 自由度，8 次迭代 | n=55 **3.30 ms**；n=200 5.13 ms；n=500 8.88 ms；**n=886 12.52 ms** |
| `.tmp/nav_incremental_replay.py` `PoseGraph4.optimize()` | `scipy.optimize.least_squares`，**4 自由度**，数值雅可比 | n=55 **7126 ms** |

⇒ **在线链路本身没有这个 6.8 s 的问题。** 回放脚本是在**原型验证一个 4 自由度的位姿图**
（`nav_loop` 现在只做 2 自由度平移，朝向直接取 HMD 实测）。
所以这个数字的正确读法是：**「若将来要把在线位姿图升级到 4 自由度，这份 `least_squares` 必须先按 §2 改好」**，
而不是「现在线上慢」。

> **一句话**：`.tmp/pointcloud` 那份"一坨"里，**有两个是真 bug、一个是真的漂移**。
> 两个 bug 都在导出链路口径上：① `cam_h` 与逐帧地面修正 `gc` 被**拆成两半**，导出只用了
> 前一半；② 高度**有符号量被无符号编码**，地板以下的点全糊成一张 0 层平板。
> 修完：三场有效离地高从**差 318 mm** 收敛到**差 9 mm**，被压平的点从 **13.8% 降到 0.2%**。

> 1.75 既不是身高也不是该统一的量，见 §三。

## 一、口径先钉死（三个数不是一回事）

修之前必须先分清，否则一定改错（我第一轮就改错了，见 §三）：

| 量 | 单位 | 本场值 | 含义 |
|---|---|---|---|
| `cam_h` | **地图单位** | 1.756 / 1.483 / 1.438 | 相机离地高（**全局估计**，整带加权中位，带 0.06 m 滞回） |
| `gc` | **地图单位** | −0.002 / −0.268 / −0.320 | **逐关键帧**的地面整体偏移修正（1.2 m 外地面众数） |
| `cam_h − gc` | **地图单位** | **1.758 / 1.751 / 1.758** | **真正跨场可比的"有效离地高"** |
| `world_scale` | 世界米/地图单位 | 0.755 | 尺度因子，**随 avatar/眼高变**（§10.10） |

**`h = (rel_z + cam_h) − gc`** —— 这是 `nav_mapping` 与 `offline_fusion.kf_rows` 一直在用的公式。
`cam_h` 与 `gc` 是**一对**：`cam_h` 允许粗糙，`gc` 负责把它拉回每个关键帧的真实地面。

## 二、两个 bug（都已修）

### 2.1 🔴 `gc` 被丢掉 ⇒ 三场地面差 0.27 m

`research/tools/pointcloud_view.py` 原先算的是 `zw = pw[:,2] + cam_h`，**没有减 `gc`**。

```python
# 修前（pointcloud_view.load_session）
zw = pw[:, 2] + cam_h                      # ❌ 少了 − gc
# 修后
gc = frame_ground_offset(p, T, cam_h)      # 新增：与 mapper/offline_fusion 同口径
zw = pw[:, 2] + cam_h - gc                 # ✅
```

后果：`235237` / `001523` 两场的地面被**整体抬高 0.27–0.32 m**。按场着色时表现为**整场分层**，
看起来像"跨场对齐错了"，其实是记账少了一项。

**证据（修前 → 修后）**：

| 场次 | `cam_h` | `gc` 中位 | 有效离地（修前） | 有效离地（修后） |
|---|---|---|---|---|
| `044153` | 1.756 | −0.002 | 1.756 | 1.758 |
| `235237` | 1.483 | −0.268 | **1.483** | **1.751** |
| `001523` | 1.438 | −0.320 | **1.438** | **1.758** |
| **极差** | — | — | **318 mm** | **9 mm** |

### 2.2 🔴 有符号高度被无符号编码 ⇒ 13.8% 的点糊成一张平板

```python
# 修前
z = np.clip(points[:, 2] * Z_SCALE, 0, 255).astype(np.uint8)          # ❌ 负高度全变 0
# 修后
Z_OFFSET_M = 1.0                                                       # 可表示 −1.00 … +4.10 m
z = np.clip((points[:, 2] + Z_OFFSET_M) * Z_SCALE, 0, 255).astype(np.uint8)
```

解码端同步 `POS[z] = buf[o+4]/ZS - ZO`。**"一坨"里最扎眼的扁平底板就是它**。

修后高度分布恢复成"地面一个尖峰 + 上方自然衰减"，不再是 0 层死平堆积。

## 三、⚠️ 作废一条建议：`cam_h` **不该**统一成 1.75

第一轮我提的"三场取同一 avatar 的统一 `cam_h`（≈1.75）"**是错的**，三条理由：

1. **1.75 不是身高**。它是**地图单位**下的相机离地高；`× world_scale` = 1.33 世界米，
   与 §10.8 用实物尺子量到的 **1.34–1.35 世界米**吻合。VRChat 侧的"身高"是另一类数字
   （§10.9 五类尺度）。
2. **`cam_h` 是全局估计，逐场被估偏是设计上已知的**。`_update_cam_h`（`nav_mapping.py:519`）
   取的是**整个 1.2–2.6 m 带内的加权中位**，`band` 只按高度切、**没有水平半径限制** ⇒
   桌面/床面/家具会把它往下拖。`235237` 的 1.483 就是这么来的。
3. **`gc` 就是为吸收这个偏差而存在的**。`nav_mapping.py:63` 注释原文：
   *"单个关键帧的地面可能整体偏离全局 cam_h（低头/蹲下/HMD 高度抖、视差系统误差）…
   按该帧 1.2 m 外地面的高度众数修正"*。所以正确做法是**补 `gc`**，不是**改 `cam_h`**。

⇒ 任何"把 `cam_h` 调准"的改动都会**与 `gc` 打架**（两边同时修 = 双重修正）。
`cam_h` 与 `gc` 的关系是**估计器 + 残差修正**，别把残差项当成误差项去调。

## 四、新增：跨场"有效离地高"一致性闸

这类错误不该靠人眼看图发现。`pointcloud_view.py` 现在在出图前强制检查：

```
[cam_h] OK   有效离地高跨场 044153=1.758, 235237=1.751, 001523=1.760 ⇒ 极差 9 mm
```

阈值与解释：

| 极差 | 判定 | 含义 |
|---|---|---|
| ≤ 50 mm | `OK` | 同一 avatar、地面修正正常 |
| ≤ 150 mm | `WARN` | 查地面证据是否够（UGC 挡地、遮挡多） |
| > 150 mm | `FAIL` | 先查**是否换了 avatar/身高**（换了要重标 `world_scale = 0.755×(眼高/1.26)`），再查地面修正 |

**反向区分力已实测**（把 `gc` 强制置零 = 复现修复前行为）：

```
旧行为（gc 置零）  044153=1.756, 235237=1.483, 001523=1.438 ⇒ 极差 318 mm ⇒ 闸门判 FAIL
```

## 五、顺带修的口径不一致：位姿源

`pointcloud_view.py` 原先硬编码 `session_pose_table`（= **merged 弹性位姿**），
而 `prior.json` 的 `pose_mode` 是 **`rigid`**。同一个世界、同一份数据，**两张不一样的图**。

`ROADMAP` 2026-10-06 的 A/B 已裁定「**刚体换系零代价、弹性形变会拉坏内部自洽会话的
多视一致性**」⇒ 融合/固化档一律 `rigid`。现在查看器默认 `--pose rigid`，
`--pose merged` 保留仅作对照。

⚠️ **本次实测两者范围只差 ±5%**（`044153` 27.4×31.1 vs 32.9×28.7 m 等），
**所以它不是"一坨"的主因** —— 别把这条当成解释。它只是口径统一。

## 六、剩下的那个"一坨"是真的（不是 bug）

修完两个 bug 后，点云跨度仍是 **55×48 m**，`prior` 的 free 层仍是放射状星芒。

* 三场**各自单看**也跨 40–51 m；`prior.npz` 栅格 486×560 @ 0.1 m ≈ 48×56 m 刚好装下；
* 与 `ROADMAP` 2026-10-06 那条裁决一致：*"free 是各会话在漂移位姿下累积扫出的糊图"*。

⇒ **这部分是 P0 的靶子，不是导出问题。** 修复后图只差在"地面齐了、负高度不糊了"，
**不要把收敛后的图读成"漂移修好了"**。

⚠️ **未分离**：55 m 里真实世界有多大、漂移占多少，本文**没有**给出拆分。
需要真值几何才能定（`Docs/解包世界资产-可行性（2026-10-06）.md` §六 S1）。

## 八、诚实边界

* **没做**：`cam_h` 估计器本身的改进（加水平半径限制）。§三 说明了为什么**不必**动它 ——
  但若将来 `gc` 也救不回来（地面全被 UGC 挡住），那才是改估计器的时机。
* **没做**：55 m 跨度里"真实世界尺寸 vs 漂移"的拆分（缺真值）。
* **没验证**：`cam_h` 偏差是否**只**由家具造成；本文只证到"整带中位无半径限制"这一机制。
* 本文用的三段录制（`044153` / `235232` / `001523`）**都是同一 avatar**（§四 的 9 mm 就是证据），
  所以**没有**覆盖"真的换了身高"那种情形 —— 那种情形应由闸门的 `FAIL` 分支接住，
  该分支只有合成逻辑、**无真实样本**。

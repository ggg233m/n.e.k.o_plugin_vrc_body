# 节流自适应：ρ 1.68 → 0.66（2026-10-29）

> 接 `rasterize瓶颈-回环重建固有代价（2026-10-29）.md` §五 的「ρ 诚实修正」。
> 那篇把 ρ=1.67 归因于「λ 翻倍」，暗示要降到达率才能修。**这个结论漏了一半**：
> 服务时间里有一大半根本不是计算，是节流器在 sleep。

## 〇、一句话结论

1. **建图线程不忙，是被节流器按住。** 实测 compute 只要 **186 ms/帧**，
   而 `done_t` 间隔 p50 是 **511 ms** —— 差额 **300 ms 正好是 `map_min_interval_s`**。
2. 积压时等这个窗口**毫无意义**：队列里已经有帧在等，早一秒建图就早一秒排空。
3. 改成**有积压就不等**（无积压时行为逐位不变）：实测 **408 → 181 ms/帧**，
   **μ 2.18 → 5.52 kf/s**，**ρ 1.68 → 0.66**（首次进稳定区）。
4. 这是唯一能把 ρ 压到 1 以下的改动，且**零风险**（本机 20 逻辑核，节流本来省不出什么；
   低核机器仍保留节流）。

## 一、怎么发现的：把 sleep 当成了"服务时间"

前面几轮我一直用 `done_t` 间隔当"服务时间"，算出 459–511 ms/帧。
同进程独占 CPU 实测同一批帧只要 **186 ms**：

| 组件 | p50 |
|---|---|
| `loops.add_keyframe` | 44.7 ms |
| `mapper.add_keyframe` | 9.0 ms |
| `_sync_acc` | 42.1 ms |
| `_sync_ray` | 33.8 ms |
| `compute` 合计（rasterize 115 + build 16） | 132.2 ms |
| **可归因合计** | **186 ms** |

差额 322 ms 不是 GIL（实测一个抢 GIL 的 Python 线程只造成 0.93×，numpy 内部释放 GIL），
而是 `_mapping_loop` 里这一行：

```python
wait = c.map_min_interval_s - (self._clock() - last_update)   # 0.3 s
```

**所以历史上所有"服务时间 585/511/835 ms"的数字，都混进了 sleep。**
`map_backlog.py` 用 `done_t` 间隔算 μ 也因此系统性低估 —— 那个 μ 不是计算能力。

## 二、改法（`backend/nav_online.py`）

`_reset` 里加两个观测：

```python
self._map_backlog_seen = 0      # 上一轮因 map_max_kf_per_batch 上限被放回队首的 kf 数
self._map_throttle_skips = 0    # 累计跳过节流的次数
```

`_mapping_loop` 每轮醒来先清零，然后：

```python
backlogged = self._map_backlog_seen > 0
wait = c.map_min_interval_s - (self._clock() - last_update)
if wait > 0.0 and not backlogged:
    timeout = wait              # 无积压：照旧节流（省 CPU）
else:
    if wait > 0.0:
        self._map_throttle_skips += 1
    ...                          # 有积压：直接 compute
```

`backlogged` 的信息源是**放回队首那一刻**（`_pending[:0] = pending[i:]` 之前）：

```python
self._map_backlog_seen = sum(1 for kd, _it in pending[i:] if kd == "kf")
```

⇒ 只用"上一轮有没有因上限被截断"这一个 bit，不需要新锁、不读队列、无竞争
（`_map_backlog_seen` 只在建图线程写，status 侧只读 int）。

## 三、实测

真实帧数据（150 帧预热 + 40 帧），走真实 `LoopCloser` + `mapper` + `NavSession.compute`：

| 方案 | 每帧 | μ | ρ（λ_active=3.65） |
|---|---|---|---|
| 死等 300 ms（现状） | **408 ms** | 2.45 | 1.49 |
| **有积压不等（本次）** | **181 ms** | **5.52** | **0.66** |

⚠️ 这是**离线重放**口径（真时钟、真算法、单线程独占）。实盘还会叠加 GIL 与写线程的
0.23 核占用，实际 μ 会低一些；但方向与量级可信 —— 因为省掉的是**确定的 sleep**，
不是"估算的性能提升"。

## 四、可观测性

`status()["map_throttle_skips"]` / `status()["map_backlog_seen"]`，
以及 `meta.json` 的 `final.map_throttle_skips`。
下次录制直接看：`skips` 很大 ⇒ 节流确实一直在拖后腿（自适应在起作用）；
`skips == 0` ⇒ 一直是采集慢于建图，节流没害处（低核机器该有的行为）。

## 五、教训（值得单独记）

**把"线程睡着的时长"当成"服务时间"，是排队论分析里最经典的错。**
ρ = λ/μ 的 μ 必须是**实际处理能力**，不是 wall-clock 间隔。
这次是靠"同进程独占 CPU 实测 186 ms vs 实盘 511 ms"这个 3 倍差才发现——
如果只信 `done_t` 间隔，会得出"必须降 λ（减少关键帧）"的错误处方，
而那会让跨趟约束供给变少，把拖影问题弄得**更糟**。

# ORB-SLAM3 双目参照评估（2026-09-26）

**问题**：单目 SLAM 在纯转头时初始化不了，尺度也没有米制锚点。换成双目能不能解决？
ORB-SLAM3 能不能直接用？
**被测**：上游 ORB-SLAM3 v1.0 的 `stereo_euroc`（Windows / MSVC 2022 自编），
`Camera.type: Rectified`。输入是 SteamVR 合成器镜像纹理录下来的真双目序列。
**身份**：**GPLv3，只做研究参照**。不链接进插件，不随插件分发（插件是 MIT）。

---

## 一、结论（先说）

1. **双目几何在 VRChat 画面上是成立的。** 21 次运行、4 段序列，全部在第 0 帧就完成
   双目初始化，不需要单目那种视差门槛；原地转头也追得住。
2. **尺度是唯一一个跨全部运行都稳定的结论。** s_eff 中位数 **0.751**，
   21 次里最差也在 **−6.0%…+1.6%** 之内，对照的是另一种方法独立标出的 s = 0.755。
   也就是说，双目 BA 和 OSC 位移比这两种独立方法得出了相同的尺度。
3. **追踪连续性不稳定，而且单次运行的结果不能用。** 同一个 exe、同一份输入，覆盖率
   可以从 13.0% 跑到 93.9%（run2_15hz 那 6 次）。原因是 Tracking / LocalMapping /
   LoopClosing 三个线程异步执行，每次调度都不一样。**每个序列至少跑 3 次，看分布。**
4. **丢追的主因是甩头。** 所有丢追段之前都有高转速，各组中位数在 70–380 °/s 之间。
   这个数是从轨迹推出来的，只是**下界**（见 §六）。丢追时特征点是满额的，所以问题
   不在纹理。
5. **回环几乎不触发：21 次里只有 1 次**（run3_640 rep2）。能把丢追接回来的机制是
   **地图合并**（每次 1–6 次），不是回环。
6. **跟不上 30 Hz。** 640 宽度单帧追踪中位 57–66 ms，720 宽度是 67–72 ms。
   30 Hz 的预算是 33 ms。
7. **不采用。** 除了 GPLv3 这一条，它每帧都要做 ORB 提取加描述子匹配，这个前端成本
   是结构性的，调参数压不到 33 ms。后续方向见 §九。

## 二、真双目从哪来

`Headset Window` 改 `eye_mode=both` **无效**：那个窗口显示的是合成器自己的镜像，
永远是单眼铺满窗口。配置已恢复成 `left`。

真正的双眼画面来自 **`IVRCompositor::GetMirrorTextureD3D11`**（`research/tools/openvr_mirror_probe.py`）：

| 项 | 值 |
|---|---|
| 应用类型 | `VRApplication_Background`，不抢 VRChat 的 scene 位 |
| 每眼纹理 | 2880×1620，RGBA8（DXGI 27），fx = fy = 810（`getProjectionRaw` ±1.7778 / ±1） |
| 眼间变换 | tx = ∓0.0315，基线 **0.063 m**，来自驱动的 `Prop_UserIpdMeters_Float` |
| 校正 | 两眼已经是平行校正对，实测 \|dy\| ≈ 0 |
| 世界尺度 | s = d_osc / d_stereo = **0.755**，游戏内有效基线约 0.0476 m，**随 avatar 缩放变化** |

**两眼必须取自同一合成帧**：两次 `CopyResource` 先连着入队，然后再统一 `Map`
（`read_stereo`）。如果逐眼 `read()`，两眼会相隔约 3 个合成帧，走动时立体点会从
约 1100 掉到约 155，尺度随深度漂移。早期的 run1 / run2 标定（s ≈ 0.50 / 0.85）
就是这样被污染的，**已作废**。

## 三、取帧性能（已修）

| 阶段 | 双目取帧 | 改动 |
|---|---|---|
| 原始 | 约 93 ms | `[:, :, :3][:, :, ::-1].copy()` 是负步长三通道收集，单眼 33 ms |
| CPU 端修正 | 约 25 ms | 在映射内存上直接 INTER_AREA 缩放，输出逐像素一致 |
| **GPU 端 mip** | **2.3 ms**（run3_720p 录制实测中位） | 镜像 → mip0 → `GenerateMips` → 取 mip 2 回读，回读量降到 1/16 |

PNG 编码移到了后台线程，录制稳定在 15 Hz（dt p99 约 73 ms）。**取帧已经不是瓶颈**，
剩下的预算全在 SLAM 上。

**输出分辨率不写死**：`record_stereo_euroc.py --target-width`（默认 720）是宽度下限，
实际分辨率取 mip 链上仍不小于它的最深一级，内参按比例缩放。降低 SteamVR 渲染分辨率
也不用改参数。

**「追踪 OK」和「覆盖」是两个不同的口径：**

- **追踪 OK**：逐帧 `GetTrackingState() == OK` 的比例，统计的是**全部**帧。
- **覆盖**：`SaveTrajectoryEuRoC` 输出里有位姿的帧数占比。它**只写最终最大的那张地图**，
  没合并回来的地图段整段丢掉。所以两者会分叉：run2_15hz 就是 OK 65%、覆盖 13–36%，
  追是追上了，但建出来的是 4–7 张碎图。

### 为什么不能拿不同场次的录制来比

run1 和 run2_15hz 是**不同场次的录制**，里面的运动不一样：run1 丢追前转速中位
70 °/s，run2_15hz 是 184–209 °/s。所以「run2_15hz 更差」**不能**归因到帧率或分辨率上，
只能说明那一场甩头更猛。

**唯一受控的对比是 run3**：`research/tools/downscale_stereo_seq.py` 把 run3_720p 整段缩到 640，
时间戳和 OSC **逐字节沿用**，只有分辨率不同。

### 受控对比：640 追得更稳，720 尺度更准

| | 640（受控） | 720（原生） | 判断 |
|---|---|---|---|
| 尺度离散 MAD | 6.2–8.9% | **4.6–5.4%** | 720 更好。两组区间不重叠，这条结论比较可靠 |
| 追踪 OK | 83.4–94.9% | 80.4–90.3% | 区间重叠，n = 3，**只是倾向**，不是结论 |
| 丢追段 / reset | 3–6 / 0 | 5–9 / 0–1 | 640 倾向更稳 |
| 单帧中位 | 63–66 ms | 67–72 ms | 640 刚好卡在 15 Hz 的 66.7 ms 预算内，720 超了 |

720 的尺度更准，符合 fx 更大（202.5 vs 180）、画面更锐（Laplacian 方差 1411 vs 831）
的预期。缩放带来的模糊也是被测对象的一部分：实时管线里 640 本来就是从 mip 2
再做一次 1.125:1 非整数缩放得到的。

## 五、这个场景下基线的物理限制

0.063 m 的基线在远处条件数很差。fx = 202.5 时，dx = 1.73 px 对应约 5.6 世界米，
而 ORB 金字塔在 octave 1 的量化步长就是 1.2 px（scaleFactor 1.2），和视差本身同量级。
实测的 dx 中位数正好落在 1.2² = 1.44 和 1.2³ = 1.728 上，就是这个量化的痕迹。

⇒ **远景深度在任何分辨率下都不可信，这是基线决定的，分辨率救不回来。** 近处 1–2 m
没问题，避障够用；远处要靠别的手段。

## 六、丢追机制

- 丢追时特征点都是满额（1200），对比度正常，所以不是纹理不足。
- 丢追前有高转速。各组中位数：run1 70 °/s，run2_15hz 184–209 °/s，
  run3 640 270 °/s，run3 720 380 °/s。最大值 363–838 °/s。
- **这些转速是下界**：它们是用「丢追前最后一个真实位姿」附近的轨迹推出来的，真正的
  甩头峰值出现在丢追的那几帧里。早期直接从画面推出过 249 °/s 的峰值，这个数和轨迹
  推出的 33 °/s 对不上，就是这个原因。
- 15 Hz 下 400 °/s 相当于每帧转过约 27°，相邻帧的共视区域大部分都没了。
- 能把碎图接回来的是**地图合并**，不是回环（21 次里只有 1 次回环）。

**没做但值得做**：用 OpenVR 的 HMD 姿态当旋转先验。纯物理转头可以用；用手柄转身时
游戏内相机和 HMD 不再 1:1，OSC 的角速度能不能补上这一项还没验证。

  旧 DLL（00:57）备份在 `.tmp/ORB_SLAM3.dll.stereo_0057.bak`。
- `Examples/Monocular/Release/`：exe 03:38，DLL 仍是 09-19 的旧版本。

  但这份旧 DLL 里**没有**词典缓存。`run_mono_tum.sh` 运行时会把 `build/Release/ORB_SLAM3.dll`
  拷过去，走那个脚本就会用上新 DLL。

**构建**：用 `.slam_probe\build_orbslam3.bat <目标>`（Ninja Multi-Config，真增量，产物路径与旧 VS 构建一致）。

- 从 PowerShell 或 cmd 直接运行。从 Git Bash 调用时要写绝对路径（`cmd //c "H:\...\build_orbslam3.bat stereo_euroc"`），
  否则 cmd 找不到相对路径的 bat。
- **LNK1189 的根因与修法**（03:10 修入 `ORB_SLAM3/CMakeLists.txt`）：Ninja 生成器拿不到 MSBuild 默认的

  校验 `impl-Release.ninja` 里有没有它。**改了编译标志要用 `--clean` 重建。**
- 该脚本已转成 GBK + CRLF（cmd 按代码页 936 解析，UTF-8 的中文注释会破坏解析）；
  转换前的 UTF-8 原件在 `.tmp/build_orbslam3.bat.utf8.bak`（那是 02:33 的旧版，不含 toolchain 参数，勿恢复）。

## 九、为什么不采用，以及下一步

**硬约束**：

1. **GPLv3**。插件是 MIT，链接它就意味着整体得按 GPLv3 分发。另起一个仓库也绕不过去，
   GPL 看的是分发和链接，不看仓库边界。
2. **30 Hz 做不到**。每帧都要做两眼 × 8 层金字塔的 ORB 提取和描述子匹配，这是它的
   结构性成本。
3. **GPU 路线走不通**。A770 没有 CUDA，而社区的 GPU 加速版和近年的学习型 SLAM
   基本都依赖 CUDA。cv2 的 OpenCL 能用，但 SLAM 的大头（g2o 稀疏 BA、图维护、词袋查询）
   本来就不适合 GPU。

**方向**：换**光流前端**。已有的点只做跟踪，不够了才补新点，单帧开销能低一个数量级；
而且帧率越高，帧间位移越小，光流越稳，30 Hz 本身也在帮着解决甩头丢追。

| 候选 | 许可 | 角色 | 主要风险 |
|---|---|---|---|
| **Basalt** | BSD-3 | 30 Hz 双目里程计（Monado 用它做 VR 头显追踪） | 主要为双目 + IMU 设计，纯双目模式要实测；Windows 要移植；没有重定位 |
| **RTAB-Map** | BSD-3（核心） | 建图、占据栅格（避障）、定位模式与地图复用（位置自知） | 能接外部里程计；有官方 Windows 版 |
| VINS-Fusion / OpenVINS / SVO / DSO | GPLv3 | — | 许可问题和 ORB-SLAM3 一样 |

上表里的许可证、Windows 支持和性能都是**待核实的先验**，还没在我们的数据上跑过。
（更新：RTAB-Map 已在同一批序列上实测，定位精度和速度都优于 ORB-SLAM3，见
`Docs/RTAB-Map双目评估（2026-09-26）.md`。Basalt 仍未测。）
现有的 EuRoC 格式序列（run3_640 / run3_720p，附 OSC 真值）可以直接拿来按本文同一口径
横向对比。

**分析器口径**（`research/tools/analyze_orbslam3_stereo.py`）：

- 轨迹按时间戳去重。`Tracking.cc:2313` 在 RECENTLY_LOST 时会把上一帧的位姿原样再压一次，
  如果不去重，丢追帧会被算成追到了。
- 日志匹配用源码里的真实字符串。`System.cc:240` 把 Verbose 设成了 QUIET，所以
  「Track Lost...」这类消息根本不会输出。

- `.tmp/orbslam3_run2_15hz/`（× 6）
- `.tmp/orbslam3_stereo_run2_15hz/`、`run3_640/`、`run3_720p/`（各 × 3）
- `.tmp/orbslam3_stereo_summary.json`

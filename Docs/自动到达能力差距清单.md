## 一、能力① 知道自己在哪

### 现状（现行实现 = `backend/nav_online.py`）

| 组件 | 事实（实读） |
|---|---|
| **位姿源** | **20 Hz 航位推算**：OSC 速度（ZOH 前值保持）× HMD 朝向。**不是**视觉位姿 |
| **回环** | `nav_loop.LoopCloser`：**ORB + PnP**，**只修平移**，朝向来自 HMD；HMD 相对 yaw 一致性是最强的外点过滤 |
| **漂移** | 两次回环之间是纯航位推算，实测约 **2.8% 路程** |
| **坐标** | 地图系 = SteamVR 站立系换轴（x 前 / y 左 / z 上），原点 = 会话起点；对外为导航系世界米 |
| **深度** | 双目 **SGBM**（`nav_mapping.make_sgbm`），约 21–26 ms/帧；**`backend/` 内没有任何深度模型** |
| **栅格** | 三态（free / obstacle / unknown）；高度相对**观测它的那个关键帧**，故头部俯仰与轨迹 z 漂移不进判定 |
| **可视化** | `GET /worldmodel/navmesh` → `grid_view()` 返回栅格 PNG（一格一像素）＋像素↔世界米换算；前端 `/ui/navmesh.js` |

**接入**：`backend/service.py` 构造 `OnlineNavigator`，并在 11 处调用
（`status` / `grid_view` / `start` / `stop` / `goto` / `explore` / `cancel` 等）。

### 缺什么

| # | 缺口 | 依据 | 验收判据 |
|---|---|---|---|
| **1** | 🟡 **跨会话重定位 —— 用户定稿的 P0**（**2026-10-04 改判，原为 🔴**） | ~~`nav_loop.LoopCloser._candidates()` 只按会话内路径距离取候选 ⇒ **线上链路根本没有全局地点检索入口**；跨会话实测失败（run7：0 接受 / 11 拒绝）~~ —— **该结论已失效**：全局入口 `backend/nav_xsession.py` 已上线且 `enabled=True` 默认开，确认约束 6→**135 条**、抽检 **16/16**，会话末自动采纳已接线。**剩下的洞**：`merged_*.npz` 下游消费未做、**全链零 live 实测**、首会话冷启动。`nav_loop._candidates()` 本身仍只按会话内路径取候选，但那是**另一条通路** | `merged_*.npz` 喂给下游并跑通一场 live，验证端到端收益 |

## 二、能力② 指定位置 → 自动到达

### 现状：**上层没有实现**（这是与原版最大的差异）

原版说"链路已经**全部写好**"，指的是 `nav_target.py` → `route_executor.py` →
`/worldmodel/navtarget/{prepare,confirm,cancel}`。**这三样全仓都不存在。**

经**穷举 `backend/process.py` 的全部路由**确认，`/worldmodel/*` 只有：

```
GET  /worldmodel/status
GET  /worldmodel/navmesh
POST /worldmodel/start | stop | world
POST /worldmodel/navmesh/start | stop | goto | explore | cancel
```

- **没有** `/worldmodel/relocalization`（原版 §一 声称"已有"）
- **没有** `/worldmodel/navtarget/*`（原版 §二 声称"已经全部写好"）

**现有的是另一套更简单的东西**：`navmesh_goto(x, y)` / `navmesh_explore()` / `navmesh_cancel()`
（`nav_online.OnlineNavigator`）——**点级目标与探索**，而且 `goto` 要求
`navmesh` 正在运行且 mapper 非空。

**它不是**"地点解析 → 吸附 → 与视觉地图绑定 → 安全状态机逐拍检查"那条链。

### 缺什么

| # | 缺口 | 说明 |
|---|---|---|
| A | **两条路线未绑定** | 离线 2.5D（`research/recorder/` + `.slam_probe/offline_probe/recorder/`）与在线 navmesh **各有坐标系与尺度**，产物从未绑定 ⇒ "去某地点"无入口 |
| B | **没有地点概念** | `backend/world_model.py` 只做 **W1 世界身份**分区，**不做地点**；语义地标通道实测判别力为零 |
| C | **`navmesh_goto` 够不够用未验** | 它只收 `(x, y)`；而 **LLM 没有依据凭空产出有意义的 (x, z)** —— 见 §三 |
| D | 尺度未定案 | 同 §一 缺口 5 |

## 三、LLM 侧地图工具（**仍然完全没做**）

实测（2026-10-04 更正，原文把**定义数**写成了**注册数**，且分解也算错）：
`tool_defs.py` **定义 20 条**（`body_*` **13** 个、`vrc_*` **6** 个、`world_observe` 1 个；
原写"11 / 7 / 1"加起来是 19，对不上）；
其中带 `@llm_tool`、作为**独立工具**给主 LLM 的只有 **11 条**（`__init__.py` 11 处装饰器，
与 `instructions.py:3` 自称的"11 个工具"一致）。
**其中没有任何一个是地图 / 地点工具。**
⚠️ 另注：另外 9 条里 **4 条**（`body_arm_pose`/`body_hand`/`body_reach_and_grab`/`body_vrchat_input`）
走**共用入口 `debug_command`，agent 是可达的**（该入口无 `agent_auto=false`）；
只有 **5 条**（`body_enable`/`body_disable`/`body_reset`/`vrc_vision_start`/`vrc_vision_stop`）
是 `panel_command`，agent 真调不到。详见 `Docs/README.md` §三 **C8**。

最小工具集（建议沿用 `vrc_` 前缀）：

| 工具 | 作用 | 返回要点 |
|---|---|---|
| `vrc_map_status` | 地图是否可用 | `available / revision / scale_validated / keyframes / generation_state`；不可用就明确说不可用 |
| `vrc_whereami` | 我现在在哪 | `state / x / z / yaw / pose_source`；未知时返回 `unknown` + 原因 |
| `vrc_place_list` | 有哪些能去的地点 | 地点 id、语义标签（若有）、是否可达、坐标 |
| `vrc_goto_prepare` | 提交目标（**不发任何动作**） | 吸附结果、`snap_distance_m`、`blocking_reasons` |
| `vrc_goto_confirm` | 在 route revision 上确认 | 才真正开始执行 |
| `vrc_goto_cancel` | 取消 | — |

配套必须做：

- `instructions.py` 增补约束条款：**坐标只属自建坐标系**、未知不许猜、confirm 前不移动、
  被拒绝时回报拒绝原因而**不是**换目标重试。
- **LLM 该给的是地点 id / 语义名，不是裸坐标** —— 它没有依据凭空产出有意义的 (x, z)，
  需要一份"能去的地点清单"来选。

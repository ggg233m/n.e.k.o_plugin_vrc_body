# 自动到达能力：差距清单（2026-09-23 基于实读代码）

> 目标拆成两个能力：**① 知道自己坐标（重定位）**、**② LLM 指定位置 → 自动到达**。
> 本文只列"缺什么 / 为什么 / 怎么验"，不改代码。所有条件均抄自实读代码，不是设想。

---

## 零、先说清一件事：坐标是哪个坐标系

- **能做到**：在**自建地图坐标系**（`self_built_map_frame`，单位米，原点＝建图起点）里知道自己在哪。
- **做不到**：在 VRChat **世界坐标**里知道自己在哪。OSC 只回传速度、没有位置；这是既有结论，不是缺实现。
- `relocalization_map_live.json` 里 `world_coordinate_anchor: False`、`navigation_truth: False` 就是在声明这一点。

⇒ 对"指定位置自动到达"来说，**自建坐标系够用**（地点之间的相对关系是真的），但**不能承诺"游戏坐标 (x,y,z)"**。

---

## 一、能力①：知道自己坐标（重定位）

### 现状
已有：视觉地图产物（`relocalization_map*.json/.npz`）、PnP 几何门 + 连续帧确认（`confirmations`）、只读观察器（`relocalization_observer.py`）、HTTP `GET /worldmodel/relocalization`。

### 缺什么（按依赖顺序）

| # | 缺口 | 依据 | 验收判据 |
|---|---|---|---|
| 1 | **尺度标定**（`meters_per_unit`） | 06:18 会话 `scale_samples=0`、`reason=timestamp_gap` | 一次连续运动后 `scale_validated=true` 且 `meters_per_unit>0`，残差稳定 |
| 2 | **OSC 与 WGC 同钟且不断档** | `scale_reason="timestamp_gap"`；`README` §WGC/OSC/HMD 时间对齐要求同一单调域 | 连续 30 s 内 `velocity_fresh` 不中断，最大洞有界并记录 |
| 3 | **相机内参用标定值** | `camera.K` 现为假设 fx=fy=320 / FOV 90°，`aspect_match=false` | 在线链路读到已标定 `fov_calibration2.json`，裁剪保持 aspect |
| 4 | **转头不丢跟踪** | `max_jump_rotation_deg=35`，5 Hz；06:18 会话 `segment_count=4` | 原地左右各转 90° 后仍在同一 segment，`new_segments` 不增 |
| 5 | **禁跨段匹配** | 现在段间坐标系互不相连（`slam_core.py:1026-1055`） | 跨 segment 查询一律 `unknown`，绝不返回另一段的坐标 |
| 6 | **丢失时明确 unknown** | 设计已对（`unknown/lost` 不伪造） | 遮挡/断档时返回 `unknown` 且给出 `reason`，不返回上一次的旧位姿 |

### 最小可用标准（能力①算是"有了"）
同一会话内、同一 segment 中，**用当前画面能以 ≥2 次连续确认给出 (x, z, yaw) 米制坐标**，且丢失时老实报 `unknown`。

## 二、能力②：指定位置 → 自动到达

### 现状
链路已经**全部写好**：`nav_target.py`（解析目标 → 规划）→ `route_executor.py`（prepare/confirm/step，安全状态机）→ HTTP `/worldmodel/navtarget/{prepare,confirm,cancel}`。
它现在不是不能用，是**所有门槛都不满足**，所以每一步都在拒绝（这是对的）。

### 硬门槛速查（抄自代码，缺一条就拒绝）

`nav_target.binding_error()`：
1. 视觉地图已加载且有 `revision`
2. `nav_map.meta.visual_map_revision == visual.revision`
3. `coordinate_system == "self_built_map_frame"`
4. `meta.scale_validated == True` 且 `meters_per_unit > 0`，**且** `visual.scale_validated == True` 且两者值相等

`nav_target.resolve_target()`：
5. `segment_id` 已知（不能 None）
6. 目标吸附到**同 segment** 的有效 `place_candidate` 或 `traversable` 边，半径 0.75 m
7. 最近候选必须有效（非 `unknown` / `alias` / `discontinuity`）

`nav_target.plan_to_target()`：
8. 起点位姿也在同 segment 走廊内
9. 选中边 `depth_verified=True` 且 `depth_state="passable"` 且 `corridor_half_width_m ≥ 0.75`
10. `meta.movement_basis_validated == True`

`service._route_safety()`（**执行期每一拍**都要满足）：
11. `velocity_fresh`：OSC 速度新鲜
12. `depth_ok`：深度 ≤1.5 s、`source=validated_depth`、map_revision 与 segment_id 均一致、`state=passable`
13. `progress_confirmed`：`localized` 且 `confirmations ≥ 2` 且导航图 available 且**时间对齐 aligned**
14. 朝向注释明确：**缺 HMD 时间戳就暂停，不许拿视觉 yaw 或 scheduler 虚拟 yaw 顶替**

`route_executor.py:222`：
15. `localization_state == "localized"` 且 `confirmations ≥ 2`，否则不推进

### 缺什么

| # | 缺口 | 说明 |
|---|---|---|
| A | **导航图与视觉地图绑定** | `nav_map_live.meta.visual_map_revision = null`、`meters_per_unit = 0`、`generation_state = invalid`。这是当前**第一阻塞** |
| B | **至少一个 `is_goal_allowed = true` 的节点** | 06:18 会话 55/55 节点 `unknown=True`、`reason=drift_suspected` ⇒ 没有任何可到达目标 |
| C | **深度层给出 `passable` 走廊** | 现在 `scale_samples=0`、深度未标定；三态仍用占位 `t_react`/`a_min` |
| D | **位姿源单一依赖视觉** | `progress_confirmed` 只认 `relocalization_status()`；而 `OnlinePose2D`（OSC+HMD 的 DR）已存在却**没进安全判据**。视觉一丢，整条路线就卡死——这是"方向乱"的架构根因 |
| E | **LLM 侧完全没有地图工具** | `tool_defs.py` 只有 `vrc_autonomy_goal`（追画面里的目标）、`vrc_wander_step`、`vrc_semantic_commit`、`vrc_vision_frame`。**没有任何"查地图/查自己在哪/去某地点"的工具** |

## 三、LLM 接线需要新增什么（能力②的上层）

最小工具集（建议命名，沿用 `vrc_` 前缀）：

| 工具 | 作用 | 返回要点 |
|---|---|---|
| `vrc_map_status` | 地图是否可用 | `available / revision / scale_validated / segment / generation_state`，不可用就明确说不可用 |
| `vrc_whereami` | 我现在在哪 | `state / x / z / yaw / confirmations / segment_id`；未知时返回 `unknown` + 原因 |
| `vrc_place_list` | 有哪些能去的地点 | 地点 id、语义标签（若有）、是否 `is_goal_allowed`、坐标 |
| `vrc_goto_prepare` | 提交目标（**不发任何动作**） | 吸附结果、`snap_distance_m`、`blocking_reasons` |
| `vrc_goto_confirm` | 在 route revision 上确认 | 才真正开始执行 |
| `vrc_goto_cancel` | 取消 | — |

配套必须做：
- `instructions.py` 增补约束条款（现有第 23–30 条的风格）：坐标只属自建坐标系、未知不许猜、confirm 前不移动、被拒绝时回报拒绝原因而不是换目标重试。
- **LLM 该给的是地点 id / 语义名，不是裸坐标** —— LLM 没有依据凭空产出有意义的 (x, z)；它需要一份"能去的地点清单"来选。

## 四、建议的最小路径（按顺序，跳步无效）

1. **止血**：视觉位姿不再独占安全判据；DR（`OnlinePose2D`）作为连续位姿源进入 `progress_confirmed` 的候选，视觉只做修正与重定位触发。
   → 先让"知道自己在哪"在丢视觉时不至于归零。
2. **修输入**：采样率（5 Hz 对转头太慢）、内参接标定值、裁剪保持 aspect。
3. **修 OSC 时间断档** → 让 `scale_samples > 0`。
4. **绑定**：`nav_map.meta.visual_map_revision` 与 `meters_per_unit` 写进在线图 → 消掉 `navigation_map_frame_mismatch`。
5. **禁跨段匹配** + 段内才允许 `localized`。
6. **受控录制**（你那一步）→ 才有"持续匀速 + 明确停止 + 驶向墙面"三类样本，用来标定深度三态的 `t_react`/`a_min` 与尺度。
7. 最后才接 LLM 工具层（第 1–6 步没成之前，接了也只会一直被拒绝）。

---

## 五、一句话

**能力①②的下层代码基本都写完了，缺的不是功能，是三件事：尺度没标定、位姿源单一依赖不可靠的视觉、LLM 侧没有地图工具。**
按 1→7 的顺序做，第 1 步（止血）能立刻让状态从"永远 invalid"变成"可以观察地推进"；第 6 步（受控录制）不由代码决定，卡在你手上。
